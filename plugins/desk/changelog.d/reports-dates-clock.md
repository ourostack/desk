The factory reports now carry each task's finish day and the operator clock ([`walk.js`](mcp/src/factory/pipeline/walk.js), [`stretches.js`](mcp/src/factory/pipeline/stretches.js), [`build.js`](mcp/src/factory/pipeline/build.js)). `jobs/<job>.json` gains `timeline.finished_on`, the task's UTC finish day as an envelope `{ state, value, basis, reasons }` read from published facts `/4`: measured when a session moved the card to `done` or `cancelled` (`basis: "transition"`), an upper bound when only the card's last update gives the day (`basis: "card_updated"`, reason `finish_from_card_update`), the latest day with the reason `reopened` when sessions finished the task on different days, and unavailable with its reason for an open task (`open_job`), a public desk (`job_offsets_withheld`), older facts (`not_in_published_facts`) or a job clock that could not be read (`job_offsets_unavailable`). The same envelope is on every `rollups/tasks.json` and `rollups/stackup.json` row as `finished_on`. The timeline also gains `human_turns_state` and `prs_state`, which say how whole the lists of operator prompts and pull requests are, so a task whose prompts were not recorded reads "not recorded", never "no prompts"; `prs[].created`, which says whether a session of the task created the pull request (`true`), only mentioned it (`false`) or ran before facts `/4` (`null`); a created pull request's `at_ms` is only ever a creating call's time, and it has none when no creating call was timed; and `waits[]`, one entry per after-stop wait `{ host, session, start_ms, end_ms, next_prompt_ms, stop, reasons }`, where `stop` is the facts' record of how the agent's turn ended (`null`, reason `not_in_published_facts`, before `/4`) and `next_prompt_ms` is the idle next-prompt time inside the lead window that the wait holds, so the waits plus the next-prompt time no wait holds add up to `waiting_by_waited_on_ms.next_prompt`. `timeline.waits_state` states that figure's state, reasons and bound for the list; when the figure is unavailable, every `next_prompt_ms` is `null` with the figure's reasons. A wait the task's segments cut is listed once per part. Every existing key keeps its meaning.

Counting change: time inside a question or plan tool's wait (a human wait whose stop is `ask_question` or `ask_plan`) is now idle `next_prompt` time, not working time, because the agent was waiting on the operator's answer; only another worker of the task working meanwhile still counts as work. Working time and flow efficiency therefore fall, as do the labeled times inside the ask (such as `value_in_working_ms`, the stack-up's `class_ms` and `waste_ms`, and `not_labeled_ms`), `next_prompt` waiting rises, and a wait of 15 minutes or more can split a work burst and add a gap, for tasks whose agents asked through those tools, once their sessions are derived again with the stop facts. Time an evaluator labeled as a long tool call there now reads as waiting on the next prompt. The formulas' recorded active time (`active_time_ms`, `active_share_recorded`) does not change.
