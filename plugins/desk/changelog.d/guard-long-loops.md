The checkout guard now decides long shell loops instead of blocking them. Before a shell command runs, the guard walks its syntax to find Git calls that would move a protected checkout. A `for` loop whose body ran a command with an unknown exit status used to double the paths it walked on every iteration, so a loop over about ten values ran past the guard's step budget and the guard blocked the whole command, which the host records as a failed tool call. The walk now merges identical states after each loop iteration, and stops inspecting once one Git call is denied, so a loop costs steps in proportion to its length ([shell-commands.js](mcp/src/runtime/shell-commands.js), [protected-checkout.js](mcp/src/runtime/protected-checkout.js)). This is the countermeasure for kaizen card [ourostack/factory#39](https://github.com/ourostack/factory/issues/39), whose hypothesis is fewer tool failures per job.
