### Fixed

On Windows, a factory writer queued behind other writers no longer fails with a permission error opening a lock file. The wait for a lock file whose deletion is still pending (Windows reports a permission error, not "exists") was a single five-second budget counted from the start of the whole wait, so a writer that had queued behind many others, such as sixteen concurrent deliveries, used the budget up on the queue and then failed on the next pending delete. The budget now counts one run of consecutive refusals and starts again each time the lock is seen held, and "busy" is waited out like the other two codes. A refusal that lasts five seconds still surfaces, and no refusal is ever treated as acquiring the lock. A stale lock file that cannot be removed is now waited on between tries instead of retried in a tight loop. Other platforms are unchanged. No emitted or published field changes.
