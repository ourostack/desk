On Windows, a Desk server waiting for another server's runtime cache build no longer crashes when the lock folders are briefly unavailable. Windows answers EPERM, EACCES or EBUSY, instead of "already exists", to a folder that is being deleted or that another process has open. A waiter checks the reclaim folder on every poll, so with several servers starting together it could hit that answer and fail its whole start-up with `EPERM: operation not permitted, mkdir '…publish-lock.reclaim-lock'`. Those answers now mean "someone else has it": the waiter waits and tries again inside its existing 30 second limit, and the removal of a lock folder retries them before giving up. An owner that cannot release its lock after the retries now fails with a message that names the lock, and any other error is still thrown as before. Other platforms are unchanged.
