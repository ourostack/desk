A merged Desk pull request is now delivered only when a release has carried it, and CI and Desk enforce that so nobody has to remember it.

After a release is published, the release workflow comments `Released in Desk <version>` on every pull request that release carries and adds a `released` label. The pull requests are the merged ones since the previous release commit, so a release that finally succeeds after a failed run also marks what the failed run left behind. Marking is safe to repeat. If it fails, the "Desk release needs attention" issue says so.

The done-gate reads a delivery policy that each repo declares in `.desk/delivery.json`: rules that match changed paths (`paths` globs, first match per file wins) and say when a change is delivered, `merge`, `github_label` (a named label) or `git_ref` (the merge commit is in a ref matching a pattern such as `refs/tags/v*`). For a pull request that has to wait for its rule, `task_update` (and `task_archive`, when it bumps a task to done) refuses to close the task until the rule is met, and the refusal names the pull request and says the release has not carried it yet. A repo with no policy defaults to `merge`, and the response says "no delivery rule declared". This repo's policy waits on the `released` label for `plugins/desk/**` only, because Crew, Superpowers and Plain Language bump their own version in the pull request that changes them, which is how Claude Code receives them. When GitHub cannot be reached or does not answer, the check is skipped and the response carries a `delivery_check` line saying the delivery was not verified, so a desk without network can still close tasks. The check is one function, `prDelivery` in `tools/delivery-gate.js`, that other callers can reuse.
