`task_update` and `task_archive` now queue the waste evaluator's request (`evaluate-requests/<job>.json`, [`requestEvaluation`](mcp/src/factory/outbox.js)) on the same terminal-status transition where they already queue the finalize request, closing a wiring gap ([ourostack/desk#77](https://github.com/ourostack/desk/issues/77)) that left the request's only path a manual `factory.js evaluate --task` run by hand — documented in [`task-lifecycle`](skills/task-lifecycle/SKILL.md) but never actually wired into the tools, so `ourostack/factory`'s `reports` rollup read "0 of 73 jobs fully labeled" and a fresh machine's `evaluate --pending` always answered `{"jobs":[]}`. The request fires on the transition to either `done` or `cancelled`: [`factory-local-capture`](docs/factory-local-capture.md) already treats both alike as a finished job, and the waste in a cancelled job is exactly what the evaluator needs to see. It shares the finalize request's opt-in gate — no factory state on this machine yet is a silent no-op that creates nothing — and the same fail-safe behavior: any error recording the request is caught and logged, never blocking or reopening the task, and neither status ever waits for it. The job identity the two requests share is now resolved once per terminal-status sync instead of twice. Reading an already-archived card's status to decide whether to request an evaluation is also now fail-safe: corrupted frontmatter on that card degrades to no evaluation request instead of throwing out of `task_archive` and breaking its `already_archived` idempotency; the finalize request still fires. [`task-lifecycle`](skills/task-lifecycle/SKILL.md) and [`factory-local-capture`](docs/factory-local-capture.md) now describe the request as automatic rather than a step to run by hand.
