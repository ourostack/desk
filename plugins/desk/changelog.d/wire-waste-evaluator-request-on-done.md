`task_update` and `task_archive` now queue the waste evaluator's request (`evaluate-requests/<job>.json`, [`requestEvaluation`](mcp/src/factory/evaluate-run.js)) on the same terminal-status transition where they already queue the finalize request, closing a wiring gap ([ourostack/desk#77](https://github.com/ourostack/desk/issues/77)) that left the request's only path a manual `factory.js evaluate --task` run by hand — documented in [`task-lifecycle`](skills/task-lifecycle/SKILL.md) but never actually wired into the tools, so `ourostack/factory`'s `reports` rollup read "0 of 73 jobs fully labeled" and a fresh machine's `evaluate --pending` always answered `{"jobs":[]}`. The request fires only on the transition to `done`, matching `evaluate-run.js`'s own "done step" design; `cancelled` still queues its finalize request exactly as before, but no evaluation, since a cancelled task has no finished job to label. It shares the finalize request's opt-in gate — no factory state on this machine yet is a silent no-op that creates nothing — and the same fail-safe behavior: any error recording the request is caught and logged, never blocking or reopening the task, and `done` still never waits for it. [`task-lifecycle`](skills/task-lifecycle/SKILL.md) and [`factory-local-capture`](docs/factory-local-capture.md) now describe the request as automatic rather than a step to run by hand.
