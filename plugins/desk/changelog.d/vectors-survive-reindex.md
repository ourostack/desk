Meaning-based search (`desk_recall`, `desk_similar`) now becomes ready on a busy desk that older Desk builds also write to. Desk stored each section's embedding by the section's row number, and re-indexing a card gives every section a new row number even when its text is unchanged. On a desk where an older session re-indexed a busy card every minute or so, each pass embedded thousands of sections only to lose them at the next re-index, so recall never became ready and the index file kept growing. Embeddings now live in a new `text_vectors` table, keyed by the section's text and the embedding settings that made them, so they survive any re-index; an edit embeds only the sections whose text is new, and re-indexing a card rewrites only the sections that changed, so an append to a long card writes one row instead of rewriting them all. A vector is saved only while a section with its text still exists, and vectors no section uses are removed after an hour.

The first start of this build copies the old table's embeddings into the new one without asking the embedding service for anything, and copies only those whose section still exists. The old row-keyed `chunk_vecs` table stays for older builds on the same desk, which keep working; this build removes the old rows no build can read, in short batches, without rewriting the database file.

When Ollama answers that a section is too long, in either its older ("input length exceeds the context length") or newer ("input (N tokens) is too large to process") wording, only that section is skipped and every other section is still embedded. `desk_status` says in plain words how many sections are too long for the embedding model and that exact-word search (`desk_search`) still finds them.
