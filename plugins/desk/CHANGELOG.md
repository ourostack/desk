# desk plugin — changelog

## 3.2.0-alpha.177 — 2026-10-02

Desk's [browser launcher](mcp/web.cjs) now finds Windows browser installations when environment variables retain their original casing, such as `ProgramFiles`, instead of requiring uppercase names. Its macOS path calculation also stays POSIX when exercised from a Windows host. Browser lock tests no longer assume a Unix PID exists.

The [bootstrap's installation hints](mcp/bootstrap.cjs) also compose POSIX script paths for Linux and macOS, regardless of the host exercising that branch.

Native Windows validation now runs package scripts through the selected Node's npm entry point rather than trying to execute a command shim directly. The test preload excludes the machine's system Git configuration, so line-ending policies cannot break fixture commits; it does not change that configuration. Startup and card-guard tests retain their behavioral checks without asserting POSIX separators or execute bits on Windows.

Fixture-only POSIX probes remain separate from the real native Node probe and MCP handshake checks.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.176 — 2026-10-02

### Boot says when the running Desk is behind main, and refreshes it

Hosts cache plugin downloads (Agency keeps them for 24 hours), so a session could run a Desk many releases old while the fix for the bug in front of it had already shipped, with nothing saying so. Boot now compares the running plugin's version with `plugins/desk/plugin.json` on `main`. When it is behind, boot starts a refresh of the host's cached copy in the background and prints one line near the top, for example `Desk 3.2.0-alpha.153 is 19 releases behind main (3.2.0-alpha.172); refreshing the Agency plugin cache in the background, so a new session will run 3.2.0-alpha.172.` The `--json` result carries the same finding as `stale_desk` (`running`, `latest`, `behind`, `channel`, `refresh`, `auto_refresh`, `line`), or `null`.

Boot never waits for the refresh. It writes its output first, then starts a small detached runner and exits. The runner runs the host's command in its own process group, kills the whole group after 8 seconds so no launcher or npm shim child survives, records the outcome in `desk-refresh.json` and `repairs.log` in Desk's state directory, and releases its claim. The attempt is claimed atomically before anything is spawned and happens at most once an hour per machine, so agents that boot together start one refresh. The commands are the host's own: on Agency, `agency plugin cache remove -f <spec>`, where the spec is the `ourostack/desk` plugin on `@main` for the session's engine (`AGENCY_ENGINE`, else the agent host), read from Agency's cache index and matched to the running version; on Copilot, `copilot plugin update desk`, only when Desk is installed under Copilot's `installed-plugins` directory (`$COPILOT_HOME` or `~/.copilot`), never for a `--plugin-dir` or a development checkout; on Claude Code, `claude plugin update desk@<marketplace>`, with the marketplace read from where Desk is installed. Where no command can be derived, or the last attempt in the hour failed or is still recorded, the line names the manual step instead (`/plugin` on Claude Code; `copilot plugin update desk` or `agency plugin cache remove "copilot:github:ourostack/desk:plugins/desk@main"` on Copilot). `auto_refresh` says what boot did: `started`, `failed` (the recorded attempt failed), `skipped` (an attempt in the last hour), `unavailable` or `disabled`.

Versions compare as semver, so `alpha.9` is older than `alpha.10`; the release count appears only when both versions share the same `major.minor.patch-alpha` line, and otherwise the line says just "behind". The remote version string is capped at 64 characters, the response at 4 KB, and numbers above the safe-integer range are rejected. The version lookup never slows or breaks boot: it starts in parallel with the rest of boot, is cut off after 1.5 seconds, sends no credentials, caches its answer in the state directory (`latest-version.json`) for an hour (a failed lookup for 10 minutes), and says nothing on any error, timeout or offline machine. `DESK_BOOT_VERSION_CHECK=0` turns the check off and `DESK_BOOT_AUTO_REFRESH=0` turns only the refresh off; both are also off inside node:test runs and in the boot-acceptance harness's child environment.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.175 — 2026-10-02

Desk's MCP server declarations can no longer drift between hosts or use a name a model API reserves. A new test reads the real `.mcp.json`, `.mcp.copilot.json`, plugin manifests and activation manifest of every plugin in the repository and fails when the two host files declare different server names, types, commands or entry files, the failure behind `web-browser_click` surviving the first rename on Copilot. The same test rejects any server name on the reserved list (`web`, `functions`, `multi_tool_use`, `browser`, `python`, `container`, `file_search`, `computer`, `image_gen`, `tool`, `tools`, `default`, `api`, `mcp`), any name outside `^[a-z][a-z0-9-]*$`, and any name where `<server>-<longest tool>`, or Claude's `mcp__plugin_<plugin>_<server>__<tool>`, would pass 64 characters. The list is the exported `RESERVED_MCP_SERVER_NAMES`. No server or tool name changes.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.174 — 2026-10-02

Several Desk versions often run at once against one factory state folder, and the factory now stays safe when an older Desk shares it. A retracted session's local copies move out of `outbox/<store-slug>/` into `retracted-copies/<store-slug>/` when the delete is pushed, so an older Desk's flush, which publishes everything it finds in the outbox, can no longer send retracted sessions back to the store. A route back moves the copies home before they publish, every flush migrates any copy of a retracting or retracted session still in the outbox, and files already placed in `retracted-copies/` by hand are adopted. Copies are never deleted.

A local facts or labels file that fails validation only with unknown keys, that declares a newer schema version, or whose derivation records a newer binding version, was written by a newer Desk. The flush now leaves it where it is, does not quarantine it, and counts it as `newer_format` in the store's status entry, so a newer Desk's multi-job sessions are no longer held back by an older process. Every other validation failure is still quarantined as before. See [factory local capture](docs/factory-local-capture.md).

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.173 — 2026-10-02

### Protected-checkout guard: fewer false denials

The protected-checkout guard keeps denying any PowerShell statement that names `git` outside the plain forms, and now allows two narrow statement shapes that provably run nothing: `Get-Command`/`gcm` with only literal names and common parameters, and `Write-Output`/`Write-Host`/`echo` with only literal arguments. They may be piped only to Select-Object, Format-*, Where-Object, Out-String or Out-Null (Get-Command) or to Out-String or Out-Null (Write-*), and only at the top level of the command. A string piped to `iex`, `cmd`, `bash` or any other element, a group, a member access, a redirect or a variable keeps the old denial.

With a checkout Desk cannot resolve (for example `git -C $r …` inside a `foreach`), plain read-only Git already passes, and a fetch into remote-tracking refs, tags or notes (`+refs/heads/*:refs/remotes/origin/*`) now passes too. A fetch into a local branch, `--update-head-ok`, and every mutating subcommand still fail closed. Bash and PowerShell share this rule.

Denial messages now lead with the fix, because hosts cut a denial at about one line: "Desk blocked this: run each git command as its own plain statement, e.g. git -C <path> status; git -C <path> fetch." and "Desk could not resolve which checkout this Git command runs in; write it literally or set it in a separate command first."

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.171 — 2026-10-01

A task card's status must now be one of the eight lifecycle states: `task_create` (`status`) and `task_update` (`frontmatter.status`) reject any other value and list the valid ones. A new agent-work migration, `03-normalize-task-status`, finds cards that carry a ghost status and prints one `task_update` for each. It folds case and the separators `-`, `_` and space, then maps `active`, `doing` and `in progress` to `processing`, `planning` and `backlog` to `drafting`, `needs review` to `collaborating`, and `waiting` to `blocked`. A value it does not know is reported and left alone, because the migration never guesses.

The factory's publish guards now cover model ids and plugin names the way they already covered agent names: a model id that cannot be published becomes `unknown`, and a plugin whose name cannot be published is hidden. One predicate decides this for both the public token check and the published-field check. A token count that is not a safe integer is now `null` with an `unavailable` entry on every host, `requested_model` is left out when it equals `model`, and the helpers the three host derivers shared now live in one module. A rejection the store reports for a file with no local key now quarantines nothing and is only counted.

A session marker written by a hook older than the one that started recording each plugin's source now gets its plugin sources filled in when the facts are derived, by the same lookups the end hook uses. On Claude Code, which keeps every installed version at `cache/<marketplace>/<name>/<version>/`, a plugin takes the source the hook reports for the one marketplace whose cache holds that name and version; when no marketplace or more than one holds it, the source stays empty. On Copilot CLI, the plain-install records in `config.json` and Agency's cache are both asked for the exact name and version, and each answers that nothing is there, that what is there conflicts (its source is not one GitHub repository, or is ambiguous), or the repository. Any conflict leaves the source empty, an answer that nothing is there never blocks, and the source is used only when every answer that names a repository names the same one. A plugin whose source stays empty stays hidden, so a backfill never publishes a name it cannot vouch for.

A Codex session no longer routes to the public store on a guess. Codex markers record no plugins, so a Codex marker whose route comes from the default, because the desk has no `_meta/factory.json`, is held with the reason `route_unverified` until a Claude Code or Copilot CLI marker for the same desk, within 30 days, also routed by default; that marker's plugin registry was checked, so an overlay would have shown. A desk that declares its store routes Codex at once. Kaizen filing ignores a Codex route that was never proven.

A controller that works several jobs in one session no longer has its whole time copied into each of them. The binder now records, for each of the controller's jobs, the spans of the session its own evidence gives that job (Desk tool calls, file writes, desk commit windows and its spawns), the factory pipeline counts only those spans of the controller's time toward the job, and a pull request the controller opened goes to the job whose span holds its creation time. The controller's tool calls are split the same way, by the span that holds each call's start. Evidence that names two jobs at the same moment, such as one desk commit touching two task folders, makes the time that follows shared by both, and only a shared span is counted in both jobs and marked `worker_shared`. Each session whose marker is still under 30 days old is re-derived once at binding version 4 and gains its spans; facts of older sessions, whose markers are gone, keep their old numbers. A public desk publishes neither the spans nor the pull request times.

`factory reconcile --desk <absolute path> --since <time> --until <time> [--store <directory>]` compares a desk's real task activity over a window with the factory's jobs and prints every mismatch with a reason code (`no_marker`, `not_opted_in`, `route_changed`, `held`, `log_missing`, `stale_binding`, `not_delivered`, `quarantined`, `pr_open`, `card_missing`, `invalid_status`, `mechanical_only`, `store_only`). It reads the desk's Git history, the local factory state and, with `--store`, a local checkout of the store; it never writes, and it prints task names only for the desk it is given and never prompt text or the machine secret. A task with no bound session is always `no_marker` (detail `unbound_markers_<n>`), and a top-level `unbound_markers` list gives each unbound marker in the window its own reason, so a marker is never blamed on a task. A `pr_open` read from the last flush without `--store` has the detail `pr_<n>_unchecked`, and a `store_only` row for a job this desk cannot map prints `job: null`. On a keyed (public) desk, `store_only` fires only for jobs with local facts on this machine. The commit rule that decides which commits count for a task, housekeeping edits and sweeps excluded, is now one function shared by the binder and reconcile.

A job whose sessions are all split among several jobs no longer reports tool retries and API retries as a measured zero: neither can be attributed to a worker, so both are now unavailable (`worker_split`). Compactions of an all-split job now report the same reason (`worker_split`) instead of `partial`. With some whole sessions they are the sum over those sessions and marked partial, and both measures now carry the same `worker_shared` flag as the job's time.

When a delivered file's session now routes to a different store, the next flush to the old store deletes the file in its intake pull request. This covers every session whose marker is under 30 days old and positively routes elsewhere, and every older session whose desk, at the desk root its derivation receipt recorded, now declares another store in `_meta/factory.json`. It does not cover a session whose receipt predates the recorded desk root and whose marker is already pruned, a session whose desk folder is gone or reaches another store only by the default route with no fresh marker, a session whose desk declaration is invalid (frozen until it is fixed), or a session whose facts are quarantined; those stay in the old store. Three rules keep this correct whatever order things happen in. First, a flush never publishes a session to a store unless it routes there, and this holds for every file, including a session the flush has no record of and a file released from quarantine. A positive route comes from a marker under 30 days old or, once the marker is gone, from the desk's own declaration at the recorded desk root. Otherwise the session keeps its last known route: the route the flush last saw it give, which it keeps in the session's derivation receipt with the desk root (both stay local and are never published), else the store the sweep derived it to. So a session pending for more than 30 days, labels evaluated long after their session, and a session whose desk folder moved still publish. A declaration that is present but unreadable or invalid, at the marker's desk root or, once the marker is gone, at the receipt's, freezes the session, and so does a marker whose hook recorded that it could not resolve a route: the session is counted as `route_unknown` and is neither published nor deleted until the declaration is fixed. Only a missing or pruned marker, a marker with no desk root, a desk folder that is gone or an older hook that recorded no overlay check keeps the last known route. An open retraction stays stalled and a tombstone stays away even then. A session with quarantined facts is frozen and counted as `held_elsewhere`. Frozen sessions are never published, never deleted and never make a flush go online. Second, every flush that goes online builds the intake branch from what the current state wants: the files to publish and the deletes still needed. When that is nothing, it closes this machine's open intake pull request and resets its branch, so a delete the state no longer wants can never merge, even if the local record of it was lost. The flush records in its status that it pushed a batch, with each pull request's number and head, and goes online once more to settle it; a pull request pushed under an earlier head (the account gained push permission, or the consent record names another account) is closed by its number. A `store_missing` answer clears that record. An idle flush with nothing pushed, nothing to publish and nothing being retracted still makes no network call. Third, retraction never deletes local files. A file is deleted only when the store holds, at the path this machine delivered it to, exactly the blob it delivered, and store names compare without regard to case. Once the delete is pushed the session is retracting, in its own protected record beside the delivered ones; when the store's default branch no longer has the file, that record becomes a tombstone that keeps the session away from the old store even if `status.json` is lost. If the session later positively routes back, the tombstone is cleared and its kept local file is published again, restoring the store's copy whether or not the delete had merged. A retraction whose route can no longer be shown positive keeps its record, leaves its delete out of the branch and is counted as `retraction_stalled`. A tree listing that GitHub truncates never counts as the file being gone. When a flush is online anyway, it also deletes a copy it finds in the store of an away session it has no record of, if the blob is exactly what this machine would publish for it. A retraction removes the session's facts file and every labels file this machine delivered for it, so a machine-keyed name is deleted exactly as it was published. A flush with only deletions still opens the pull request, whose body adds a line such as `Retracted: 2 files (route_changed)`; the line gives a count and never names the other store or a session. A delete the store refuses returns the session to delivered and is counted as `retractions_refused` in the flush status; it is not retried while the route stays elsewhere, and the entry is cleared as soon as the session's route changes. `desk_status` and `desk_doctor` count an outbox file the flush places elsewhere (away, a tombstone, stale or stalled) as `route_changed` instead of pending, and `factory reconcile` reports such a session as `route_changed`, all through the same route helper as the flush. Two limits remain. A pull request under an earlier head that the current account cannot close stays recorded and can still merge. And if the flush status and the retracting record are both lost while a delete pull request is open, and the session's route also becomes unknown, that pull request can still merge. The store's `validate-pr` accepts the deletion of a file at a facts or labels path, with no content to check, only from a maintainer (owner, member or collaborator), so a contributor without that association cannot retract and is refused as `removal`; a maintainer's retraction is not held as maintenance, and renames are still refused. Git history keeps the deleted content.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.170 — 2026-10-01

### Guard: inspection Git no longer outlives its hook, and the tests clean up after themselves

The protected-checkout guard reads repository state through `git symbolic-ref` and `git config`. When a read hung (a FIFO include, a stalled filesystem) and the hook was then killed or hit its own deadline, the Git child kept running with its parent gone, sleeping forever; 116 such processes up to 19 hours old were found on one Mac. Each inspection Git now leads its own process group, and the group is killed when the hook exits or receives SIGTERM, SIGINT or SIGHUP (the signal still takes its normal course afterwards). A kernel alarm armed inside the child (`perl` sets `alarm` and then execs Git, so no extra process exists) ends the read one second after its own timeout even if the parent is SIGKILLed or only the hook PID is killed. Windows has neither process groups nor perl, so there only the child itself is killed.

The tests that make Git block on a FIFO now share one helper that wakes or kills blocked readers, and every guard fixture folder is only deleted after anything still running inside it has been killed and has exited. A new regression test kills a parent mid-read with SIGTERM and SIGKILL and asserts no Git process is left in the fixture.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.163 — 2026-10-01

### A task card cannot be rewritten through the shell and committed by hand, and boot says to stop when something is missing

Round E of the boot acceptance runs showed an agent rewriting a live task card with a node script run through Bash and committing it by hand, which skipped every check `task_update` makes. Two layers now close that. First, the desk gets its own git `pre-commit` hook ([`mcp/src/desk/card-commit-guard.js`](mcp/src/desk/card-commit-guard.js)): a commit that adds or edits a live card (`<track>/<slug>/task.md`, or the same under `desks/<alias>/`, including a rename that also edits it) is refused unless Desk itself is committing, and the refusal names `task_update` and the ToolSearch line that loads it. Deleting a card and a pure rename still commit by hand, so archiving by `git mv` is unchanged. Desk installs the hook at boot, in the one-time tidy and when the index opens, and installing again changes nothing. A `core.hooksPath` is respected, a pre-commit hook that was already there is kept as `pre-commit.desk-chained` and runs after Desk's check, and a hook that cannot be installed shows as one `card guard:` line in the boot's degraded list. Desk's own commit path (`task_update`, `task_create`, `task_move`, `task_archive`, `track_*`, `friction_add`, `lesson_add`, `desk_save`) sets `DESK_TOOL_COMMIT=1` for its git call, and so does the tidy's final hand commit in `migrations/02-tidy-desk.md`. `desk_save` now refuses a task card path, so a card cannot ride through the one commit path the hook trusts. Setting `DESK_TOOL_COMMIT=1` or `--no-verify` by hand is a deliberate override and out of scope: the hook stops the accident, it is not a lock.

Second, the task-status guard now also reads `Bash` and `PowerShell` calls, best effort. ## 3.2.0-alpha.130 — 2026-09-29

The checkout guard's cache of already-decided Git calls is now keyed on a call's target and Git's own environment (`GIT_DIR` and its siblings, `GIT_CONFIG_*` overrides) instead of the whole modeled shell environment. A shell loop that calls Git every iteration against the same target — for example `for f in $(ls); do git -C "$dir" status; done`, or a retry loop around a plain `git push` — previously spent one real Git read per iteration even though nothing about the call actually changed, because the loop's own variables (a loop counter, an unrelated export) were part of the cache key and made every iteration look new. A long enough loop could exhaust the guard's 7 s Git-read budget and fail closed on a command that was always going to be allowed. A loop's Git reads are now bounded by its distinct Git targets, not its length; a loop over enough genuinely distinct targets to still exhaust the budget is denied with a reason that says why and what to do instead (split it into fewer targets per command, or run it as a script file), rather than just "retry it." A dangerous Git call inside a loop on a protected checkout is still denied, and still short-circuits the rest of the loop. [ourostack/factory#39](https://github.com/ourostack/factory/issues/39)

Review of that fix found a related, pre-existing gap in the same target resolution: the guard decided which checkout a Git call ran in from the modeled working directory alone, never from `GIT_DIR` or `GIT_WORK_TREE`, so a command whose environment (ambient, or a leading `GIT_DIR=… GIT_WORK_TREE=… git …` assignment) pointed Git at a real, protected checkout was silently allowed whenever the modeled working directory itself did not exist on disk. The guard now also resolves that checkout from `GIT_WORK_TREE`, or the parent directory of a plain `.git` `GIT_DIR`, when the command line does not already say so with `-C`, `--git-dir` or `--work-tree`; an environment value the guard cannot compute is still left for the Git read itself to reject, so it fails closed exactly as it already did.

A relative `GIT_DIR` or `GIT_WORK_TREE` (`cd "$repo" && GIT_DIR=.git git reset --hard`) resolves against the directory the Git call runs in, not the hook's own working directory.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.129 — 2026-09-29

A long-lived session's factory hook stays pinned to whichever cached Desk install was on disk when the session's own process started, even after a newer Desk is installed and even though the session's own plugin metadata (and so its marker and published facts) reports that newer version. A re-derivation run by that stale process was therefore applying binding logic — including a housekeeping exclusion such as [`isCardHousekeeping`](mcp/src/factory/desk-repo.js) — from whatever Desk version it actually started under, while claiming credit for a version that had already fixed the very defect it was still running into: a commit's mechanical, non-substantive touches to task cards could bind as real work again on a later, otherwise-correct republish, simply because the process doing the deriving predated the fix.

`deriveMarker` now compares the Desk version it is actually running (read from its own co-located `plugin.json`, never from the marker or an installed-plugins registry) against the "desk" entry in the marker's own declared `plugins`, and holds — publishing nothing — when its own version is older than what the marker declares. A marker with no "desk" plugin entry, or a deriver at or ahead of the declared version, is unaffected. This does not repair a session already published by a stale deriver; it stops the same stale process from doing it again on its next quiet sweep, restart or hand correction, until a fresher process picks the marker up.

Two refinements keep that hold from ever outliving its purpose. First, the hold now expires: a marker's declared version is frozen at the moment it is written, so if the machine later rolls back to an older Desk, the marker keeps naming a version no installed deriver can ever reach, and an unconditional hold would wait forever, until the marker's own 30-day pruning deleted it and lost the session's facts outright. Past seven days since the marker's `updated_at`, this deriver stops waiting for a fresher process and derives with the code it is actually running instead. Second, the "desk" declaration itself can be ambiguous: two different-origin "desk" installs can coexist in one marker's `plugins`, and when they name different versions there is no non-arbitrary one to trust, so that case is treated the same as no declaration at all and never holds.

Ships `desk-mcp@1.4.0-alpha.6`.

## 3.2.0-alpha.128 — 2026-09-28

**A Desk move, rename, or archive no longer rewrites a task card's YAML just to make its one real edit.** `task_move`, `track_rename`, and `task_archive`'s terminal-status bump used to read a card into an object, merge in the new field, and dump the whole object back to YAML — changing quote style, adding `.000` milliseconds to timestamps, folding a long single-line scalar into a `>-` block, and reordering or dropping comments on every card the tidy touched, even though only `track:`, `title:`, `updated:`, `merged_into:`, `status:`, or `factory_report:` actually changed. They now call a new [`patchMarkdownFrontmatter`](mcp/src/util/fm.js), which finds each named top-level frontmatter line, replaces just that line and that field's own continuation lines with the new value, and appends a field that's genuinely new — leaving every other byte of the card, including quoting, date formats, block scalars, key order, and comments, exactly as written.

[`isCardHousekeeping`](mcp/src/factory/desk-repo.js) also recognizes more of what a real tidy commit produces in history already committed, and in cards other tools still touch directly. A frontmatter scalar now counts as unchanged when it's semantically equal after parsing: a date-only value (`2026-05-26`) equals its midnight-UTC timestamp form, with or without `.000` milliseconds, and a folded (`>-`) or literal (`|-`) block scalar equals the single-line scalar with the same text. A card's body counts as unchanged if it only gained or lost exactly one trailing newline. Anything the parser isn't confident about — a field nested inside a list item, a block scalar with blank lines or a `+` chomp, a changed key order — still counts as real work, matching every other case `isCardHousekeeping` already treated conservatively.

Deriving a commit's diff-tree entries and rename substitutions now happens once per commit `sha` instead of once per card touched, cached for the life of one desk-reader instance, so a tidy commit touching many cards no longer re-derives the same substitutions for each one.

The cards still counted as real work in each case are real work for reasons specific to each: a genuinely new card, a field nested inside a list item that this judge doesn't parse, and a card that gained an actual new field alongside a real body edit.

## 3.2.0-alpha.124 — 2026-09-28

A job's identity is now a task's birth path — the `track/slug` its card, `task.md`, was first added at — instead of its current `track/slug` ([`resolveJobIdentity`](mcp/src/factory/desk-repo.js), [ourostack/desk#76](https://github.com/ourostack/desk/issues/76)). It also refuses when a track this run's own staged renames moved a folder into now holds a task card, live or archived, whose `track:` field doesn't name it — the mark a raw `git mv` leaves behind instead of going through `track_rename` — while a track this run never renamed is never scanned, so pre-existing bad data elsewhere never blocks an unrelated, correctly checked tidy. The printed procedure now says plainly, in its own step, that a raw `git mv`, a bare `git add -A` or folder/pattern add, and deleting `.git/index.lock` are forbidden, that a track or task only ever moves through `track_rename` or `task_move`, and that step 5 and step 6's own raw move of an emptied or stale track into `_archive/` is the one exception, since no track-archive tool exists yet.

## 1.3.2 — 2026-05-26

**Git-hygiene: mass-history-rewrite upstream-currency rule.** Encodes a lesson learned the hard way during an author-rename rewrite: force-pushing rewritten history without first verifying the local clone is current with origin silently drops any commits that advanced upstream since the last sync.

What changes:

- New `Mass history rewrites — upstream-currency check is load-bearing` subsection in `git-hygiene/SKILL.md` (under `Force-push — safe-conditions procedure`).
- Three concrete patterns: (1) the standing `git fetch origin && git log HEAD..origin/<branch>` check before any force-push that follows a history rewrite; (2) start-from-fresh-mirror-clone as the preferred pattern for `git filter-repo` runs (sidesteps the stale-checkout window); (3) recovery procedure when commits did get dropped — fetch the orphan chain by SHA into `refs/recovered/old-tip`, rebase onto the rewritten base (clean when the rewrite only changed metadata since trees are identical), force-push again after re-applying the upstream-currency check.
- Existing `AI-attribution cleanup` use case cross-references the new subsection.

Why this lives in desk (substrate), not an overlay: every consumer agent that ever rewrites history on a shared branch faces the same trap, regardless of context (corporate engineering, autonomous agent, personal-coding). The rule belongs with the engineering posture skills the substrate provides.

## 1.2.0 — 2026-05-22

**`session-start-migrations` framework.** New skill that auto-heals stale machine state when a plugin's canonical names drift (workspace dir renamed, plugin clone moved, symlink target changed, etc.). Walks every enabled plugin's `migrations/<NN>-<slug>.md` dir at session start, runs each migration's Detect predicate, and (for the ones that fire) runs Safety check + Migrate + Announce, then hard-stops the session for restart.

Why this lives in desk (substrate), not in any overlay: overlays sometimes rename themselves, and a migration framework hosted inside the plugin being renamed has to rename itself mid-execution. Substrate-resident means the framework survives any overlay churn.

Design choices:

- **Self-evidencing predicates, no marker file.** Each migration's Detect block inspects actual machine state (a dir's existence, a symlink's target). Robust against restored backups, partial Time Machine snapshots, and any other path where a marker file desyncs from reality. Cost: every Detect runs on every session start; on a machine with no pending migrations (the common case) this is a few cheap bash exits.
- **Four sections (Detect / Safety check / Migrate / Announce)** map cleanly to one concern each. Detect is a pure predicate. Safety guards against partial state. Migrate does the work, idempotently. Announce is the operator-facing message.
- **Cross-plugin ordering by alphabetical filename.** The `<NN>-<slug>.md` convention plus a 2-digit prefix gives global ordering across every plugin's migrations dir; plugins coordinate by picking the next available `NN` rather than via a central registry.
- **`needs_restart: true` hard-stops the session** after the announcement. The operator restarts; the next session begins against canonical paths.

Integration: `desk:session-start` now hands off to this skill in a new Step 0.5 — after Step 0's host-identity probe, before Step 1's prereq probe. The order matters: most later steps assume `$DESK/` resolves to the canonical workspace path, so migrations run first.

This release ships the framework only; concrete migrations live in consumer overlays.

## 1.1.0 — 2026-05-22

**Archive is now searchable.** Reversed the v1.0 indexer behavior that skipped `_archive/` at index time. Archive content was always meant to be preserved for future recall — making it unsearchable defeated the purpose.

What changed:

- **Indexer**: walks under `_archive/` ancestors. Loose `.md` files there (migrated legacy filenames like `2026-02-23-planning-foo.md`) are also indexed — basename pattern infers kind (`-planning-` → planning, `-doing-` → doing, etc.) or falls back to `kind: archive`. Each indexed doc gets a new `is_archived: bool` flag.
- **Search tools**: all five accept an optional `scope: "active" | "archived" | "all"` parameter. **Per-tool defaults match each tool's purpose:**
  - `desk_search` → `active` (day-to-day signal beats archive noise)
  - `desk_recall` → `all` (this IS the historical lookback tool)
  - `desk_similar` → `all` (similarity has no time/status semantic)
  - `desk_timeline` → `all` (already temporally scoped by window)
  - `desk_thread` → no scope param; always walks across (refs don't respect archive boundaries)
- **DB schema**: new `is_archived` column on `docs` table + index. Migration is idempotent: opening an existing v1.0 DB ALTER-ADDs the column with default 0; next reindex populates correctly.

Operator-visible: `desk_recall("teams bot integration")` now finds archived planning/doing notes from months ago. `desk_search("teams bot")` still defaults to active-only — agents asking "what should I do next" get current work, not archived history. Override per-call with `scope: "all"` when historical breadth matters.

Migration: existing indexes auto-upgrade their schema on next open. To populate archive embeddings, run `ouro desk reindex --force` once per bundle (or `mcp call ... desk_reindex --args '{"force":true}'`).

## Setup (v1.0)

After `ouro plugin install github:ourostack/ouroboros-skills:plugins/desk --agent <name>`:

1. **Install plugin's MCP deps:** `cd ~/.ouro-cli/plugins/desk/mcp && npm install`
2. **Install Ollama** for full semantic surface (recall / similar). Mac one-time: `curl -L https://github.com/ollama/ollama/releases/latest/download/ollama-darwin.tgz | tar -xz` then add the binary to PATH. Linux: `curl -fsSL https://ollama.com/install.sh | sh`.
3. **Pull the embedding model:** `ollama serve &` then `ollama pull nomic-embed-text` (one-time, ~274MB).
4. **Restart daemon** so plugin MCP discovery picks up the new server: `ouro stop && ouro up`.

Without Ollama, desk_search falls back to FTS5-only (keyword) and desk_recall/desk_similar return empty. Substrate works; semantic surface is degraded.

## Known limitations (v1.0)

These do NOT block v1.0 use but are tracked for follow-ups:

- **Plugin install does not run `npm install`.** After `ouro plugin install ...`, the operator (or a v1.1 install hook) needs to `cd ~/.ouro-cli/plugins/desk/mcp && npm install`. Otherwise the server can't spawn (`@modelcontextprotocol/sdk`, `better-sqlite3`, `sqlite-vec`, `gray-matter` missing). v1.1: either auto-run install on plugin install OR vendor deps OR ship as a bundled single-file build.
- **Tool input schemas are loose.** `inputSchema: { type: "object", properties: {}, additionalProperties: true }` — agents have to infer from descriptions. Works but agents occasionally pass wrong field names on first attempt. v1.1: define explicit JSON Schema per tool.
- **`mcp__ouro-<agent>__send_message` response wrapper hangs at 600s** when the agent makes multi-tool sequences via desk MCP, even though the agent finishes successfully (artifacts on disk). This is in the **ouro MCP** comms layer, not desk. Tracked separately.
- **Ollama is a soft dep** for full semantic surface. With Ollama down, `desk_search` falls back to FTS-only (still works), `desk_recall` returns empty + a note, `desk_similar` uses stored embeddings only. For the agent-as-substrate promise, the operator should keep Ollama + `nomic-embed-text` available.
- **Daemon must be restarted** after a fresh `ouro plugin install ...` for the new plugin's MCP server to be discovered. v1.1: signal the daemon to reconcile on plugin-list change.

These are upgradable in place — none change the v1.0 wire format or storage schema.
