# Factory local session capture

Desk records local session facts without waiting for a network service, delivers their published form to a factory store from a detached process at the next session start, and provides the deterministic pipeline a store uses to validate published facts and waste labels and rebuild reports. The store's own workflows live in the store repository, and delivery to the live public store is not yet proven on installed hosts. The [end hook](../hooks/lib/factory-end.cjs), [runner](../mcp/src/factory/derive-run.js), [delivery](../mcp/src/factory/flush.js), [boot checks](../hooks/lib/boot-checks.cjs), [pipeline](../mcp/src/factory/pipeline/) and [synthetic tests](../../../tests/desk/mcp/__tests__/factory/) define this boundary.

## Working on the factory

Before you design, plan, change or review anything here, invoke the `factory-work` skill: it holds the Lean reading and the terrarium checks. One rule from it that this doc follows throughout: a field that was not measured is absent or `null`, never `0`.

## Host events

| Event | Local action | Detached action |
| --- | --- | --- |
| Claude `Stop`, Copilot `agentStop` | Refresh the protected session marker. | Run `factory.js finalize --job <job>` for each pending finalize request, at most eight. |
| Claude `SessionEnd`, Copilot `sessionEnd` | Refresh the marker with the end reason. | Run `factory.js derive --marker <file> --wait-quiet 30000`. |

The [host manifests](../hooks/hooks.json) and [Copilot manifest](../hooks/copilot-hooks.json) register these events. The [handler](../hooks/lib/factory-end.cjs) caps stdin at 1 MiB and stops waiting for input after 150 ms. Its supervisor keeps the unchanged 1.5-second deadline outside the worker that performs synchronous metadata and OS-protection work, terminates a blocked worker and waits for its exit. Both processes print nothing. Ordinary native operation targets 500 ms; the [subprocess tests](../../../tests/desk/mcp/__tests__/factory/end_hook.test.js) allow 2 seconds for CI. The local protection helpers may invoke OS ACL utilities, but neither the hook nor derivation requests a network operation.

Copilot log paths come from `sessionId` under `COPILOT_HOME` (otherwise `~/.copilot`), not from prompt text or `transcriptPath`. Agency plugin-session locations supply the `launcher` entrypoint. Plugin names and versions come from sibling manifests on Copilot and the installed-plugin registry on Claude. Each plugin also records its install source, the GitHub `owner/repo` it came from, or `null` when that is not known for certain. Every lookup fails closed:

- **Claude Code:** the plugin's marketplace must be a GitHub repository in `known_marketplaces.json`, and the marketplace's cached manifest (`<installLocation>/.claude-plugin/marketplace.json`) must list the plugin. The source is then the marketplace's repository for a relative path inside it, or the listing's own GitHub repository. A plugin the manifest does not list, a listing hosted anywhere but GitHub, or a name listed twice with different sources has no source.
- **Copilot under Agency:** the source comes from Agency's cache index. Every index entry counts, including non-GitHub ones. A plugin has a source only when the whole index was read and every cached entry at the plugin's exact name and version came from one GitHub repository. A name never matches on its own. An index with more than 256 entries, an entry whose folder cannot be read, and a scan the source budget cuts short all give no source for any plugin.
- **Plain Copilot:** exactly one `installedPlugins` record in `config.json` must match the plugin's name and version, and its marketplace must be a GitHub repository in `settings.json` `extraKnownMarketplaces`. Copilot keeps no marketplace manifest to check the listing against, so the marketplace's repository stands in for the plugin's.

The Stop hook gives the lookup 400 ms. After that, every source is `null` and the plugins are still recorded. Markers and local facts written before sources were recorded stay valid, and their plugins read as having no known source. The marker captures the resolved route so deleting a temporary plugin folder cannot redirect a later sweep to the default store. Every discovery cap, including Claude's records-per-key and aggregate manifest-directory limits, makes routing incomplete; only the desk's own valid declaration can override that hold. The [marker validator](../mcp/src/factory/marker.js) limits paths and metadata, while the [canonical resolver](../mcp/scripts/resolve-desk-root.js) owns desk selection. Hook-facing activation reads are regular-file-only, no-follow and capped at 64 KiB. An unresolved binding defers capture rather than guessing. `DESK_PERSON`, when set, supplies an explicit `desks/<alias>` binding prefix; no identity is inferred from content.

**A privately routed session never reaches the public store on any path, and every hold is visible.** A route is held (`store: null`, `invalid_declaration`) whenever the hook could not read the whole plugin set: a manifest or plugin folder that is missing, unreadable, linked or too large, a symlinked Copilot plugin folder, a missing or unreadable Claude Code registry, a registry that does not list the running Desk (a `claude --plugin-dir` session, whose overlays the hook cannot see), too many plugins, or a scan the deadline cut short. The unread plugin may be the overlay that declares a private store, and only it can say. Every reader reads the warned manifests again and routes to the store a manifest declares once it reads, unless that store is the public one ([store-route.js](../mcp/src/factory/store-route.js)). A reread never releases a hold to the public store, whether the manifest now declares it or an older Desk recorded it as the default: the file at that path may not be the plugin the session ran with (a Copilot plugin folder carries no version, so another plugin can take its place). Nothing infers the default store for a held session: another session's plugin scan says nothing about the plugins this one ran with (a `claude --plugin-dir` overlay, another config folder, an overlay uninstalled since), so a hold whose cause cleared without a declaration waits until the desk declares its store in `_meta/factory.json` ([held-route.js](../mcp/src/factory/held-route.js)). A registry whose Desk record is another version in the same cache folder as the running Desk (Desk updated mid-session) counts as listing it. A marker an older hook wrote with the default route and no plugins at all is read as held, because a hook that read its plugin set always lists Desk. A held marker is kept for 90 days instead of 30; the sweep counts holds in `status.json` `route_holds`, and `desk_doctor` and session start print each with its path, reason and remedy, and the number of held sessions pruned unsettled (`held_pruned`). Without a current marker, a session goes only to the store this Desk last checked positively for it, which its receipt records as `checked_route`: the flush, the derive and the sweep write it on a positive route, and nothing else does. A receipt an older Desk wrote, or none, freezes the copy on this machine. A copy kept aside while its desk folder was gone comes back once the folder resolves and the session is derived to a checked route here again.

## Local state and commands

All factory state lives at `$XDG_STATE_HOME/ouroboros-skills/desk/factory`, or `~/.local/state/ouroboros-skills/desk/factory`. The [outbox](../mcp/src/factory/outbox.js) applies the shared owner-only protections and refuses Git checkouts, symlinks and hard links. Capture, derivation and finalize callers also exclude the canonical bound desk, including unversioned desks and symlink aliases, before creating state. Direct marker reads, sweep and status use the same owned-directory, leaf-protection, 64 KiB and filename/session identity checks. The read retains the protected directory's identity, compares the opened descriptor with the post-read descriptor and current pathname, and rechecks directory/leaf identity before returning data. Leaf repair follows identity validation; corrupt/expired pruning rechecks the same owned directory and leaf rather than adopting a replacement. Markers are local bookkeeping, not published facts: paths, routing warnings and exact hook times never enter a facts file. Prompt fields, assistant text, task titles and tool arguments are not copied into markers.

Run commands from the installed Desk plugin root:

```sh
node mcp/scripts/factory.js account --store ourostack/factory
node mcp/scripts/factory.js consent --store ourostack/factory --contribute yes --account <login>
node mcp/scripts/factory.js derive --marker <protected-marker-file> --wait-quiet 30000
node mcp/scripts/factory.js status
node mcp/scripts/factory.js flush --store ourostack/factory
node mcp/scripts/factory.js finalize --job <job> [--job <job> ...]
node mcp/scripts/factory.js validate-pr --base <base-sha> --head <head-sha> --author-association <value>
node mcp/scripts/factory.js build --store <store-directory> --out <output-directory>
node mcp/scripts/factory.js job-link --store <owner/repo> --desk-remote <url> [--person-prefix <prefix>] [--desk <desk-root>] --track <track> --slug <slug> [--this-machine]
node mcp/scripts/factory.js evaluate --desk <desk-root> --task [desks/<alias>/]<track>/<slug>
node mcp/scripts/factory.js evaluate-accept --job <job>
node mcp/scripts/factory.js kaizen-check --store <directory> --repo <owner/repo> [--author <login>]
node mcp/scripts/factory.js andon --store <directory> --repo <owner/repo> [--author <login>]
node mcp/scripts/factory.js reconcile --desk <absolute path> --since <time> --until <time> [--store <directory>] [--person-prefix desks/<alias>]
```

The [CLI](../mcp/scripts/factory.js) returns one JSON result. `derive` accepts only a marker in the protected marker directory, waits for source quiet for up to five minutes, and then returns `written`, `held`, `skipped`, `not_opted_in`, `log_missing`, `source_unreadable` or `invalid`, with the selected store when known. `flush` makes one delivery attempt and prints `{ result, pr? }`; `finalize` takes one to eight distinct jobs and prints each job's outcome. A Codex marker records no plugins, so one whose route is the public default is held (`held`, reason `route_unverified`) until a Claude Code or Copilot CLI marker for the same desk, within 30 days, also routed by default; a desk that declares its store in `_meta/factory.json` routes Codex at once. The sweep reports the held Codex count as `route_unverified`, and local `status` shows it as `held_markers.route_unverified`. Local `status` includes marker/finalize counts, derivation receipts, routing warnings, the last flush result per store and skipped boot checks; it is not a public report and must not be uploaded as facts. Its receipts carry the binding fields described under "How a session is credited to a task", and `route` (the store the session last positively routed to) and `desk_root` (the session's absolute desk path), and its last flush entries carry `intake_prs` (each pushed intake PR's number and head, `owner:branch`, which names the delivering account); all three are local only and never published. No command prints the machine secret or a token.

## How a session is credited to a task

A job is one outcome, recorded as one task card. Everything a session tree does while working an outcome belongs to that outcome's job: the main agent, every subagent, and the time spent briefing, waiting on and reading back from them. Mentioning, filing, tidying or updating another card is not working on it. The [binder](../mcp/src/factory/binding.js) and the [focus rules](../mcp/src/factory/focus.js) decide this from the events a deriver reads out of the transcript; those events stay in memory and never reach facts.

### Declaring the task

The session's main agent calls `task_focus` with a task's `track` and `slug` when it starts or switches to an outcome, or with `clear: true` for a side conversation that belongs to no task. `task_create` with `focus: true` creates a card and declares it in one call; without the flag, a created card does not move focus. Both are declarations, and so is a clear. A subagent never calls `task_focus`: its brief carries a `Desk-Task: <track>/<slug>` line instead.

- **The call waits only for admission.** While the Desk server is still admitting, `task_focus` waits up to 2 seconds for it, then answers or refuses. It gains no write authority: it reads the card and writes nothing.
- **A session with no focus is reminded.** Every task tool result carries a short `focus_note` hint, worded for the main agent, until the session sets a focus or clears it on purpose. `task_update` and `task_archive` on a card other than the focused one carry a hint too. Hints never block a call.
- **The factory reads the transcript.** Focus is recorded only as the tool call in the transcript, so a session is credited the same way after a resume.

### What the binder credits

1. **Declared stretches come first.** The main agent's declarations cut the session into stretches. A stretch that names a task belongs to that task, and a stretch that clears belongs to none. A subagent's own `task_focus` call is ignored.
2. **Inference fills only what nothing declares.** Where a stretch has no declaration, including the start of a session before its first declaration, the binder infers the task from evidence inside it: files written under a task's folder, task tool calls that name it, subagent briefs that name it, commits whose `git add` or `git commit` names a path in its folder, and work in a code repository. Repository evidence counts, within one stretch, only for the one card that lists that repository and has evidence of its own in that stretch. A commit that names no path (`git add -A`, `git add .`, `git commit -am`) counts for nothing, and so does another session's commit that lands while this session's `git commit` runs. Window-only and pathless commits bind nothing. Where inference finds nothing before the first declaration, that stretch goes to the first declared task.
3. **An inferred segment has a floor.** Within one inferred stretch, a segment shorter than 1 minute joins the longer inferred segment beside it, and a lone segment stays. A declared stretch is never merged or dropped, whatever its length, and a whole short helper session still binds to its job.
4. **Subagents follow one job.** A subagent belongs to the task on its `Desk-Task:` line when that card exists, else to its parent's job when it is nested, else to the job the main agent held when it spawned it. A background subagent stays with the job it was spawned for, even after the main agent moves on, and a subagent resumed later keeps its job. A subagent's own touches never create a job.
5. **Touching a card binds nothing.** Creating a card, updating another card's status and committing another card bind nothing. The focused job keeps its own status transitions, and a transition on a card that is none of the session's jobs is not recorded; `reconcile` reports that case as `status_unobserved`.
6. **A job's segments are always recorded.** A session that binds any job carries segments, even for a single job, so a cleared or unbound stretch is never counted. A job keeps at most 200 segments, and the time the cap took from the task that held it, dropped or given to another task, is kept in the local receipt.

### Local receipt fields

Each derived session has a receipt in the local `status.json` with these fields. They never reach facts, and an absent value means "not recorded", never `0`.

| Field | Meaning |
| --- | --- |
| `bound_by` | For each job the main agent is in, `focus` when its time came from a declaration and `inferred` when it came from evidence. |
| `own_activity` | The spans of the session's own `git commit` calls in the desk and of its successful task tool calls, in milliseconds from the session's start. `reconcile` uses them to tell a session's commits from another session's. |
| `focus_disagrees` | The declared jobs that hold a stretch where inference finds at least 10 events on another task and none on the declared one. |
| `segments_capped_ms` | The time the segment cap took from the task that held it: dropped, or given to another task. It is `0` when the binder measured that the cap changed nothing. |
| `repo_unresolved` | How many directories outside the desk named no repository because repository evidence was not available: the directory is gone or could not be read (reconcile prints it as `repository_evidence_unavailable`). A directory that exists and is cleanly in no repository is not counted. |
| `checked_route` | The store this Desk last routed the session to on a positive, current route (a desk or overlay declaration, a proven default). Without a current marker, the flush sends the session only to this store; an absent value freezes it. |

The receipt also records `binding_version` (7 for this binder; 6 stopped joining two different cards through a Git rename, made a focus on a merged task follow the merge, and made `segments_capped_ms` count handed-over time; 7 re-derives every session once so its facts carry the stop facts, ask-tool waits and created PRs of published facts `/4`). A session whose receipt records an older version is derived again, and one that records a newer version is left alone. `binding_version` is the re-derive version, so a bump does not always change the binding: 7 changed the facts, not what binding credits. The last version that changed the binding is 6 (`BINDING_RULES_VERSION` in [derive-run.js](../mcp/src/factory/derive-run.js)), and reconcile and capture coverage compare receipts with that one. So a version-6 session whose transcript is gone before it re-derives still reads as bound by the current binder, not as stale. The waste evaluator's stop-facts relabel keys on the receipt value 7.

### Shared sessions

A session is shared between jobs only when their segments really overlap. A job with no segments, as in a file written by an older Desk, holds the whole session and so overlaps every other job. A job's time comes from the session's active intervals inside its segments, never from a segment's wall-clock span. A public desk publishes no segments, so a public desk's session that binds several jobs stays marked shared.

### Sessions whose capture marker was pruned

A marker is pruned after 30 days, which leaves a session with an outbox copy and no marker. Each sweep rebuilds such a Claude Code session from its transcript, but only in a desk that declares its store in `_meta/factory.json`, and only when all of these hold:

1. The session's outbox copy is already in the outbox of the store that desk declares.
2. A desk root is known: the receipt's `desk_root`, or else the transcript's working directory when it is exactly a desk root.
3. That desk's declaration names the same store. A desk that routes by default is never rebuilt this way.
4. No store holds a retraction record or a kept copy of the session.
5. The desk is not a crew desk, so its person prefix is none.

Any other session stays frozen, and nothing about it is guessed. The sweep reports how many sessions it rebuilt, how many it left frozen (by reason) and how many are still pending, so a session left behind is visible.

## Outcomes: delivery and sign-off

A job is delivered when its task reaches `done`, and it is accepted only when the operator says so. The task tools record this on the task card (`signoff`, `flow`, `returns`; see `task-card-format`), and each session's facts carry what the card says about the job, as an `outcomes` list with one entry per job (at most 256). A session that touched more jobs keeps the first 256 by job ID and flags `outcomes` `capped`, so a cut list never reads as the whole one. That flag is published only as `desk.factory.published/3`; the published validator refuses it in a `/1` or `/2` file as `inconsistent`.

Published facts are `desk.factory.published/3` only when they carry something only `/3` allows: that `outcomes` flag, or a commit's `at_ms`. Every other file is still published as `/2`, so an unchanged session republishes the same bytes, and `/1` and `/2` files already in a store stay valid. A commit's `at_ms` is the offset on the session clock at which the session recorded the commit; today only Copilot CLI records it (`session_refs.created_at`, the earliest row naming the commit), and only a time inside the session is kept. It is published under the same rule as a controller PR's `at_ms`: only for a desk known to be private and only in a session whose jobs carry segments. It never runs past `session.duration_ms` (`range`), a file marked `{job_offsets, desk_public}` carries none (`inconsistent`), and a `/1` or `/2` file carrying one is `inconsistent`.

Local facts. An entry holds the job, the card's revision count (`rev`), the outcome `state` (`not_delivered`, `not_recorded`, `delivered_unsigned`, `accepted`, `refused` or `reopened`), `verified` (true, false, or null when there is no answer), the operator's refusal `reason` (or null), the number of `deliveries`, and the times of the delivery, of the sign-off and of the observation, plus `first_validating_at` and `first_delivered_at` when the card has them. The times stay on the machine. `reopened` means the task was delivered and is back in work without a refusal. `not_recorded` means the card was finished before the record existed; it is never read as accepted.

Acceptance. An acceptance recorded through `task_signoff` counts as accepted, recorded by the agent on the operator's word. The factory reads `state` alone: an older entry whose `verified` is true or false and a newer entry with no `verified` count the same way.

Published facts. The same entry is published without any time or name: the job (keyed the same way the published `jobs` are keyed for that desk), `rev`, `state`, `verified`, `reason`, `deliveries` and `wait`. `rev` and `deliveries` are cut to 9999, which reads "9999 or more". `wait` is how long the delivery waited for its answer, as one of four classes (`lt_1h`, `lt_1d`, `lt_7d`, `ge_7d`) with a `censored` flag: a delivery with no answer yet has waited at least that long, so its flag is true. A state with no wait has `wait: null`, never a zero. `returns_truncated` and `returns_unreadable` (a count from 1 to 9999) are published when present. A time is never published, and neither is a track, a slug, a title or a person.

### Returns and rework

A return is any move that sends work back: a refusal, a move out of `done`, or a move below the furthest status the task had reached (`task-lifecycle`, "Returns"). Every return carries a reason the agent gave: `agent_error`, `changed_ask`, `new_information` or `external`. A return the operator caused by refusing also carries the operator's reason, and the entry keeps a `refusal_verified` flag that nothing reads: a recorded refusal counts by its recorded reason. Each entry of the `outcomes` list gains `since` (`created` or `adopted`: a card adopted from before the record has no known start, so it is left out of first-pass yield) and a `returns` list of at most 32 entries, each `{ reason, caught, counts, refusal, refusal_verified }`. `caught` says where the return was found: `in_task` (before the first review), `at_review` or `after_delivery`. `counts` says whether the return counts against first-pass yield: it does not when the deciding reason is `changed_ask`, because a changed ask is not a defect. The deciding reason is the operator's when the refusal recorded one and the agent's otherwise, with no `verified` distinction. When the list is cut, `returns_truncated` is true (published only when true); `returns_unreadable` counts damaged lines, so a damaged card never reads as having no returns. The times of the returns stay on the card and are not in the facts.

Published facts carry `since` and `returns` as the local entry has them, with the same four agent reasons, three catch points, `counts`, and the refusal reason and its verified flag, and no time, name or track.

## Human attention

Facts carry `human_turns`, a list of at most 1,000 entries in time order, so the factory can say how much human attention each accepted outcome cost. An entry is `{ at, basis, window_ms, prompt_class, output_class }` locally and `{ at_ms, basis, window_ms, prompt_class, output_class }` when published, where `at_ms` is the offset on the session clock, the same clock the intervals use. `basis` is `first` (the first human prompt of the session), `after_stop` (the agent had stopped) or `mid_turn` (the agent had not stopped since the previous human prompt). `window_ms` is the gap from the agent's stop to the prompt for `after_stop`, the time since the previous human prompt for `mid_turn`, and `null` for `first`. `prompt_class` and `output_class` are size classes of a character count: `none` is 0, `xs` 1 to 20, `s` 21 to 200, `m` 201 to 1,000, `l` 1,001 to 5,000 and `xl` above 5,000. No prompt text, command, path or reply text is held, only the class. A session over the limit keeps the first 1,000 entries and flags `human_turns` `capped`.

What a human turn is, per host:

- **Claude Code.** A human turn on Claude Code is a root prompt line whose `origin.kind` is `human`. The interrupt marker, a headless prompt, a scheduled task, a subagent's report and any line a hook or a tool result wrote are not human turns. A session where none carries an origin flags `human_turns` `field_absent` and writes no list, so a transcript from a host version that wrote no origin never reads as having no human turns; a mix flags `host_records_partly`. A queued prompt counts as `mid_turn`: the human typed it while the agent worked, so a `mid_turn` window is not human wait time, only the time since the previous prompt. The size of a reply is the text of the root assistant lines since the previous human turn, with no thinking, tool use or subagent lines.
- **Copilot CLI.** A human turn is a root `user.message` with no `source`, not an autopilot continuation. The agent's stop is the last root turn end with no root turn start after it. Nothing proves that a `user.message` with no `source` was always typed by a human, so every Copilot list is flagged `host_records_partly`: the list is kept, and the figure is not proven complete or exact.
- **Codex.** The log does not mark which prompt a human typed. Codex is flagged `host_does_not_record` and writes no list.

A prompt dated before the last kept turn is dropped and flags `source_unreadable`: moving a time would make up a fact, and one skewed line must not void the whole session. So is a prompt dated before the agent stop that comes before it: its wait would read as a measured zero. A human prompt with no readable time, an unreadable line, and a log that ends mid-record flag `source_unreadable` or `log_truncated` too, and the list is then a lower bound.

What cannot be known. No host records how long a person read a reply or how long they typed, and none records whether the person read while the agent was still writing. The estimate is built from the size classes and the gap the host shows, so it is an estimate and never a measurement. A permission decision is not a human turn: only Copilot records its wait, and Claude Code and Codex record none.

The estimator (method version 1) is a pure function of one entry, and it refuses an entry it cannot read:

`estimateTurn(turn) = max(FLOOR_MS, min(turn.window_ms ?? Infinity, READ_MS[turn.output_class] + TYPE_MS[turn.prompt_class]))`

| Constant (ms) | `none` | `xs` | `s` | `m` | `l` | `xl` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `READ_MS` (reading the reply) | 0 | 1,000 | 5,000 | 30,000 | 150,000 | 400,000 |
| `TYPE_MS` (writing the prompt) | 2,000 | 3,000 | 25,000 | 150,000 | 180,000 | 180,000 |

`FLOOR_MS = 1,000`, `PERMISSION_MS = 5,000` and `ATTENTION_METHOD = 1`. Reading is taken at about 50 ms per character of a representative reply for the class (1,250 characters a minute). Typing is taken at about 300 ms per character (40 words a minute) up to class `m`; classes `l` and `xl` are treated as mostly pasted and held at 180 seconds. A permission decision is `max(FLOOR_MS, min(wait, PERMISSION_MS))` and is reported beside the headline, not in it. The store recomputes every figure from the entries, and changing any constant raises the method version, so a figure is only compared with figures of its own method version.

Each turn belongs to the job whose segment holds its `at_ms` (the segment that started last when several do). A turn in no segment is unattributed, and a turn in a session whose jobs publish no segments is unplaced when the session has jobs and unattributed when it has none. Nothing is dropped, and every turn stays in the headline.

The headline, human attention per accepted outcome, is the sum of the estimates over every human turn of every session in the period, divided by the jobs accepted (recorded by the agent on the operator's word), including turns on jobs that were refused, are unsigned or were never delivered. The headline has three states, and the figure always carries its `state` and `reasons`. It is measured when every session in the period kept a complete list. The headline is partial, printed as a lower bound, when some session in the period flags the field (Codex sessions and every Copilot session do), or a session was cut by the limit; a partial figure is a lower bound on the total. It is unavailable when no session in the period kept a list (`no_turn_records` when no session is in the period, `turns_not_recorded` with the host's own reason otherwise), and no total is published then. It is also unavailable, with no total, when every turn is unreadable (`turn_not_estimable`). It is unavailable, with the total still published when a list exists and a turn could be estimated, when no verified acceptance exists (`no_accepted_outcomes`); the total is shown as "at least" when partial, and the headline shows no value and is never zero. A turn the estimator cannot read is counted, adds no time and gives `turn_not_estimable`; when every turn is unreadable the time is left out. Sessions in the old `/1` format carry neither list nor flag, so they are outside the period: coverage pages no longer count them under human turns, and their per-job result still reads `not_recorded`.

## Why the agent stopped, created pull requests and finish days

Published facts `/4` carry three things the factory needs to show a task on its own clock and say why it waited. Each value is derived when the session ends, so none of them needs the transcript later; the waste evaluator, which reads the session log itself, still does.

**Why the agent stopped.** Each `human_wait` interval carries `stop: { end, asks, pending_agents }`. `end` is how the agent's turn ended before the wait: `end_turn`, `max_tokens`, `rate_limit`, `api_error`, `refusal`, `interrupted`, `ask_question`, `ask_plan` or `not_recorded`. `asks` is whether the agent's last reply text ended in a question mark (`null` when the turn had no reply text), and `pending_agents` whether the agent's own background agents were still running (`null` when the host does not say). Only the last character of the reply is looked at, and nothing else of the text is read or kept.

- **Claude Code.** `end` comes from the turn's last root reply: its `stop_reason` (`end_turn` or a stop sequence is `end_turn`; `max_tokens` and `refusal` are themselves; `tool_use`, a thinking line's empty reason or an unknown reason is `not_recorded`), or, when the turn ended on an API error, `rate_limit` for a 429 or a `rate_limit` error and `api_error` otherwise. The wait the interrupt marker ends, and the wait after it while the agent did nothing, are `interrupted`. `pending_agents` comes from the turn's `system/turn_duration` line: `true` when its `pendingBackgroundAgentCount` is above zero, `false` when the line has no count (the host writes the count only when it is above zero: on the operator's transcripts, from 2.1.274 to 2.1.290, it never appears as 0), and `null` when the turn has no such line. A root `AskUserQuestion` or `ExitPlanMode` call that got an answer is also a `human_wait` spanning the call, with `end` `ask_question` or `ask_plan` and both flags `null`; the call stays a tool interval too, and the reports decide how its time counts. A subagent's call is not a wait on the operator.
- **Copilot CLI.** `end` is `interrupted` when the root logged an `abort` after its last turn started. Otherwise, when the root logged a `session.error` or a failed model call after its last turn started and wrote no reply after it, `end` is `rate_limit` for status 429 or an error type of `rate_limit` or `quota` (Copilot logs a used-up quota as status 402), and `api_error` for any other error. Otherwise `end` is `end_turn`. On this machine's logs (2026-10-08), every root error was followed by the session's shutdown, not by a prompt, so no wait carries an error end yet. `asks` comes from the last root `assistant.message`; `pending_agents` is always `null`.
- **Codex.** Codex writes a `human_wait` between turns but no stop facts, so each of its waits publishes `end: "not_recorded"` with both flags `null`.

A session derived before stop facts were recorded publishes each wait with `end: "not_recorded"` and both flags `null`.

**Created pull requests.** `refs.prs[].created` is `true` only when the session's own call created the pull request: a Claude Code `gitOperation.pr` with action `created` (in the root or a subagent's transcript), or a Codex or Copilot CLI `gh pr create` that finished with exit code 0 and printed the pull request (a failed create can still print an existing pull request's URL). A pull request Claude Code knows only from its `pr-link` line is `false`, because that line is also written for pull requests the session only looked at: on the operator's transcripts, read for event codes only on 2026-10-08, 62 of the 131 pull requests a session knew only from a link were first linked more than two minutes after GitHub created them, and 4 were created before the session began. For Copilot CLI, only the first pull request URL in that call's result is read; the rest of the result is not. On the operator's Copilot logs, read the same way on 2026-10-08, all 60 such calls printed a pull request that GitHub had created 0.8 to 8.8 seconds before the result. Every other pull request in Copilot's session store is `false`. A desk that withholds its job timing publishes `false` for every pull request.

**Finish days.** A job whose card was seen `done` or `cancelled` publishes `finished_on`, the UTC day of the session's own last move of the card into that status (`finished_basis: "transition"`), else of the card's `updated` time when the session saw it (`"card_updated"`, an upper bound). It needs a readable card creation time, because the same source must also be published on the task clock. An open job, a job without that time, and every job of a desk that withholds its timing publish `null` for both. A day before 2025-01-01, or after the day the flush runs, is withheld, because the store would refuse it. The day comes from the local file alone, so a session whose transcript is gone still gets one the next time its facts are published.

## Waste labels

When a task reaches `done` or `cancelled`, `task_update` (or `task_archive`) itself records an evaluation request at `evaluate-requests/<job>.json`, the same way and on the same opt-in gate it already records a finalize request — because the session that finished the job is usually not derived until it ends, this is a record only, not a prepared brief. Both terminal statuses request one: a cancelled job is still a finished job (see "Only finished jobs count" below), and the waste in it is exactly what the evaluator needs to see. `evaluate --pending`, which the loop's evaluate step runs (see [The improvement loop](#the-improvement-loop)), prepares every retained request's briefs, and the plugin then runs the evaluator headlessly on a subscription sign-in. An interactive agent that retries a job handles the answer as `desk:session-start` (its `details.md`, "Factory lines") says: when the answer is `ready`, it starts a fresh `desk:observer` subagent in the background with only the brief paths. `evaluate --task <track>/<slug>` remains available to record and prepare one task's request directly, for example a task finished before this wiring existed. A request is cleared once every session of the job has settled labels, or has its labels held back because its facts are quarantined. Labels are settled while the evidence they were made against still stands: accepted labels record a fingerprint of the job's own share of the session, the facts intervals that overlap it and the stop hints (`labels-basis/<store>/<job>/<session>.json`), so a job that finished in a session that runs on for days is labeled at its finish, and again, at most once a UTC day, only while that session's facts are derived again with different evidence for the job (a share that keeps growing under a held focus is relabeled daily until the session ends). Labels whose evidence changed during the run (a session that ended mid-run) are kept but leave the job wanting labels. Labels recorded before the fingerprint was kept follow the old rule (an open session is labeled again, an ended one stands). Labels of an older rubric are labeled again while the session's log is still on disk and its facts were derived with stop facts (derive receipt `binding_version` 7 or later), and stand otherwise. A request is and moved to `evaluate-requests/expired/` after 30 days or to `evaluate-requests/quarantine/` as `not_opted_in` when its stores lose consent. Before each sweep the loop's evaluate step also asks for every finished job that needs labels and has no request, expired request or quarantined request (`requestFinishedJobs`): a job whose latest observed card status is `done` or `cancelled` and that has a labelable session whose labels are missing or no longer settled, by the rule above. A session held back behind quarantined facts is passed over; the job's other sessions still count. This is the backstop for a request the done step never recorded and for one settled while its only sessions were held back behind quarantined facts that were later released; its request records the card's observed time as `finished_at`. It is also how already-labeled finished jobs are relabeled under a new rubric and how labels follow facts derived again: a job whose request expires is never asked for again. The requests it records carry the evaluate step's own start time, so they never make the step due once more. Without factory state or consent, `evaluate` answers `not_opted_in` and creates nothing. The observer labels each session's waste with the [factory-evaluator rubric](../skills/factory-evaluator/SKILL.md) and never sees the working agent's conversation. Neither status waits for it.

- **`evaluate`** computes the task's job ID exactly as the task tools do and, for each of the job's sessions (from the jobs index) that a store with consent holds, writes one brief to `evaluations/<job>/<store-slug>/<host>-<session-id>.brief.json` in the protected state folder. It answers `ready` with the brief paths, `not_opted_in` when no store has consent, or `no_sessions`. A session whose ID is not a version-4 UUID gets no brief, because its labels could never be published. Neither does a session whose facts are quarantined, even facts too broken to read: its labels could only ever travel with those facts, so its labels key is quarantined instead, as `facts_quarantined` with the quarantined facts file's name in the record's `facts` field, and the session counts as settled.
- **The brief** ([evaluator](../mcp/src/factory/evaluate-run.js), `desk.factory.evaluator-brief/2`) holds the job, the session, the plugin version and rubric version the labels must carry, the host's session log path from the session's marker (or `null` when the marker or the file is gone), the session's start as the clock origin, the session on the published clock, one stop hint per human wait (`stops`: the wait's range, its stop facts from the local facts or `null`, and the class a rule gives them or `null` when the evaluator decides), the `unavailable` codes that apply and the output path. Its intervals come from the same code that publishes facts (`publishedClock`), so evidence copied from them matches the store's facts. The brief stays on this machine.
- **`evaluate-accept`** checks each answer against a brief rebuilt from the session's own local facts and marker, never the brief file the evaluator can edit; facts that are gone are refused as `facts_missing`. The checks are: JSON within the facts size cap, the current labels schema (`desk.factory.labels/3`, else `schema_outdated`), the brief's job, session, plugin version and rubric, on the file, every stretch and every stop (`job_mismatch`, `session_mismatch`, `evaluator_mismatch`), every `unavailable` code the brief names and no false `facts_missing` (`inconsistent`), and the store's own evidence, range and stop checks against the brief's intervals with each wait's stop facts from the hints (`evidence_unmatched`, `range`, and `inconsistent` for a stop on a wait a rule decides). Each session comes back `accepted`, `missing`, `rejected` with `{ code, path }` errors (including `too_large` and `unsafe_file` for an answer file that cannot be read), `not_opted_in` or `invalid_brief`. No result echoes anything the evaluator wrote. Accepted labels are rebuilt field by field, written as canonical bytes to `labels/<store-slug>/<job>/<session-id>.json` in the protected state folder, and the brief and answer are removed. A rejected answer never enters the outbox.
- **Delivery.** Local labels are already on the published session clock, as offsets from the session's start, never times of day. `toPublishedLabels` maps them to `labels/<job>/<session-id>.json` in the store and keys the job ID exactly as the facts transform does for a desk that is not known to be private. `pendingLabels` lists labels whose published bytes the store has not received, recorded in `delivered/<store-slug>.json` under `labels/<job>/<session-id>.json`.

## Store-side validation and reports

`validate-pr` judges exactly what merging the head into the base would land. It builds the merge result with `git merge-tree --write-tree` (Git 2.38 or later; an older or unreadable Git fails with `git_too_old`, and a merge-tree failure other than a conflict with `merge_tree_unavailable`, both without a result), lists changes as the base against that tree, and reads bytes through `git show` and `git ls-tree`. It refuses a head whose merge conflicts (`merge_conflict`) and a head that carries merge commits not already on the base (`unexpected_merge`). A `base...head` diff would read only one merge base, while the merge uses all of them, so a crafted head could otherwise pass while its merge changed something else. It never checks out, imports or executes candidate-controlled files. Contributor changes are limited to at most 500 added or modified data files of three kinds: published facts at `facts/<host>-<session-id>.json`, published labels at `labels/<job>/<session-id>.json` and the machine's capture record at `capture/<intake id>.json` (see "Capture coverage"). Each facts file must pass the canonical published-bytes gate, match its filename identity, preserve host/session identity when modified and never reduce `session.duration_ms`. Validation output contains only stable reason codes and safe paths. Any change that is not a published facts or labels file, including any other file under `facts/` or `labels/`, is accepted only for GitHub author associations `OWNER`, `MEMBER` or `COLLABORATOR`, and is marked as maintenance for the store workflow to leave unmerged. Only an author association of `OWNER`, `MEMBER` or `COLLABORATOR` may delete a facts or labels file (a retraction, see below): such a delete at those two path shapes validates with no content to check and is not maintenance, a delete at any other path is maintenance, every other author's delete of a facts or labels file is rejected as `removal` (a delete at any other path is rejected as `path`, or `removal_path` from `validatePr` itself), and a rename is still rejected. A modified facts file's previous bytes are read at the base, and its new bytes in the merge result.

A labels file holds an independent evaluator's waste labels for one job's session, in the exact [labels schema](../mcp/src/factory/label-schema.js), `desk.factory.labels/3` (files in `desk.factory.labels/1` and `/2` stay valid as they are). It carries the job and version-4 session IDs, the evaluator, a list of stretches, a list of stops (`/3` only), and a list of what the evaluator could not read. Nothing in the file is free text:

- **Evaluator.** `plugin_version` is a Desk version such as `3.2.0` or `3.2.0-alpha.58`: three numbers of at most three digits, optionally followed by `-alpha.N`, `-beta.N` or `-rc.N`. `model` uses published facts' own model-ID validator: a token of at most 80 characters with no spaces, with no date, time of day or credential-shaped value. `rubric` is the rubric version as a digit string from `1` to `999`.
- **Stretches.** Each stretch is a `[start_ms, end_ms)` span on the session clock with a `class` of `value`, `support` or `muda`, a `waste` that names one of the eight classic wastes for `muda` and is `null` otherwise, `mura` and `muri` flags, and at least one evidence range. Stretches are listed in start order and never overlap. A `/2` stretch also carries the evaluator's `confidence` in the label (`high`, `medium` or `low`) and the `evaluator_version` that assigned it (never newer than `evaluator.plugin_version`, else `inconsistent`), and may be `class: "unknown"` with `waste: "unknown"`: time the evaluator looked at and could not tell. The rollups keep `unknown` as its own row of the waste Pareto: it counts in the waste and unknown time every row's share is taken of (value and support time are not in it), but not in `muda_time_ms` or any `muda_time` measure, because it is not known to be waste. Each Pareto row lists the `evaluator_versions` of the labels behind it and, when every one of them recorded a confidence, `confidence_ms: { high, medium, low }`, which adds up to the row's `total_ms`; a row a `/1` label speaks to has no `confidence_ms`, so it reads as not recorded and is never counted as high. The evaluator's accept step takes only current answers (`/3`, else `schema_outdated`), with the brief's version on every stretch and stop. An evidence range may cite any interval of the session, not only one inside its own stretch; a defect stretch may rest on an earlier failed tool call, for example.
- **Stops.** A `/3` file lists why the agent stopped before each human wait the evaluator classified (the brief hints only the waits that overlap the job's own share, none when the share is unknown, and Desk keeps no stop on another wait): `{ wait, why, confidence, evaluator_version }`, where `wait` is one `human_wait` interval's `[start_ms, end_ms]` copied exactly and `why` is `decision`, `approval`, `acceptance`, `question`, `stopped_short` or `unknown` ("could not tell"). Stops are listed in wait order (`order`), at most one per wait (`duplicate`), never newer than the file's evaluator (`inconsistent`) and empty with `facts_missing` (`inconsistent`). The waits a rule classifies from their stop facts (`max_tokens`, `rate_limit`, `api_error` and `refusal` as `error_limit`, `interrupted`, `ask_question` as `question`, `ask_plan` as `approval`; `STOP_RULES`) are never the evaluator's: a stop on one is `inconsistent` at its `why`. Stops describe waits, which are idle time, so they never enter class or waste totals; evaluator labels still describe working time only. A `/2` file has no stops and stays valid; rubric 4 replaces rubric 3 by the existing replacement rule.
- **Unavailable.** `unavailable` uses a closed set of codes. `session_log_missing` means the host's session log was gone or unreadable, so the labels rest on the facts alone. `facts_missing` means the job's local facts were missing, so the file carries no stretches.

The gate reads that session's facts file, `facts/<host>-<session-id>.json` for either host, from the tree the merge would leave. It reads the file in the merge result when the merge adds or modifies it, treats it as absent when the pull request removes it, and otherwise reads it at the base tip, so labels whose branch predates their facts pass once the facts reach `main`. Exactly one such file must exist (`facts_missing`, `facts_ambiguous`) and pass the published-facts gate (`facts_invalid`); labels that declare `facts_missing` need no facts file, but one that exists is still checked. The labels must name a job that file binds (`job_unbound`), every stretch and every stop's wait must end within the session (`range`), every evidence range must equal one interval's `start_ms` and `end_ms` exactly (`evidence_unmatched`), every stop's wait must equal one `human_wait` interval exactly (`evidence_unmatched`), and a stop on a wait whose `stop.end` a rule decides is `inconsistent`. Evidence names time ranges rather than list positions, so labels stay valid when a still-running session is re-derived and grows. The job and session inside the file must match its path (`job_mismatch`, `session_mismatch`). Anyone may replace a labels file, but only with labels from an evaluator whose plugin version and rubric are both no lower than the ones it replaces (`evaluator_downgrade`); the previous bytes are read at the base.

A public store receives a plugin's name and version only when the plugin was installed from a public repository; the flush resolves each source's visibility, and the store's own, with the references', and never publishes the source itself. Every other plugin, including one with no known source, and every plugin when the store's visibility is unknown, is counted in `refs.private.plugins`. A store known to be private or internal, an organization's work store, receives every plugin's name. `refs.private.plugins` is optional in the published schema, so files published before it existed stay valid.

Published facts and labels share one refusal for secrets. Model IDs, plugin names and PR and commit repository names are refused as `credential_like` when they start with a token prefix such as `ghp_`, `github_pat_` or `sk-`, or hold a 16-character or longer hex or letter-and-digit run, a password value or an IPv4-looking run. The factory keeps its own copy of Desk's credential rules, and a test holds the two in parity. The rule can also refuse a real name: a repository such as `acme/build2026Q3release` holds a 16-character letter-and-digit run, so a facts file that names it is refused as `credential_like`.

`build` reads regular files directly under `facts/` and `labels/<job>/`, validates them again, sorts every key and collection explicitly, and replaces the output directory with deterministic `README.md`, `index.md`, `jobs/<job>.json`, `jobs/<job>.md` and `rollups/` bytes. It reads no wall clock. A store without `facts/` has zero sessions and publishes an empty index. Dotfiles such as `.gitkeep` are ignored; any other entry that is not a published facts file stops the build with a stable code (`invalid_facts_entry`, `facts_entry_not_regular_file`, `facts_not_directory` or `invalid_published_facts`), and so does any entry under `labels/` that is not a labels file in a job directory (`invalid_labels_entry`, `labels_not_directory`) or that fails the labels gate or names another job or session than its path (`invalid_published_labels`). This matches the facts policy: `validate-pr` gates what merges, so such a file means the store was changed around the gate, and a future labels schema version needs a matching build before labels in it can merge. A labels file that passes but no longer matches its session's facts, for example because the facts were re-derived, is not used and is counted in the rollups' coverage by reason (`evidence_unmatched`, `range`, `job_unbound`, `no_facts`, `facts_ambiguous`, or `facts_missing` when the labels declare it). Sessions with a job offset are placed on the job clock; sessions without one still count toward coverage and signals but do not enter the timeline. The classed formulas cover lead time, queue, active and busy time, parallelism, concurrent sessions and agents within a job, wait unions, flow efficiency, rework signals and unavailable first-pass yield.

Missing data is never a measured zero. A wait total, the active-time family or the API-retry signal is `unavailable` with the declared reason when every contributing session lacks its field (`human_waits`, `permission_waits`, `api_retries` or `turns`), and is marked `partial` with the count of uncovered sessions when only some do. A `tool_durations` gap, such as an open session's unfinished tool call, means only some tool intervals are missing, so it makes the active-time family partial and never unavailable. Flow efficiency and the "What mattered" shares use activity and waits clipped to the job clock's `[0, lead]` window, so no share exceeds lead time; work before the task card is reported separately as active before card. Busy time is the plain sum of turn, tool and subagent intervals, so a tool call inside its own turn counts twice and parallelism measures overlapping recorded work, not concurrent agents. Status follows the latest transition once any terminal one exists, and a transition without an offset never supplies a lead time. A job whose latest transition reopens it after `done` is open again: its lead time and flow efficiency are censored at the latest session end like any open job's, and the earlier `done` stays in its transition history. Once such a job closes again, its lead time ends at the `done` that begins its final terminal stretch, the first `done` after the last reopen; a job closed only once is unaffected.

The [rollups](../mcp/src/factory/pipeline/rollups.js) answer which waste costs the most across jobs, with no who and no when. Jobs are grouped by plugin version, host, job class and waste type, never by contributor. A job's plugin version is the Desk version all its sessions report (`unknown` when any session reports none, including a session whose Desk install source was not known to be public, `mixed` when they disagree), and its host is the one host of all its sessions (else `mixed`). Published facts carry neither the task card's `kind` nor milestone 4's organization signal, so every job's class is `other` and `search_waste` is unavailable with reason `not_in_published_facts`; `coverage.json` records both.

- `rollups/muda.json` is a Pareto of muda time by waste type, largest first with ties broken by waste name, overall, per job class and per plugin version, with each waste's share, cumulative share and job count. Muda time comes from labels: a finished job counts only when every one of its sessions has usable labels for it, and a waste the evaluator did not find is then a measured zero. Each session's labeled waste counts once in any one total, even when the session is bound to several jobs (the labels of the first such job by job ID are used); each Pareto reports the labeled sessions it summed and how many of them several jobs share. A job with some sessions labeled is excluded as `partial`, and one with none as `not_labeled`. A group without a fully labeled job has no Pareto, and a Pareto with no muda has no shares.
- `rollups/measures.json` gives the measure catalog's median, 75th percentile and counted jobs overall and per plugin version, host and job class: `lead_time`, `queue_before_start`, `active_time`, `flow_efficiency`, `human_wait`, `permission_wait`, `api_retry_wait`, `tool_failures`, `tool_retries`, `api_retries`, `compactions`, `retouches`, `muda_time`, `muda_time.<waste>` and `search_waste`. It lists andon's quality measures: `tool_failures`, `tool_retries`, `api_retries`, `retouches` and `muda_time.defects`.
- `rollups/tool-kinds.json` sums calls and failures per tool kind over every session with facts, each session once, most failures first.
- `rollups/coverage.json` counts unattributed sessions and their session time, and labels files used and unused by reason.
- `rollups/index.md` renders all four.

Only finished jobs count. A job is finished when its status is `done` or `cancelled` and its lead time is not censored; every measure of any other job, including a job reopened after `done`, is excluded as `open_job`, because its totals so far are right-censored and the newest plugin version always has the most open jobs. Each group reports its open jobs. Only complete values count. A finished job's value is excluded when the formulas mark it unavailable or `partial`, and each measure lists its exclusions by reason; a measure no job supplies has no median, never a zero. Medians and p75 use the nearest-rank method: sort the counted values ascending and take the value at 1-based rank `ceil(p × n)`, so the result is always a measured value. Output is byte-stable: JSON keys are sorted and every list has an explicit order.

### The kaizen check

In a job that can write issues but not code, the store's build runs `factory.js kaizen-check --store . --repo <owner/repo>` with the workflow token in `GH_TOKEN` ([kaizen.js](../mcp/src/factory/pipeline/kaizen.js)). A kaizen card is an open issue labeled `kaizen` whose body holds one fenced `yaml` block with `kaizen: 1`, a `signal` from the measure catalog, a `job_class` (`any`, or a class the store fills), optional `evidence_jobs`, an optional `countermeasure` pull request URL, the `plugin`, the `version` that first carries the countermeasure (empty until it ships) and a `hypothesis` naming a measure and a direction (`down` or `up`). For each card with a version, the check takes the finished jobs of that class whose every session ran the plugin at that version or later (after) and those whose every session ran an earlier version (before); jobs whose sessions straddle the version are left out as `mixed_versions`, jobs without the plugin as `plugin_not_reported`, and any job's excluded measure under its own reason. Versions order by semantic-version precedence, as Desk's release checks do.

The [comparison](../mcp/src/factory/pipeline/compare.js) treats jobs that share a session as one independent group, because the per-job measures count that session's events in each of them; it reports each side's jobs, groups and median (nearest rank), the change in median (after minus before) and its 95% cluster-bootstrap interval from 10,000 resamples of the groups, seeded with the card's number so every build reproduces it. A side enters the comparison only when a distribution-free 95% interval for its median can exist: with n independent groups the chance that all of them fall on one side of the true median is 2 × 0.5^n, which must be at most 5%, so each side needs at least 6 groups. The code derives that minimum from the confidence level rather than storing it. Below it there is no interval and no verdict, whatever the values. The card gets `confirmed` when the whole interval lies in the hypothesis's direction and `not-confirmed` when it lies wholly in the other. Otherwise it carries neither, and the comment says which of two things holds: "not enough independent jobs yet" (no interval) or "no clear change so far" (the interval touches or spans zero). Published facts do not carry a job class yet, so every job is `other`; a card that names any class other than `any` or `other` gets the error `job_class_not_published` rather than waiting forever. A card without a version gets a comment saying so, and a card that does not parse gets one comment listing stable error codes with the field or block line. The check keeps exactly one comment of its own per card, edits it only when the numbers change, and never closes a card. A card whose issue calls fail is reported with a stable code and the rest are still checked; the command then exits 1. It echoes nothing from the card but validated values, and its comments carry no date or time.

Cards come from the desks. `friction_add` with `about: "system"` records friction about the shared system on the desk as a kaizen candidate and sends nothing. The loop's mirror step files the store issue for each improvement card that names a measure, and `file_card: true` files it at once ([kaizen-file.js](../mcp/src/factory/kaizen-file.js)). The desk write is prepared first. The card goes to the store the desk's facts go to: the desk's own `_meta/factory.json`, else the routing the session hooks recorded from the overlays' declarations; with neither, nothing is filed (`route_unknown`). It is filed with that store's recorded consent, as its recorded account. Unless GitHub reports the store as private, the card carries only structured fields: a generated title and body naming the plugin (only `crew`, `desk`, `plain-language` or `superpowers`; any other is refused as `plugin_not_public`), the friction class and the measure, and a generated card block (`signal` and a `down` hypothesis, or `up` for `flow_efficiency`, when the signal is known; `job_class: any`; the plugin; no version yet). Evidence jobs must have the job-ID shape, and a public store refuses this machine's plain local job IDs (`evidence_jobs_local`). A private store's card also carries the free-text title and body, which are refused if they hold anything credential-shaped, a home or drive path, or an email address. Each card carries a fingerprint (a keyed hash of the plugin, class and normalized title): a retry that finds the open card returns it as `duplicate` and files nothing, and at most five cards go to one store from one machine in any 24 hours (`held_cap`). The desk keeps a one-line record with the card's URL. The issue's author (the recorded account) and creation time are GitHub metadata; a card filed during a curator pass dates that pass, not the friction, but it is still a more precise time than a batched facts flush. The kaizen worker then ships each card's countermeasure, fills in `version` when the release lands, and closes confirmed cards. It never sets `countermeasure` or `version` on a card that still has no `signal` or `hypothesis`: the free text that would let a later pass complete such a draft stays on the filing desk, so a card that ships a fix before it names what the fix moves can become impossible for anyone else to judge or complete. A card already in that state is not lost by default: if the desk's own friction record can reconstruct what it was filed for, the worker completes `signal` and `hypothesis` from it and the check judges the card as usual; otherwise the card stays open with a comment saying why it can't be judged yet, until its `before` side runs out under the next rule. It also does not wait forever on a card whose `before` side, given how the fleet updates, will not gain another job — once every session in the store already runs the plugin at or after the card's `version`, that side stays at `0` jobs, `0` groups build after build — closing that card instead on its merged, verified countermeasure (merged, with tests, on green CI), with the closing comment saying plainly that no statistical verdict is coming. Andon is the backstop this leaves in place: it keeps watching every release of every tracked plugin for a release-over-release quality regression on its own schedule, independent of any kaizen card's state.

### Andon

Then the build runs `factory.js andon --store . --repo <owner/repo>` ([andon.js](../mcp/src/factory/pipeline/andon.js)). Andon watches only the plugins listed under `andon.plugins` in the store's `factory.json`, a maintenance path that intake pull requests cannot change; a store without the file raises nothing. For each tracked plugin, quality measure (`tool_failures`, `tool_retries`, `api_retries`, `retouches` and `muda_time.defects`) and job class, it uses only finished jobs whose every session ran exactly one version of the plugin, and treats a version as comparable when its jobs form at least 6 independent groups, the same minimum as the kaizen check. It compares the latest comparable version with the comparable version before it, so a version superseded before it gathered enough jobs is skipped rather than blocking the comparison. When the 95% interval for the change in median lies wholly above zero (worse), it opens an issue labeled `andon` titled `Andon: <plugin> <version> <measure> <job class>`, or updates or reopens the one it opened before, so there is never a second issue for the same alarm. The body gives the numbers, lists every compared job as evidence, and names every other plugin whose versions changed between the two sets of jobs; the regression then belongs to that set of versions, not necessarily to one plugin. The build closes its own andon issue, with a comment, when the alarm's version or a later comparable version is no longer clearly worse than the baseline; with too few groups to compare, it neither opens nor closes. A reviewer who judges an alarm not to be a real regression labels it `andon-dismissed`: the build never reopens or closes that issue, but when its numbers change it updates the body and adds a comment with them. It reads and changes only issues `github-actions[bot]` opened. Andon watches quality measures only, so no flow gain can offset a quality regression.

The desks see open alarms at session start. After each consented store's flush, the start-time delivery reads that store's `factory.json` and its open `andon` issues with the recorded account, and keeps those the build opened (`github-actions[bot]`) for a tracked plugin and no one labeled `andon-dismissed` ([andon-watch.js](../mcp/src/factory/andon-watch.js)). It records at most 20 of them in the protected `status.json` under `andon`. A store whose `factory.json` is missing (404) is `config_missing`, never "tracks nothing", so its open andon issues never read as clear; only a present, valid config may track no plugins. A failed refresh records its code as `failure` and `failed_at` beside the last good list. The next session start prints one `Factory:` line per store that has any ([boot-check.js](../mcp/src/factory/boot-check.js) `andonBootCheck`), so a line shows what the previous refresh found, and `Factory: andon state unknown for <store> since <date> (<code>)` for each contributing store with no record (`not_refreshed`), an unreadable `status.json` (`status_unreadable`), a record more than 72 hours old (`stale`) or more than five minutes in the future (`future_dated`), or a refresh that failed after the last success (its code) (`andonUnknown`). The loop's route step also keeps an andon card's condition present while its issue is still open but no longer tracked by a shrunken plugin list. The `curator` pass handles andon issues before any other card.

Each job Markdown report has exactly four second-level sections: `What happened`, `What mattered`, `What was waste` and `What we could not see`. Every Markdown value shows its evidence class. `What was waste` renders the independent evaluator's labels for the job's sessions that the build accepted against their facts: how many sessions are labeled, muda time by waste, value and support time, mura and muri flags, and what the evaluator could not read. It says "Not classified yet" only when no session of the job has accepted labels, and it always keeps the inferred candidate and wait signals. The job report names public pull requests and counts private references. The index reports sessions seen as unavailable, because the store only receives sessions that published facts, and includes bound and unattributed session counts, host counts, every unavailable field/reason rate and plugin-version session counts. Generated files contain no calendar dates, times of day, task names, local paths or transcript text. `job-link` reuses the binding module's accepted job-ID calculation and points to the job Markdown on the store's `reports` ref.

The [runner](../mcp/src/factory/derive-run.js) combines the existing native derivers, job binder, store resolver and consent-aware outbox. Per-session locks prevent concurrent derivations from overwriting one another. Receipts retain source identity, size, modification time and the effective marker hash. [Lifetime reconciliation](../mcp/src/factory/session-lifetime.js) checks native resumes and later root activity before treating a marker as ended; unclassifiable or over-limit lifecycle records cannot certify closure. Sweep and file-based requests use only the protected marker reread under the derivation lock; an enumerated copy cannot override that read on timestamp grounds, and a missing file cannot fall back to the copy. Quietness and source identity are checked under the lock. `sweep(env, { quietMs: 600000 })` derives quiet changed logs and currently ended sessions, not busy resumed sessions with stale end markers. A requested `derive --wait-quiet` also rechecks quietness under the lock, including late shutdown writes. Markers remain available for retry and later resumes. The jobs index mirrors the outbox: each derive replaces the jobs listed for its file, so a re-derive that drops a job removes it from the index, and an index written before that rule is rebuilt once from the outbox files (a stamp, `jobs-index.rebuilt`, records it; a failed rebuild is retried on the next sweep and never stops a sweep). The sweep then rebuilds sessions whose marker was pruned when it is safe to (see "Sessions whose capture marker was pruned" above) and records counts of what it rebuilt, left frozen and left pending. Each session start runs `sweep` before delivery, described next.

## Delivery: flush, finalize and the boot check

[`flush(env, { store, runner, deadlineMs })`](../mcp/src/factory/flush.js) is the only code that sends anything to a store, and it never sends local facts. It takes `flush.lock` in the protected state folder (a lock older than ten minutes is abandoned; a live one returns `locked`), reads the store's consent and account, releases the quarantine an older Desk wrote when a store refused its facts as `private_plugins_missing` (its facts named every plugin; this Desk always writes `refs.private.plugins`), together with the labels quarantined with those facts or held back behind them as `facts_quarantined`, and transforms every outbox file that is not quarantined, and every quarantined facts file whose record names no blob or a blob different from the one it publishes now, with `toPublished` and the public gate `validatePublishedBytes`. A quarantined file whose published bytes equal the refused blob stays quarantined and costs nothing: its record is left as written, and a repository whose visibility is already known is not looked up again. A quarantined file whose repositories cannot be resolved stays quarantined without stopping the files that can go, while a deadline, an offline network, a rate limit or a failed sign-in still ends the flush. The files that go again are released together, once, before sending; a record that is not a regular file (a symlink, a directory or a hard-linked file) is left where it is and its file is never sent, and it never blocks another file. Each referenced repository's visibility, each plugin's install source and the store's own visibility, and the visibility of the desk's own GitHub remote, come from the seven-day cache or `GET /repos/{owner}/{repo}` with the account's token: `private: false` is public, `private: true` private, and 403 or 404 unknown. A 403 or a 404 is retried once, with a plain, unauthenticated HTTP request, before it is accepted: a fine-grained token scoped away from a repository, or an organization's SSO enforcement, still answers 403 or 404 for a repository that is genuinely public, and the retry tells that case apart from one that is truly private or gone. The retry never goes through `gh`: unsetting its token environment variables still leaves it free to fall back to its own stored login, which would answer for whichever account happens to be signed in there instead of for no one. Only the confirmed answer — public, private or still unknown — reaches the cache; a network failure, a 5xx or a rate limit, on either try, is never cached as unknown, and stops the flush instead. Because answers are cached for seven days, a plugin repository that turns private, or a store that turns public, can keep its old answer for up to a week. A desk that is not known to be private publishes machine-keyed job IDs without timing, keyed by the protected 32-byte machine secret. A file the transform refuses (`implausible_session_span`, `session_id_not_v4`, `invalid`) or the gate rejects (its first error code) is quarantined and not sent; the record keeps the `blob` the store refused, when a rejection supplies one. When nothing changed since the last delivery, the flush ends there without a network call.

Otherwise it reads the store. With push permission the machine's intake branch `intake/<intake_id>` lives in the store; without it, in the account's default-branch-only fork, created on first use and updated with `merge-upstream` (a fork that is not ready yet returns `fork_pending`). An account without push permission that cannot fork the store returns `account_cannot_deliver` instead of waiting on a fork that will never exist: the store disallows forking, or the account is an Enterprise Managed User (its login holds `_`), which cannot fork or open pull requests outside its enterprise. Closed intake PRs are read newest first, page by page, down to the last PR already read, which is remembered by number in status and moved only after every page has been read. When the store automation (`github-actions[bot]`) commented a first line `factory-rejected: <code>` on one, followed by one such line per further code, every file of that PR, all pages of up to 500, is quarantined with its first data code. When every code is `merge_conflict`, `unexpected_merge` or a `*_check_unavailable` code (the store's own check failing to run, such as `intake_check_unavailable` or `corrections_check_unavailable`), the intake branch was stale, not the facts bad: nothing is quarantined, the files go out again on a branch rebuilt from the store's current default branch, and the flush reports `intake_stale_retried` with `stale_retries`, the number of stale-refused PRs it read, instead of `delivered_pr_open`. `validator_unavailable` never closes a PR. A rejected file with no local outbox file behind it (a session already delivered or gone) writes no quarantine record; the flush result counts those files as `rejections_unmatched`. The comment names no file, so a rejected PR quarantines its good files too, each with the blob the PR carried; the next flush sends a quarantined file again only when its published blob differs from that one, so identical content is never sent a second time. Labels quarantined on their own are not retried. Accepted waste labels travel the same way: each local labels file becomes its published form through `toPublishedLabels`, with the job keyed exactly as its session's facts are, and the labels gate `validateLabelsBytes`; one either refuses (`invalid`, or the gate's first code such as `too_large`) is quarantined at `quarantine/<store-slug>/labels/<job>/<session-id>.json` and never sent. A rejected intake PR quarantines its labels files with its facts, and a stale one sends them again, under the rules above. Labels go only with their session's facts, already on the default branch or in the same batch, because the store's gate refuses labels without facts and that refusal would quarantine every file of the PR; labels whose facts are not there yet wait for a later flush. Labels whose facts are quarantined, by this flush, by a rejection it reads or by an earlier flush, would wait forever, so they are quarantined too, as `facts_quarantined` naming those facts. Files whose exact published blob already sits at `facts/<name>`, or at `labels/<job>/<session-id>.json` for labels, on the store's default branch are marked delivered. Before anything is published or deleted, the flush places every session it could act on by where it routes now, with the one route helper ([session-route.js](../mcp/src/factory/session-route.js)) that the local status and reconcile also use, resolved the way the sweep resolves it. A positive route to this store makes the session here, and a positive route to another store makes it away. A positive route comes from a marker under 30 days old (its desk's declaration, or the overlay check its hook recorded for a default route), or, when the marker is missing or pruned, has no desk root or its desk folder is gone, from the desk root the session's derivation receipt recorded, when that desk declares its store in `_meta/factory.json`. A desk root, the marker's or the receipt's, that is an existing folder whose `_meta/factory.json` is present but unreadable or invalid makes the session unknown, and so does a marker whose hook recorded a route that names no store (an invalid overlay, or an incomplete plugin scan): the desk owner has said the route is changing, but it cannot be read where to. A desk folder that was recorded (the marker's or the receipt's) and no longer resolves, because it was moved or renamed, says nothing about where the desk routes now, so the session is not here: it is frozen and its copies are kept, until a positive route returns. Anything else says nothing new and keeps the session's last known route: a missing or pruned marker whose receipt's desk root declares nothing, a marker with no desk root, a marker from an older hook that recorded no overlay check for a default route, and a Codex default route that no Claude Code or Copilot CLI marker for the same desk within 30 days proves now (a Codex session held at derive time never reached an outbox, so one that did was proven then). The sweep, the flush and reconcile read a marker's route, and prove a Codex default route, with the same functions. The last known route is the `route` the session's derivation receipt recorded when the flush last saw it route positively, else the receipt's `store` (the sweep's latest derive), else this store, whose outbox holds the file. Placement alone is not enough: a re-derive after a route change leaves the old copy in the old store's outbox, and a route to a store without consent is never re-derived, so the flush records `route`, and the session's absolute `desk_root`, in the receipt itself; the sweep records `desk_root` too. Both stay in the local `status.json` and are never published. A last known route to this store makes the session here, so a session pending for more than 30 days, or labels evaluated long after their session, publish as before; one to another store makes it stale, never published there and never deleted. The session's own retraction records come before anything but a positive route: a retraction still open makes it stalled, and a finished retraction's tombstone makes it away, even when the declaration is invalid. Retraction follows three rules. First, a session is published to this store only while it is here. This holds for every file, including a session with no delivered record and a quarantined file that would otherwise be released. A session that is unknown, stale or stalled, or whose facts are quarantined (held), is frozen: it is never published, nothing of it is deleted, and its records stay as they are. The flush counts these in the store's `last_flush` status entry, as `route_unknown` (unknown sessions, frozen until their declaration is fixed), `retraction_stalled` (sessions whose retraction is open but whose route can no longer be shown positive: the record is kept and the delete stays out of the branch) and `held_elsewhere` (files of held away sessions still in the store), and frozen sessions never make a flush go online. Second, a flush that goes online builds the intake branch from what the current state wants, every time: the files to publish and the deletes still needed. When that set is empty, it closes this machine's open intake PR, found by its own head exactly as `openPr` finds it, and resets the branch to the default branch, so a delete the state no longer wants never merges. The status entry keeps `intake_pushed: true`, and `intake_prs`, the number and head (`owner:branch`) of each PR pushed, from the moment a batch is pushed until an online flush finds nothing to change and no PR left open; while it is set the flush goes online even with nothing else to do. A PR pushed under an earlier head (the account gained or lost push permission, so the route moved between the store and its fork, or the consent record names another account) is invisible under the current head, so every online flush closes it by its recorded number, whatever it pushes; its branch is left as it is, because it may sit in a fork this machine no longer uses, and a closed PR merges nothing. One that cannot be read or closed stays recorded, and keeps the flush going online until it is closed. A `store_missing` answer clears both, since no PR can be open on a store that is not there. This survives the loss of any retracting record, and an idle flush with no pending file, no retraction in progress and nothing pushed still ends with `nothing_pending` and no network call, except once after `status.json` lost the store's entry on a machine that delivered to, retracted from or was refused by the store before: that flush goes online to find an intake PR the lost entry would have named by its current head (one under an earlier head stays unknown). Third, retraction never deletes local files. Once the delete is pushed they leave the outbox, because an older Desk's flush publishes whatever `outbox/<store-slug>/` lists and cannot tell a retracted session from a pending one: the session's facts move to `retracted-copies/<store-slug>/<host>-<session-id>.json` and its labels to `retracted-copies/<store-slug>/labels/<job>/<session-id>.json`, in the same protected state folder, with the same owner-only, no-symlink and no-hard-link checks as the outbox. A copy is written to its new place before it leaves the old one and is never deleted; if a different file is already there, both stay. Every flush also moves any outbox copy of a session that has a retracting record or a tombstone, so copies an older Desk left behind, and files already placed in that folder by hand, are adopted and made owner-only. The same move happens before any delete for every session that is not here: at every flush, the copies of each session that is away, stale, stalled or unknown, held or not, delivered or not, leave the outbox for `retracted-copies/<store-slug>/`, and every sweep, after its orphan pass, routes every session with a copy in any store's outbox the way the flush does (its marker, else the desk folder its receipt recorded, else, with no marker and no receipt, the desk its Claude Code transcript names, as the orphan pass reads it) and moves its copies out of every store it does not route to, including a store whose consent is off and whose own flush never runs. A session with no route at all (an invalid declaration, or no desk folder that still resolves) belongs nowhere and is kept in every store. A kept copy whose transcript is unchanged is not derived again. So "away" is durable outside `status.json`: a kept copy goes back to the outbox, and publishes, only on a positive route here, and without one it is frozen (never published, never deleted) however its `status.json`, marker, tombstone or retracting file was lost, corrupted or restored from an older copy. A held session (a facts quarantine; a labels-only quarantine holds nothing) with no positive route and no derivation receipt is frozen the same way, and a refusal an older Desk recorded as `private_plugins_missing` is lifted only for a session that is here. An away session's facts file and every labels file this machine delivered for it are deleted, in the same intake PR, at the published paths their delivered record kept (an older Desk's record without a path is trusted only when republishing now gives the same blob). The delete is made only when the store's default branch holds exactly the blob this machine delivered at that path, and store names compare without regard to case. Once the delete is pushed, the session is retracting: its `{path, blob}` list moves to `retracting/<store-slug>.json`, in the protected state folder beside `delivered/`, written before the delivered records are dropped. Every online flush checks a retracting file against the default branch. Still there with the same blob, the delete stays in the branch; gone, or holding anything else, the retraction is over and the record becomes a tombstone, `{path, blob, done: true}`, in the same file. A delivered record of an away session whose file the default branch no longer holds ends the same way, without a delete. The tombstone keeps the session away from this store for good, whatever else is lost, including `status.json` and the marker; only a positive route back clears it. The local status and reconcile read the kept copies from `retracted-copies/` for `route_changed` and `stale_copy`, and the folder name is owned by [session-route.js](../mcp/src/factory/session-route.js) with the rest of the route decisions. A tree listing that GitHub reports as truncated never counts as a file being gone: the record stays until a full listing shows it. Because the local files are kept, a session that positively routes back finds no delivered record, has its kept copies moved back to the outbox and the labels folder first (a file already there, such as the sweep's newer derive, wins, and the kept copy is retired beside itself as `<name>.kept-<n>`, never deleted, so the session no longer reads as one that left), and is published as new, which restores the store's copy whether or not the delete had merged; its retracting record or tombstone is dropped once the branch no longer carries its delete. When a flush is online anyway, it also deletes a file of an away session it has no record of (the record was lost) if the default branch holds exactly the blob this Desk would publish for it, which only this machine's file can be. The store accepts a retraction only from a maintainer (`OWNER`, `MEMBER` or `COLLABORATOR`), so a contributor without that association cannot retract. A delete the store refuses returns the session to delivered and is counted as `retractions_refused` in the status entry. The refused name is kept there and not retried while the session's file stays delivered and its route stays elsewhere; any change of route clears it, nothing is quarantined, and the session publishes normally if it routes back. A refusal whose state change a crash interrupted is finished by the next flush. The PR body adds `Retracted: <n> files (route_changed)`, counts only, never the other store or a session. A session is never both published and deleted in one PR, and a flush with only deletions still opens the PR. What is retracted, then, is every file this machine delivered to the store for a session that positively routes elsewhere now, or whose desk root, recorded in its receipt, declares another store. What is not: a session whose marker is pruned and whose receipt predates `desk_root` (sweeps before this change did not record it, so such a session is retracted only after a re-derive or a flush that sees its marker), a session whose desk root no longer exists or reaches another store only by the default route with no fresh marker, a session whose desk declaration is invalid (frozen until it is fixed), and a session whose facts are quarantined. Three limits remain. A retraction whose route can no longer be shown positive is stalled, counted and never finished until a positive route returns. An intake PR under an earlier head that this account cannot close (an account change to one without the rights to close the old account's PR) can still merge, and is counted as long as it stays recorded. And if `status.json` and `retracting/<store-slug>.json` are both lost while a delete PR is open, and the session's route also becomes unknown, nothing makes the next flush go online, so that PR can still merge. The rest, at most 500 files and 24 MiB per flush with facts first, become one tree and one commit titled `Factory intake`; only the intake branch is force-updated, to exactly that commit, and left alone when it already holds the same tree on the same base. The open PR for that head is reused, or one is opened titled `Factory intake` whose body is the file count. Store trees, PR lists and comments are read as data and never executed.

Several Desk versions can run at once against one state folder, each with the version it loaded at start, so this Desk leaves a file it cannot fully read to the Desk that wrote it. A local facts or labels file that parses but fails local validation only with `unknown_key` errors, or that declares a newer schema version (`desk.factory.local/2`), is skipped: never published, never quarantined and left in place. A session whose derivation receipt records a newer `binding_version` than this code's is skipped the same way. The flush counts these in the store's `last_flush` status entry as `newer_format`. Any other validation failure keeps its behaviour: a file that does not parse or fails with another code is quarantined as `invalid`. A labels file is also a newer Desk's when it fails this Desk's local schema and its `evaluator.plugin_version` is newer than the Desk running (a file that passes the local schema but fails only the published gate is not covered by this rule). A Desk older than the labels newer-format guard (up to about alpha.173) does the opposite, because it quarantines such files as `invalid`. Every quarantine record now names the Desk that wrote it (`desk_version`). Each flush, before it looks for anything to send, judges again a labels record with no blob whose `reason` is one of this Desk's own check codes (`LABEL_CHECK_CODES` in `label-schema.js`: `invalid` and the schema codes): when the session is routed to this store (the same placement the flush uses to publish, so a session routed elsewhere, held or not shown positive keeps its record) and the local file now passes the full publishing check, the record is removed and the file goes out. A record the flush wrote for a store's refusal carries `source: "store"` and is never released this way; a store record written before that mark and without a blob can still be released, which costs one more send and one more refusal. Any other reason (a store's refusal, a hold behind quarantined facts, `too_large`, which a store also gives) is never released this way, with or without a blob. A valid `desk_version` at or above this Desk's keeps the record; a missing or malformed one does not stop the re-check, because the 14 records written before Desks named themselves cannot be told from an older Desk's decision and the check is the same gate that would publish the file. A file that still fails keeps its record.

Every outcome is one stable code: `delivered_pr_open`, `intake_stale_retried`, `nothing_pending`, `not_opted_in`, `no_account`, `gh_missing`, `gh_too_old` (older than 2.40.0), `auth_failed`, `store_missing`, `account_cannot_deliver`, `fork_pending`, `rate_limited`, `offline`, `locked`, `deadline` or `unexpected`, recorded as `last_flush` in `status.json`. A flush that ends before it reaches the account (`nothing_pending`, `not_opted_in`, `gh_too_old`, `rate_limited`, `offline`, `locked`, `deadline`, `unexpected`) keeps the store's standing account fault (`no_account`, `auth_failed`, `gh_missing`, `account_cannot_deliver`) as `account_fault` in the same entry, and the loop's route step reads it as still present, so only a flush that used the account clears it ([flush-health.js](../mcp/src/factory/flush-health.js)). The token comes from `gh auth token --user <account>`, lives only in memory and reaches `gh api` only as `GH_TOKEN`, with `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1` and `GIT_TERMINAL_PROMPT=0` and every ambient token removed. It never appears in an argument, a result, status, an error or a file. `deadlineMs` (120 seconds) is checked before and after every `gh` call, and a call still running at the deadline is abandoned; the Git calls that read a desk's remote share the same deadline, and one killed by its time limit or a signal stops the flush rather than reading as a desk without a remote. A flush on a machine without factory state returns `not_opted_in` and creates nothing.

`finalize(env, { job, runner })` re-derives the job's sessions from the jobs index and every marker updated since the job's finalize request, letting a session that is still writing go quiet for five seconds, within its own deadline. It then flushes every store holding one of the job's files, waiting out another flush's lock within its own deadline, and removes the request only once all of those files are delivered or quarantined. Any failure, a busy or unreadable session, or a file still in the open PR keeps the request for the next end of turn or session start. A request older than 30 days is dropped.

Both session-start hooks run the [boot-check registry](../hooks/lib/boot-checks.cjs) after building their existing output: an ordered list of checks, each with its own budget inside one 300 ms total, and the real time each takes is charged against that total. A check that overruns, including one that blocks synchronously past its budget, or fails is skipped for that start with its line and repair discarded. When factory state exists, the skip and its elapsed milliseconds are recorded as `boot_checks` in `status.json`; on a machine without factory state it is deliberately not recorded anywhere, because creating that state would turn on finalize requests; repairs start detached with ignored stdio after every check has run. When no check has a line, the hook's output is byte-identical to what it built; otherwise it gains exactly one line, `Desk boot pre-checks: <line>; <line>`, addressed to the agent. The checks, in order:

1. `factory` ([source](../mcp/src/factory/boot-check.js)) reads only consent, the jobs index, the delivered record, the outbox, quarantine and finalize names, and the first 40 lines of the bound desk's task cards. When the desk's store has no consent decision it says nothing: the [boot script](../mcp/scripts/session-boot.js) owns the consent question, which never comes before the operator's work and is never raised in a noninteractive session. For every pending finalize request, whatever person prefix the task tools bound it under, and every finished job (`done` or `cancelled`, updated within 30 days) with an undelivered outbox file, it starts one detached `factory.js finalize` for up to eight of them. The plugin scan and the Git calls that read the desk's remote stop at the check's deadline, and the check is then skipped rather than guessing. Cards are read in the desk layout only, below `desks/<alias>/` when `DESK_PERSON` names one; nothing infers a person from other files.
2. `labels` ([source](../mcp/src/factory/boot-check.js)) runs when a store has `contribute: true`. It reads the names in `evaluate-requests/` and in each contributing store's `quarantine/<store-slug>/labels/<job>/`, the times of those job folders, the reason in each quarantine record there, and, only when both hold something, the jobs index; it never opens a request. A retained request counts as waiting unless every session the jobs index lists for its job has quarantined labels. When any request is waiting, it returns one `Factory evaluator:` line: how many finished jobs wait for labels, how long the oldest request has waited and, from the evaluate step's lag record, how long ago the oldest unlabeled job finished and whether that is past the 1-hour target, the jobs the lag leaves out by the first 8 characters of their IDs (tried three times without an accepted result, or with a session on a host the plugin cannot label on this machine), and either that the plugin labels them in the background (with the last result) or why it cannot (`no_agent_cli`, `no_credentials`, `unsupported_host`, `sign_in_unknown`, `disabled_would_bill`, `disabled`); it starts nothing, because the loop's evaluate step does the work. Finished jobs with quarantined labels, from a job folder updated within 30 days or a request left out of the waiting count, are reported as `Factory: N finished jobs have quarantined waste labels`, and the line says whether a card is open for them. A job folder whose every record is a `job_unbound` withdrawal is not reported, because the flush withdrew those labels on purpose after the session stopped binding the job, and the hold lifts by itself if the session binds the job again. The `andon` line likewise says whether each open andon issue has an improvement card. A noninteractive or headless session gets none of these lines. `desk:session-start` (its `details.md`, "Factory lines") says what the agent does with each line.
3. `desk-health` ([source](../mcp/src/runtime/desk-health.js)) reads the bound root's own `last-start` record. A degraded record becomes one line such as `Desk: degraded (crew checkout on feature-x; writes paused); run desk_doctor`. Otherwise, when a branch is checked out, it starts a detached fast-forward. That process fetches in the background and runs `git merge --ff-only @{upstream}` only when the checkout is on its state branch (the configured one, else `main`), has no tracked changes or Git operation in progress, and has no commits its upstream lacks, checked again after the fetch.
4. `workspace-tidy` ([contract](workspace-tidy.md)).
5. `improvement` ([source](../mcp/src/factory/boot-check.js)) reads the improvement cards once, within its own budget, and returns one `Improvement cards:` line: how many cards are open (those `improvement_next` would offer) and how old the oldest is, or that the cards could not be read. It also counts card files set aside under `_meta/improvement/invalid/`. It is registered last.

After their output is built, both hooks start [factory-start.cjs](../hooks/factory-start.cjs) detached with ignored stdio, but only when a store has `contribute: true`. It runs one `sweep` and then a flush of every consented store within one 120-second deadline, prints nothing and always exits 0.

## Consent, status and the report link

Each machine records one decision per store. When the bound desk's store has none, the `factory` boot check asks the agent to ask once, and [`desk:session-start`](../skills/session-start/SKILL.md) Step 2.7 (and [`desk:first-run-bootstrap`](../skills/first-run-bootstrap/SKILL.md) at its endpoint) asks the operator in plain words: what is published (durations, counts, tool kinds, plugin and model versions, public references), what never is (prompt, assistant or tool content, names, dates and times of day), that the store is public, and that the contributor's GitHub account is the visible author of the intake pull requests. Before asking, the agent names the account with `factory.js account --store <store>`, which asks GitHub about the store with each signed-in account's own token instead of assuming gh's active account, prefers an account with push permission, then one that can fork, and never picks an Enterprise Managed User for a store outside its enterprise; when no signed-in account can deliver it reports `no_account_can_deliver` with each account's reason (`store_not_visible`, `auth_failed`, `forking_disabled` or `managed_account`), and nothing is asked. Yes and no are both recorded with `factory.js consent`, yes with the account `account` named, so the question is never asked again. A noninteractive session neither asks nor records. The boot line asks exactly when `desk_status` reports `undecided`: both read the decision with the same code, and `held`, `unreadable`, `yes` and `no` mean there is nothing to ask.

`desk_status` and `desk_doctor` report `factory` from the [local status](../mcp/src/factory/local-status.js), read without creating anything:

```json
{ "store": "ourostack/factory", "source": "default", "consent": "undecided",
  "stores": [{ "store": "ourostack/factory", "consent": "undecided", "pending": 0, "route_changed": 0, "quarantined": 0, "last_flush": null }],
  "warnings": [] }
```

`store` and `source` are the bound desk's routing (`desk`, `overlay` or `default`, or `invalid_declaration`, `plugin_scan_incomplete` or `no_desk` with `store: null`). `consent` is that store's decision: `yes`, `no`, `undecided`, `unreadable`, or `held` when no store is resolved. `stores` lists the resolved store and then every other store with a recorded decision, each with its outbox files never delivered and not quarantined whose session the flush would publish there (`pending`: here, or unknown and waiting for its route), its outbox files whose session the flush places elsewhere (`route_changed`: away, including a finished retraction's tombstone, stale, or stalled, read exactly as the flush reads routes, so they are never pending there), its quarantined files and its last flush result code. `warnings` holds skipped-manifest codes only. Neither tool prints the machine secret, an account, an intake ID, a token, a time, a local path or any content; `desk_doctor` adds the same data as a `Factory` summary section, and its preview snapshot carries none of it. The Desk MCP server reads the host's plugin set the way the end hook does ([factory context](../mcp/src/tools/factory-context.js)): Claude Code sets `CLAUDE_PLUGIN_ROOT` for the server, so its plugin registry is read; otherwise the folders beside Desk's plugin root are. The scan is the end hook's own code, loaded from the plugin root in `DESK_PLUGIN_ROOT`, because an installed server runs from a source mirror in the cache that has no `hooks/` folder. Claude's launcher sets that variable; on every other host (Copilot's and Codex's configs pass no environment) the server's entrypoint sets it to its own installed plugin folder before anything else runs.

On the transition to `done`, `task_update` and `task_archive` write `factory_report: https://github.com/<store>/blob/reports/jobs/<job>.md` into the task card when the resolved store has `contribute: true` and the desk is known to be private: its cached visibility is `private` or `internal`, so the store publishes the job under its plain job ID, and `<job>` is that ID. It is `factory.js job-link` for the task, computed from the same job identity as binding. `job-link --this-machine` answers the operator rather than the card: on a desk known not to be private it prints `{ "link": ..., "keyed": true, "note": ... }`, the report of the job ID keyed with this machine's secret, which covers this machine's sessions only, and a note saying the link is private. It never prints a link that might be wrong: a desk whose visibility is not known gets `{ "link": null, "reason": "visibility_not_known" }` until the next flush asks GitHub again, and a machine with no secret yet gets `{ "link": null, "reason": "no_machine_secret" }`, because it has published nothing keyed; the command never creates the secret. That link is for the operator's own evaluation (see `desk:online-evaluation`) and never goes on the card or anywhere public. Any other desk gets no link, because its store job is keyed so that nobody can tie the desk's public cards to it, and a link would make exactly that tie. The card then records why, as a reason code and nothing else, in `factory_report_unavailable`, and the tool result carries the same `factory_report_unavailable`: `desk_not_private` (a public desk, a desk GitHub answered as unknown, or a desk with no GitHub remote), `visibility_not_known` (a GitHub desk whose cached visibility answer is expired, absent or unreadable) or `job_identity_unavailable` (the task's job identity could not be read). `job-link` prints `{ "link": null, "reason": "<reason>" }` for the same cases. A missing link is not permanent. Every later `task_update` of a card that records `factory_report_unavailable` asks again: it writes the link and removes the field once a link can be named (its result then carries `factory_report`), and updates the reason otherwise. `task_archive` asks again the same way for any such card it archives, and for a card already in `_archive/` whenever it is called for it again, which is the one tool path that reaches an archived card. When the answer is the reason the card already records, that call writes and commits nothing and says so with `factory_report_unchanged: true`. `factory reconcile` counts the cards still waiting (`counts.report_link_unavailable`). Neither field can be set through a task tool's `frontmatter`; both are refused there. Each answer replaces the last, so a card never keeps an older link beside a reason, or an older reason beside a link, and a card whose desk no longer contributes loses both. The link names where the job's report will be, not that the report exists: the store writes it only after it has merged facts that credit a session to the job and rebuilt its reports, so the link answers 404 until then, and for good for a job no session was ever credited to. Done never waits for delivery. Without consent a move to `done` writes neither field and removes an older one. For `cancelled`, and for edits of a card that is already `done` and records no reason, the link fields are left as they are. A failure to compute the link never fails the task operation.

## Reconcile

`factory.js reconcile --desk <absolute path> --since <time> --until <time> [--store <directory>] [--person-prefix desks/<alias>]` compares a desk's real task activity in a window with the factory's jobs and prints each mismatch with a reason code (see [reconcile.js](../mcp/src/factory/reconcile.js)). It only reads.

- **Which tasks it lists.** A task is listed only when it had real work in the window (or, with `--store`, the store holds a session for it, as `store_only`): a real commit that changes the task's folder beyond its card's frontmatter, or a bound session that holds time in the window. A job holds its segments, never the whole span of its session (a job with no segments, as in a file an older Desk wrote, holds the whole session).
- **Housekeeping is counted, not listed.** A mass commit (one spanning more than three tasks), a commit that carries the trailer `Desk-Tidy: true` (the one-time tidy and its revert add it) and, for older history, a commit whose subject starts with `Tidy desk`, `Revert the desk tidy` or `Revert "Tidy desk` is housekeeping. A card touched only by housekeeping, with no session time in the window, appears in `housekeeping_cards` and in no mismatch, unless the store holds a session for its job in the window, which makes it a `store_only` row.
- **Each task carries its story.** Its bound sessions in start order, each with `active_ms` (the session's active time cut to the job, never a segment's wall-clock span, and `null` when the facts cannot be read) and `bound_by` from the local receipt: `focus`, `inferred`, `subagent_only` (only subagents worked the job), or `not_recorded` (the receipt is older than the binder, meaning below the last version that changed the binding, 6, or missing). `counts.bound_by` counts the story entries each way, so adoption of `task_focus` is measurable.
- **Sessions.** The top-level `sessions` list holds each story session once, with `segments_capped_ms` and `repository_evidence_unavailable` (the receipt's `repo_unresolved`). A receipt written before a measure existed, or by an older binder (`binding_version` below 6, the last version that changed the binding), says `not_recorded`, never `0`, because an older binder's value is not this binder's measure. The `counts` totals give the sum of the recorded values (in the measure's own unit: milliseconds or directories) with `sessions`, how many sessions were recorded, and `sessions_not_recorded`, how many were not; the total's state is `not_recorded` when none was.
- **Cards without a report link.** `counts.report_link_unavailable` is `{ cards, archived, by_reason, jobs_missing, not_checked }`. `cards`, `archived` and `by_reason` count every card of the desk, live or archived and not limited to the window, that records `factory_report_unavailable`; `by_reason` counts the three reason codes, and any other text counts as `unrecognized` without being echoed. `desk_not_private` is meant to last. The others clear themselves: a live card on its next `task_update`, an archived card when `task_archive` is called for it again. `jobs_missing` (`{ cards, archived, by_reason, named }`) counts and names, with `--store`, the done cards whose `factory_report` link names a job the store does not hold: `job_removed` only with positive evidence that the job's facts were delivered from this machine (a delivery record joined to the job by a local copy whose facts hold it; the jobs index alone is not evidence, because it can name a session whose facts never held the job), else `job_missing` (the store lacks it and the cause is not known); `named` lists `{ track, slug, reason }`. `not_checked` (`{ cards, by_reason }`) counts the done cards with a link that were not judged, so a zero never stands for unchecked: `too_fresh` (finished less than a day ago), `no_store` (the store was not read, as in the loop's daily step), `visibility_not_known` (a store was given but the desk's visibility is not known, so job IDs cannot be compared) and `store_file_unreadable` (a store facts file could not be read, so a job may be absent from what was read). The two newer parts are kept apart from the original three fields so an older Desk reading them still reads the counts it knows. The loop's daily reconcile keeps each desk's latest count and sums them into `status.json` as `reconcile.report_link_unavailable` (the health record shows `cards`, `archived` and `by_reason`).
- **`counts.mentioned`** counts real commits on a task that fall inside the own activity of a session bound to another task: a session's own `git commit` calls and its task tool calls, each widened by a minute. They are mentions, not mismatches. Its `sessions` counts the sessions that recorded their own activity, and `sessions_not_recorded` those that could not.
- **Reasons.** A task takes the first reason that explains it, in this order: `not_bound`, `not_opted_in`, `route_changed`, `held`, `log_missing`, `stale_binding`, `receipt_too_old`, `own_activity_cut`, `focus_disagrees`, `not_delivered`, `quarantined`, `pr_open`, `card_missing`, `invalid_status`, `status_unobserved`, and `store_only` for a store job the desk shows no real activity for. `not_bound` replaces the older `no_marker`: a real commit that no session's own activity owns. Its detail counts the desk's unbound markers in the window (`unbound_markers_<n>`), and a task is never blamed on a marker. `mechanical_only` no longer exists, because such cards are `housekeeping_cards`. `stale_binding` means the receipt is older than the binder. Its detail says whether anything will fix it: `binding_version_<n>` when the session's marker is still there, so the next sweep derives it again; for an orphan (its marker was pruned) `orphan_binding_version_<n>` when the orphan pass may still rebuild it, and otherwise why it will not: `orphan_route_unknown` (its desk does not declare the store holding it), `orphan_crew_desk`, `orphan_host_not_rebuilt` (only Claude Code sessions are rebuilt) or `orphan_derive_failed` (frozen after repeated interrupted derives under this Desk). `receipt_too_old` means no session's recorded own activity owns a real commit, but a session of this desk that predates `own_activity` overlaps it and may have made it. `own_activity_cut` is the same for a session whose receipt holds the binder's full 500 own-activity spans and was still running after the last one: what it did after that span was not kept (`sessions_<n>`). `focus_disagrees` means the receipt says a declared stretch held none of the job's own events, and is reported in addition to another reason. `invalid_status` and `status_unobserved` are reported in addition too. `status_unobserved` applies with `--store`, when the card's status differs from the latest status the store observed for the job, which happens when the status changed while the session was focused elsewhere. Observations are ordered by when each is known to hold: the end of the published file that made it, or, for `done` and `cancelled`, the card's `updated` when that is later. A session that is still open counts only as far as its published file goes, never as far as this machine's newer local facts, so an old observation from an open session never stands in as the latest one. When the latest observations tie (nothing places them in time) and disagree, which one is latest is not known: the task gets no `status_unobserved`, and `counts.status_unobserved` carries `not_checked` with the number of such tasks and `reason: "observations_unordered"`.
- **Markers.** The top-level `unbound_markers` list gives each unbound marker in the window its own reason (`held`, `not_opted_in`, `route_changed`, `log_missing`, or `null` for none), so a marker is never blamed on a task. Markers count only between `--since` and `--until`.
- **Routes.** A bound session the flush places elsewhere than the store whose outbox holds its facts is `route_changed`, never `not_delivered`, read with the same route helper as the flush and the local status: detail `routes_elsewhere` for away (a positive route elsewhere, or a finished retraction's tombstone), `stale_copy` for stale, and `retraction_stalled` for stalled.
- **Store rows.** A `pr_open` read from the last flush without `--store` has the detail `pr_<n>_unchecked`. A `store_only` row for a job this desk cannot map prints `job: null`. On a keyed (public) desk the store's job ids are keyed, so `store_only` fires only for jobs with local facts on this machine.

## The improvement loop

The factory closes its own loop: it notices a problem, a card records it, an agent fixes the cause, a later check confirms the fix, and the record shows the result. Nobody has to ask for a pass. This section is for an agent that meets a card mid-task and for a person reading the factory cold.

### Cards

An improvement card is one Markdown file on the desk, in `_meta/improvement/` (under `desks/<alias>/` on a crew desk), committed with the desk. Its key is `<source>:<id>`, so the same finding never makes two cards, and a finding that comes back after its card closed reopens that card and counts a recurrence. The source says where the finding came from: `andon`, `friction_candidate`, `reconcile_class`, `desk_problem`, `store_build`, `evaluator`, `flush_health` or `loop_alarm`. A card holds only codes, counts and pointers (a job id, an issue or pull request number, a reconcile reason). Desk builds its title; no prompt text, command text, file content or absolute path goes into a card. A card is in one of six states: `open`, `claimed`, `shipped`, `verifying`, `closed_confirmed` or `closed_unverified`. A card file that cannot be read is moved to `_meta/improvement/invalid/` and counted, never deleted.

### What an agent does with a card

Three tools carry the work (all in the [MCP README](../mcp/README.md)). `improvement_open` opens a card for a finding, finds it already open or reopens a closed one. `improvement_next` claims the oldest open card, or one whose claim ran out, and answers with the card, a claim id and the authority below; it refuses in a noninteractive or headless session. `improvement_update` lets the holder of the claim ship the card with its countermeasure pull request, release it back to `open`, or close it as `wont_fix`, `duplicate` or `not_reproducible`. Nothing else is patched by hand: the loop sets the shipped version, the check results and every other close.

A card is standing, pre-authorized work. The agent that takes one decides the fix, writes it with its tests through the normal pull request flow, merges when the repository allows it and calls `improvement_update`. It records every ruling it makes in the countermeasure pull request, and the card links to that pull request. A human is asked only at a true gate: money on a human's payment method, a credential or account only a human can act in, or an irreversible destructive action. [`desk:curator`](../skills/curator/SKILL.md) holds the routine. At session start the improvement line says how many cards are open and how old the oldest is; the foreground agent hands the oldest to a background subagent when its own work allows.

System friction opens its card by itself. `friction_add` with `about: "system"` writes the friction entry and then opens `friction_candidate:<fingerprint>`; the entry ends with `Improvement card key: ...`, so the agent that takes the card finds the note by searching the desk's friction files for that key. The other sources open cards without a call, in the loop's route step (below).

### The steps

A detached worker does the mechanical part. It starts at session start after the delivery worker, only when a store has consent and never in a headless factory session, so there is one worker per machine. The end of a turn starts it too, so a finished job is labeled within the hour of its finish rather than at some later session start ([evaluation kick](../mcp/src/factory/evaluate-kick.js)): right after a finalize run has derived the finished job's sessions, and at the end of any turn with no finalize pending, the worker starts when the evaluate step is due for the kick, never in a headless session, with the loop off, with no request waiting, or while a worker holds its lock. For the kick, the step is due when a request is newer than its last run, when the queue is draining (its last run accepted a job's labels, a job the runner can run today is left and the day's ceiling is not spent), or past its gap when a job the runner can run waits (`evaluator.ready_now`, or `ready_later` from an earlier UTC day); a request this machine cannot prepare or run never keeps the kick firing. It runs evaluate, route, mirror, reconcile, verify, measure in that order, each only when due, and exits by itself within 20 minutes. A step is due after its gap: evaluate at most every hour, route and mirror every 6 hours, reconcile and verify every 24 hours; measure runs every time. An evaluation request recorded after the evaluate step last ran makes it due at once, whatever the gap. A worker whose evaluate step accepted at least one job's labels (`evaluator.accepted_last_step`) starts the next worker as it ends; a step whose runs timed out, spent their budget, failed or were rejected starts none, through the same kick, so the queue drains back to back, one 15-minute run after another, until no job the runner can run today is left or the day's ceiling is reached. The kick changes no money rule: the daily ceiling, the sign-in probe and the money rule below apply to every run it leads to.

- **evaluate** asks for finished jobs that have no request (the backstop above), labels the waste in each finished job's sessions headlessly (the money rule below), fresh finishes first and oldest finish first, with relabels after them, counts the requests that expired, and records the label lag: how many finished jobs have a session with no labels yet that the runner can label and is still trying to, and when the oldest of them finished (`status.json` `evaluator.lag`), and how long its facts scan took (`evaluator.scan_ms`: a run starts only with 15 minutes left before the step's deadline, so a growing scan shows here before it crowds runs out). The jobs left out are named apart, never in the lag: `unsupported_jobs` (an unlabeled session on a host the runner does not support, such as Copilot or Codex) and `gave_up_jobs` (three runs without an accepted answer). An accepted run starts a job's attempts again, keeping the day's date, so a session labeled again as its facts change never reaches the limit.
- **route** turns findings into cards: reconcile mismatches that persisted, delivery faults, expired evaluation requests, quarantined labels, open andon issues, filed Desk problems, store builds that fail and the loop's own alarms. Each is one `improvement_open`.
- **mirror** opens the store's kaizen issue for a card that has a measure, so the store's build can judge the fix.
- **reconcile** runs the read-only [reconcile](#reconcile) over the last 7 days and keeps only counts by reason.
- **verify** finds the release that shipped a card's countermeasure, reads the evidence and closes or reopens the card (below).
- **measure** writes the health record.

Turn the loop off with `DESK_FACTORY_LOOP` set to anything but `1`, `true`, `on` or `yes`; that stops every step. Turn the evaluator off alone with `DESK_FACTORY_HEADLESS_EVALUATOR=0`.

### The money rule

The plugin starts the evaluator itself only on a subscription sign-in. Under per-token billing, a per-token credential in the environment or an unknown sign-in, it does not run, spends nothing and says so: `disabled_would_bill` or `sign_in_unknown` on the health record and in the session-start line. Only `no_agent_cli`, `no_credentials`, `unsupported_host` and `sign_in_unknown` open the `loop_alarm:headless_blocked` card, after two blocked days; `disabled_would_bill`, `disabled` and `budget_exhausted` are shown on the health record and at session start and never carded, so the person can decide. Under `disabled_would_bill` the evaluator stays off and the agent changes nothing about billing or sign-in. Each run also carries a budget flag of 1 US dollar and a 15-minute limit, and the run's reported cost is kept (`not recorded` when the output carries none, never zero). Only the plugin's own evaluator process is ever started or stopped, never one found by name. An interactive agent runs `evaluate --pending` and starts a `desk:observer` only to retry a job the loop could not finish.

### Bounds

- At most 30 evaluator runs a day per machine, a safety ceiling rather than a pace; one job at most once a day, and at most three times in a row without an accepted answer (an accepted run starts the count again).
- 1 live claim per machine and 2 new claims per machine per day; a claim lasts 4 hours, then the card is open again.
- The 72-hour freshness rule: a reading older than 72 hours decides nothing, and a step that last succeeded more than 72 hours ago, or failed three times in a row, is stale.
- Two age alarms: the oldest open card is older than 7 days (`loop_alarm:improvement_age`), or a card has been in verification for more than 21 days (`loop_alarm:improvement_stuck`). Loop alarm cards are not counted in either age.
- Verify checks a card at most once every 23 hours and at most 25 cards a run.

### How a card closes

Closing needs evidence, and a reading that failed decides nothing.

- A card mirrored to a store issue closes only on the store's verdict: `closed_confirmed` when the build confirms the change, `closed_unverified` when it cannot.
- A card with no store issue closes on its source's own recovery: an andon issue closing, a reconcile reason at zero on two runs, a store build passing again, a loop condition clearing.
- A Desk problem closes after 7 days quiet from the version that shipped the fix, with its issue closed: `closed_confirmed` when the known-hit reading is measured and shows no hit, `closed_unverified` otherwise.
- Thin data never confirms a card. A card still reading thin data after 14 checks closes `closed_unverified` (`thin_data_after_14_checks`) when its pull request is merged with green checks, and goes back to `open` when it is not merged.
- A condition that is measured present again at 3 verifying checks reopens the card.

### When a loop alarm card opens

A loop alarm is a card like any other. The loop opens it when its own machinery needs a fix:

- `improvement_age`: the oldest card has waited too long. Take it with `improvement_next`.
- `improvement_stuck`: a shipped card cannot reach a verdict. Check that the countermeasure pull request merged and released, and that the release lookup and the store reading work; fix what is missing.
- `unsigned_age`: deliveries wait for sign-off longer than 7 days. It reads the `signoff` counts that session start records in `status.json` (a scan older than 72 hours reads `stale` and alarms nothing); a partial count is a lower bound and alarms when it is already above the limit. Sign the deliveries off with `task_signoff` to clear it.
- `headless_blocked`: the evaluator could not run on two days in a row. An agent can fix `no_agent_cli` (install the agent CLI) and `no_credentials` (the CLI is not signed in; agents run sign-in flows themselves). `unsupported_host` means the job's host cannot run the evaluator; read which hosts are supported before changing anything. `sign_in_unknown`: check the CLI's sign-in status and repair what an agent can, which is a CLI that is not signed in; never switch billing. The other blocked states never open this card: `disabled_would_bill` is a person's money decision, so the agent changes nothing, `disabled` is the person's own switch and `budget_exhausted` ends with the UTC day.
- `label_lag`: a finished job has waited more than an hour for labels (`evaluator.label_lag_minutes` on the health record above `label_lag_alarm_minutes`, 60). The owner is the loop's evaluate step ([evaluator step](../mcp/src/factory/evaluator-step.js), triggered by the [evaluation kick](../mcp/src/factory/evaluate-kick.js)). The lag counts only jobs this machine can label and is still trying to (jobs on an unsupported host and jobs at the attempt limit are named on the session-start line and counted as `unlabeled_unsupported` and `gave_up`), and the alarm stays down while the evaluator cannot run at all (`no_agent_cli`, `no_credentials`, `disabled_would_bill`, `sign_in_unknown`, `disabled`), which have their own state and alarm. Read the health record's `evaluator` (its `headless.state`, `jobs_today` against `cap_per_day`, `gave_up`) and the evaluate step's `last_result`: a spent daily cap ends with the UTC day, a blocked state is the `headless_blocked` card's, and `disabled_would_bill` is the person's decision, so the agent changes nothing about billing. A lag that grows while the evaluator runs and nothing is blocked means the trigger or the backstop missed the job; check that the job has a request in `evaluate-requests/`.
- `labels_quarantined`: labels were refused or their session's facts were quarantined. Read the quarantine folder and the `facts_quarantined` record for the cause. A label withdrawn as `job_unbound` does not raise it.
- `facts_quarantine_not_settling`: a coverage pass was recorded although a facts quarantine did not settle within the hour (`coverage_kept` is `quarantine_not_settling`), so a host mostly in quarantine goes to the store as not counted. Read the quarantine records (`desk_version` names the Desk that wrote each; a record without it came from an older Desk), check whether the copies validate now, and run `factory.js flush --store <store>` from the installed Desk, which releases those that do. A long-running session on an old Desk can quarantine them again; restart it.
- `cards_invalid`: card files were set aside under `_meta/improvement/invalid/`. Restore each to `_meta/improvement/` once fixed, or delete it, and commit.
- `capture_loop_slot`: the loop's own health record fails the store's `loop_slot_v1` rule, so the capture record goes without its loop slot. Find which count is out of range on the health record (`loop.health` in `status.json`) and fix its source.
- `step_stale:<step>`: a step has not succeeded for 72 hours or failed three times in a row. Read that step's `last_result` on the health record and fix it.

### The health record

The `measure` step writes the loop's health into `status.json` in the machine's protected factory state, under `loop.health` (`desk_status` and `factory.js status` read it). It holds counts of cards by state and source, the age of the oldest open card and of the oldest card in verification, cards closed and reopened in the last 30 days, the unsigned deliveries, open alarms, the evaluator (waiting, expired, given up, quarantined, the label lag in minutes, the finished jobs still unlabeled and those on a host the runner does not support (`unlabeled_unsupported`), its state, today's runs and cost against the daily cap), the reconcile mismatch counts by reason, the cards still waiting for a factory report link (`reconcile.report_link_unavailable`: `cards`, `archived` and `by_reason`, each `unavailable` with `not_recorded` until a reconcile has counted them), and each step's last run, last success, last result, counts of runs and failures, expected interval and whether it is stale. Every number, constants such as the alarm limits and the expected intervals included, travels as `{ state, value, reasons }`: `measured` with a value and no reasons, `partial` with a lower-bound value and its reasons, or `unavailable` with `value: null` and the reason code. A value that was not recorded is `unavailable` with the reason `not_recorded`, never zero, so an empty list means nothing was found only where the count itself is measured. The loop's reconcile compares the desk only; it does not clone the store in this version. The two reasons that need the store's facts, `status_unobserved` and `store_only`, are therefore listed under `reconcile.store_side` as `unavailable` with the reason `store_not_compared`, never as zero mismatches. Comparing against the store is left to a later change. The record never holds a path, a task name or free text, and it is kept on this machine (a later change flattens it and delivers it with the intake).

## Completion and remaining boundary

The [task tools](../mcp/src/tools/task.js) write `finalize/<job>.json` on `done`, `cancelled` and archive, including repeat archive calls, only when factory state already exists. They use the same job identity as binding; a factory failure emits a fixed diagnostic code without failing the completed task operation. This does not wait for a store, create consent or mark a report delivered.

The [CLI](../mcp/scripts/factory.js) advertises `finalize`, so the end-of-turn hook now starts it for pending requests, and the `factory` boot check is the backstop. Delivery to the live public store, and installed Claude, Copilot and Desktop behavior for delivery, remain unverified until the channel update is installed and the controller runs the live proof.

## Capture coverage

The sweep counts each host's root sessions on disk and says what became of them. It lists folders only and never opens a transcript, except that for Codex it reads at most the first 16 KiB of each rollout file's first line to tell a child session from a root session. A symlink, a hard link and a symlinked folder are never counted. The counts go to the local `status.json`, and once a store says it accepts them, one content-free record per machine goes to that store. Nothing from a transcript is stored, logged or published.

### The buckets

Every session a host kept on disk is in exactly one bucket, and the buckets of a host add up to its `on_disk` count (the sweep checks the sum for every host before it writes anything).

- `derived`: the session has facts and they are placed with their store (delivered, or waiting in the outbox for that store).
- `held`: facts are not being made or sent for it, because its facts copy is quarantined (a transient state while a quarantine is being released, see `coverage_kept` below), its marker names no store, the store has no `contribute: true` consent, or it is an unproven Codex default route.
- `frozen`: facts exist or could exist, but the session cannot be published now. Its route is unknown, stale or stalled, or it is an orphan that is not current (see below). `frozen_by_reason` counts the reasons as fixed codes, and tolerates reasons it does not know.
- `pending`: the session has a marker and its store has consent, and its facts are not derived yet.
- `not_seen`: the capture hook never marked the session (or, on Copilot CLI and Codex, the marker says no desk), so there are no facts for it. On Copilot CLI and Codex an unmarked session has no owner (`-`), and a store's record leaves those out (see the owner rules below); they stay in the local `status.json`.
- `not_in_a_desk`: Claude Code only. An unmarked session in a folder that belongs to none of this machine's known desks. On Copilot CLI and Codex this is `null`, because an unmarked non-desk session cannot be told from a miss there.

A bucket that cannot be told is omitted or `null`, never `0`. A host that is `absent` (no folder), `unreadable` or `capped` (more than the entry budget or the three-second time budget) carries only its `state` and `unverified`, no counts.

Every not-current orphan reads as `frozen`. An orphan is current when its receipt is at or above 6, the last version that changed the binding, even though the orphan pass still re-derives one below 7 while its transcript is on disk. The orphan pass counts its pending orphans machine-wide, so that count cannot be split by owner and is never used: one owner's record must not move with another owner's sessions. The reason is `orphan_unsplit`, or `orphan_pass_unavailable` when the pass left no usable result. `frozen_by_reason` has that one source, so its counts add up to `frozen` and no orphan is counted twice; the pass's own reasons are a tally of its last window and stay in `status.orphans`.

### The local `status.json` keys

- `coverage`: `{ method: 1, ran_at, hosts }`, one entry per host as above, plus `by_owner` (each owner's own buckets, which sum to the host's) and, on Codex, `undetermined` (rollouts whose first line could not be read) and `fallback` when set.
- `coverage_failed`: set to `state_unreadable`, `count_failed` or `classify_failed` (the stage that failed, no message) when a pass fails. A failed pass keeps the earlier `coverage` in place and writes only this code. A successful pass clears it.
- `coverage_kept`: set when a coverage pass is held back because the quarantine is in flux, so a record is never built from a transient state. A pass is in flux when a quarantine folder changed within the last 5 minutes (a folder dated in the future counts as settled), or when the sessions whose facts copy is in quarantine are more than half of a host's sessions on disk (sessions held for another reason, such as a store without consent, do not count). While passes are kept the previous `coverage` stays and the value is `{ code: "quarantine_in_flux", since, at }`; the sweep reports `kept`. The keep lasts at most one hour from `since`. After that the pass is recorded anyway, the value becomes `{ code: "quarantine_not_settling", since, at }`, and the status and the doctor say the quarantine did not settle. In that recorded pass, each host most of whose sessions are in quarantine keeps its counts and is flagged `held_in_quarantine: true`; the record sends it as `{ "not_counted": true }`, never as a share, and the loop raises the `facts_quarantine_not_settling` alarm so the store's status line still shows that something is wrong. A pass with nothing in flux clears it.
- `coverage_cache`: local only. Its keys are Codex rollout file names, kept so the next sweep need not reread unchanged files. It is never copied into `coverage`, a record, `last_flush` or any other file.

### Owners and withheld sessions

Each session has an owner, and a store's record counts only its own sessions plus the owner `-`, except that an unowned `not_seen` session of a host whose `not_in_a_desk` is `null` (Copilot CLI and Codex) is withheld like `?`.

- A store name is the owner when a marker, a receipt or a facts copy tells it. Names are compared in lower case.
- `-` means the session belongs to no store: no desk evidence names it, and at most one store has `contribute: true`.
- `?` means the owner cannot be told, and a `?` session is in no record at all. This happens when a marker or receipt names a desk root but its store cannot be told (a desk with no tellable store, or a route that is unknown or whose desk folder is gone); when two sessions of one desk folder point to two stores, or one of them to none; when two desks share one Claude Code folder name (a folder-name collision) and their sessions point to different stores; and when an unowned session exists while two or more stores have `contribute: true`, because it could belong to either.
- An unmarked Copilot CLI or Codex session has no owner, because those hosts cannot tell a session in no desk from a missed one, so it might belong to a private store. A store's record leaves it out of every count, and the host keeps `not_in_a_desk: null` so the store can tell. The share of such a host is therefore not a measure of capture coverage, only of delivery of sessions that were already marked, and the store reads it as unavailable.
- Failing closed costs a slightly high-looking share. Failing open could put a private desk's activity in a public record, so every doubt is withheld.

### The published record

When a store accepts capture records, the sweep's coverage is scoped to that store and sent as `capture/<intake id>.json` in the same intake pull request as facts, through the same outbox and flush. The file name's intake id is the machine's existing intake branch name, so it is already public. The record holds counts and fixed words only: no date, path, session id, desk name, store name or host name beyond the three hosts.

The key set is closed. Any other key fails the store's gate with `unknown_key`. The machine-readable list is this block, and a test fails if it differs from the schema ([capture-schema.js](../mcp/src/factory/capture-schema.js)):

```text capture-record-keys
top: schema basis hosts loop
host: on_disk derived held frozen pending not_seen not_in_a_desk unverified
uncounted: not_counted
```

- `schema` is `desk.factory.capture/1`, and `basis` is always `still_on_disk`. `basis` is required so the share cannot be shown without its caveat.
- `hosts` holds zero to three of `claude-code`, `copilot-cli` and `codex-cli`. A host that is `absent` on this machine, or whose in-scope total is 0, is left out. A host that could not be counted (its listing was `capped` or `unreadable`, or most of its sessions sat in a quarantine that did not settle, `held_in_quarantine`) is exactly `{ "not_counted": true }`, with no other key: never a zero and never left out. Every other entry has the eight keys above. Each count is an integer from 0 to 1,000,000, `not_in_a_desk` may be `null`, and `unverified` is a boolean. The buckets add up to `on_disk`, which is the in-scope total, not the machine's.
- `loop` is one optional slot, the closed loop's health record, in the store's `loop_slot_v1` shape. `validateLoopSlot` is exactly as strict as the store's rule, so a record Desk accepts is one the store accepts: `v` is required and is `1`; the only other keys are the nine count keys of `LOOP_SLOT_COUNTS` in [capture-schema.js](../mcp/src/factory/capture-schema.js), each a whole number from 0 to 1,000,000 or `null` (never a boolean or a string), and `headless`, a code matching `^[a-z_]{1,32}$` or `null`; the slot is at most 512 bytes and never nested. A key the store does not know is refused here, not a week later by the store. The slot is filled from the loop's stored health record by [loop-slot.js](../mcp/src/factory/loop-slot.js), only when that record was written in the last 72 hours: the four improvement card counts (open, claimed, shipped, verifying; loop alarm cards are not in the open count, they are `loop_alarms_open`), `oldest_open_age_days` the age of the oldest open card plus the record's own age in whole days (the slot has no date, so the store's 7-day alarm is never late), `closed_confirmed_month` and `closed_unverified_month` the cards closed in the last 30 days, `loop_alarms_open` the open loop alarm cards, `steps_stale` how many steps are stale and `headless` the evaluator's state code. A number the loop could not measure (unreadable, partial, or no card to age) is `null`, never 0, a stale or missing record sends no slot, and a single value that fails the store's rule is sent as `null` while the rest of the slot goes. The empty record never carries it.
- The record is at most 2 KiB, in canonical bytes.

The share is "of sessions still on disk" and an upper bound: a host that deleted its old transcripts is invisible here. A store's record is also self-reported: the store cannot check it, and anyone who can open an intake pull request can overwrite a capture file, so the numbers are a signal, not proof.

### Reading the record with number states

The record is raw input, and a store's reports must read it by the same rule as every other number: a count never stands alone, and a number that was not measured is never shown as 0. A host entry that is present has measured counts, and when its `unverified` is `true` the counts are a lower bound, shown as unverified in words. A `null` `not_in_a_desk` was not measured. A host left out of the record means no session in this store's scope (or no such host on the machine), which is not the same as zero sessions seen on the machine; for Copilot CLI and Codex it can also mean that every session in scope was an unowned one that the record withholds. A host whose entries all have `not_in_a_desk: null` (Copilot CLI, Codex) cannot say which unmarked sessions were missed, so the store reads its capture shares as unavailable with the reason `host_does_not_say_desk`, raises no low or dropped alarm for it, and marks the store-wide share partial with that reason. A host that is exactly `{ "not_counted": true }` could not be counted on that machine at that time, or most of its sessions sat in a quarantine that did not settle: it has no data, shown as "not counted", never as 0 and never as "no sessions", and it does not stand for the counts the store held before. A store with no record has no data. A rollup over machines says how many machines it rests on (n of N). The record carries no reason keys, so the store's own reading and wording apply, in the terms of its README.

### Codex is unverified until proven

A record's Codex entry says `unverified: false` only when the in-scope `derived` count is above 0 (a Codex session this store's own facts were derived from), the listing had no `undetermined` rollouts, and no fallback listing was used. Otherwise it says `unverified: true`. An `undetermined` residual is a rollout whose first line was unreadable, too long or invalid, so it could be a root or a child. It is never counted as a session, and any above 0 makes the host unverified. The host's own receipt-based flag is not read for the record, so another store's derived session cannot change a public record.

### A host that is capped, unreadable or mostly in quarantine

A host whose listing is `capped` or `unreadable`, or that the sweep flagged `held_in_quarantine` (most of its sessions sat in a quarantine that did not settle within the hour), goes into the record as exactly `{ "not_counted": true }`, and the other hosts keep their true counts, so the record never overwrites a host's true counts with a gap and never says zero for one it could not count. The store takes that shape and nothing else (`capture_keys` or `capture_values` otherwise). The local `status.json` still says why (the host's `state`, or its `held_in_quarantine` flag with `coverage_kept`). A machine that stays stuck stays visible in the record, and the store's rule for stale files (below) still catches a machine that stops sending. A machine whose only host is uncounted sends that one flag, which replaces the record the store held: the store reads "could not count", not "no sessions".

### When a record is sent

- Handshake: the record is sent only when the default branch holds a file `capture.json` at its root whose content is exactly the JSON object `{"capture":1}` (read through the account's own client, from the store, not a fork). Anything else, no file, an error, bad JSON, an extra key or another value, is `store_not_ready`: no record is sent, `status.capture[<store>].skipped` says so, and the store is asked again after a day. `factory.json` is deliberately untouched (a `capture` key there enables nothing), so an older client's andon parser keeps working. A store that is not ready never delays facts.
- Coverage older than three days (by `ran_at`), unparsable or in the future sends nothing and retracts nothing. A failed pass leaves the earlier coverage in place, so it is used only while it is still fresh.
- Replacement is throttled to once in 20 hours, and only when the bytes differ from what the default branch holds. The one exception is a corrected record: when the captured share (`derived` over `derived + frozen + pending + not_seen`) of any host named by both this record and the last one sent differs by 0.15 or more, the record is due at the next flush. The share of the last record sent is kept locally as `sent_share` in `status.capture[<store>]` (a ratio per host, never published). A small change still waits. The bookkeeping lives in `status.capture[<store>]` and never in a delivered record. A push that rebuilds the intake branch without a record the open pull request carried either finds the record on the default branch (settled) or records it as not delivered: `dropped: "capture_dropped"` and `dropped_at`, with `sent_at` forgotten so the record is due at the next flush instead of 20 hours after the lost send. State with no kept bytes cannot be checked, so it keeps `sent_at` and records `dropped: "capture_drop_unconfirmed"`, which is never raised as a finding because the record may have landed. A record still `capture_dropped` six hours later is raised as a finding: `capture_dropped` in the doctor and boot status.
- Retraction is the empty record, `hosts: {}`. It is sent when a record was sent before and nothing is left in scope (every host `counted` or `absent`). Any contributor may send it. A host that could not be counted is in the record as `not_counted`, so it is not an empty scope and is never retracted.
- A refusal that names the record (a `capture_*` code except `capture_check_unavailable`, or `path` for the pull request that carried it) is counted as a stale pull request: facts are sent again and never quarantined because of it. The record backs off a week. A data code beside it still quarantines facts as before.
- `capture_check_unavailable` is the store's own check failing to read the commits, an infrastructure failure and not a refusal of the record. It is a stale pull request like a merge conflict: facts go again, nothing is quarantined, no week's wait is recorded, and the record goes again in its normal 20-hour turn.
- The record's own gate fails (a bug, not a store refusal) only as `capture_invalid`: nothing is sent and it is asked again after a day.

### Local retention

The sweep keeps local state from growing without bound, and never at the cost of a retraction. A finished retraction's tombstone records when it finished (`at`) and is pruned after 90 days, but only when no local copy of that session is left for that store (outbox, labels, `retracted-copies/` or quarantine); kept copies are never deleted, so a tombstone normally stays as long as they do. A kept copy that has no positive route here fails closed and stays frozen: a lost or unreadable `status.json` never makes it publish. A delivered facts copy is pruned only when its transcript is gone, its record is over 90 days old, the delivered record holds a trusted path and the blob sha of this very copy (so nothing newer and undelivered is lost and a later retraction can still find the file); a delivery recorded by an older Desk has no such sha, so its copy stays. `factory.js status` shows `retention` (what the last sweep pruned, a failure code, or that nothing has run; a failed copy prune is counted as `copies_prune_failed`) and `capture_check`, a line per store whose own capture check could not read the record three times in a row. Neither waits for someone to look: a failed pruning raises the `retention` finding (`prune_failed`, or `copies_prune_failed`) and a store whose check failed three or more times in a row raises `capture_check_unavailable`, only for a store this machine still contributes to. Each is a line in `desk_doctor`'s summary and in the plain-text boot (starting `Factory: `), next to the orphan pass's finding, before the consent line. Kept copies with no positive route anywhere are frozen for good: never published and never deleted, which is the fail-closed cost of a session whose route can no longer be shown. The local status counts them per store (`kept_frozen`, with `kept_frozen_oldest_days`) and `desk_doctor` prints the count and the oldest age.
