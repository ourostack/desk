# Factory local session capture

Desk records local session facts without waiting for a network service, delivers their published form to a factory store from a detached process at the next session start, and provides the deterministic pipeline a store uses to validate published facts and waste labels and rebuild reports. The store's own workflows live in the store repository, and delivery to the live public store is not yet proven on installed hosts. The [end hook](../hooks/factory-end.cjs), [runner](../mcp/src/factory/derive-run.js), [delivery](../mcp/src/factory/flush.js), [boot checks](../hooks/boot-checks.cjs), [pipeline](../mcp/src/factory/pipeline/) and [synthetic tests](../mcp/__tests__/factory/) define this boundary.

## Host events

| Event | Local action | Detached action |
| --- | --- | --- |
| Claude `Stop`, Copilot `agentStop` | Refresh the protected session marker. | Run `factory.js finalize --job <job>` for each pending finalize request, at most eight. |
| Claude `SessionEnd`, Copilot `sessionEnd` | Refresh the marker with the end reason. | Run `factory.js derive --marker <file> --wait-quiet 30000`. |

The [host manifests](../hooks/hooks.json) and [Copilot manifest](../hooks/copilot-hooks.json) register these events. The [handler](../hooks/factory-end.cjs) caps stdin at 1 MiB and stops waiting for input after 150 ms. Its supervisor keeps the unchanged 1.5-second deadline outside the worker that performs synchronous metadata and OS-protection work, terminates a blocked worker and waits for its exit. Both processes print nothing. Ordinary native operation targets 500 ms; the [subprocess tests](../mcp/__tests__/factory/end_hook.test.js) allow 2 seconds for CI. The local protection helpers may invoke OS ACL utilities, but neither the hook nor derivation requests a network operation.

Copilot log paths come from `sessionId` under `COPILOT_HOME` (otherwise `~/.copilot`), not from prompt text or `transcriptPath`. Agency plugin-session locations supply the `launcher` entrypoint. Plugin names and versions come from sibling manifests on Copilot and the installed-plugin registry on Claude. Each plugin also records its install source, the GitHub `owner/repo` it came from, or `null` when that is not known for certain. Every lookup fails closed:

- **Claude Code:** the plugin's marketplace must be a GitHub repository in `known_marketplaces.json`, and the marketplace's cached manifest (`<installLocation>/.claude-plugin/marketplace.json`) must list the plugin. The source is then the marketplace's repository for a relative path inside it, or the listing's own GitHub repository. A plugin the manifest does not list, a listing hosted anywhere but GitHub, or a name listed twice with different sources has no source.
- **Copilot under Agency:** the source comes from Agency's cache index. Every index entry counts, including non-GitHub ones. A plugin has a source only when the whole index was read and every cached entry at the plugin's exact name and version came from one GitHub repository. A name never matches on its own. An index with more than 256 entries, an entry whose folder cannot be read, and a scan the source budget cuts short all give no source for any plugin.
- **Plain Copilot:** exactly one `installedPlugins` record in `config.json` must match the plugin's name and version, and its marketplace must be a GitHub repository in `settings.json` `extraKnownMarketplaces`. Copilot keeps no marketplace manifest to check the listing against, so the marketplace's repository stands in for the plugin's.

The Stop hook gives the lookup 400 ms. After that, every source is `null` and the plugins are still recorded. Markers and local facts written before sources were recorded stay valid, and their plugins read as having no known source. The marker captures the resolved route so deleting a temporary plugin folder cannot redirect a later sweep to the default store. Every discovery cap, including Claude's records-per-key and aggregate manifest-directory limits, makes routing incomplete; only the desk's own valid declaration can override that hold. The [marker validator](../mcp/src/factory/marker.js) limits paths and metadata, while the [canonical resolver](../mcp/scripts/resolve-desk-root.js) owns desk selection. Hook-facing activation reads are regular-file-only, no-follow and capped at 64 KiB. An unresolved binding defers capture rather than guessing. `DESK_PERSON`, when set, supplies an explicit `desks/<alias>` binding prefix; no identity is inferred from content.

## Local state and commands

All factory state lives at `$XDG_STATE_HOME/ouroboros-skills/desk/factory`, or `~/.local/state/ouroboros-skills/desk/factory`. The [outbox](../mcp/src/factory/outbox.js) applies the shared owner-only protections and refuses Git checkouts, symlinks and hard links. Capture, derivation and finalize callers also exclude the canonical bound desk, including unversioned desks and symlink aliases, before creating state. Direct marker reads, sweep and status use the same owned-directory, leaf-protection, 64 KiB and filename/session identity checks. The read retains the protected directory's identity, compares the opened descriptor with the post-read descriptor and current pathname, and rechecks directory/leaf identity before returning data. Leaf repair follows identity validation; corrupt/expired pruning rechecks the same owned directory and leaf rather than adopting a replacement. Markers are local bookkeeping, not published facts: paths, routing warnings and exact hook times never enter a facts file. Prompt fields, assistant text, task titles and tool arguments are not copied into markers.

Run commands from the installed Desk plugin root:

```sh
node mcp/scripts/factory.js consent --store ourostack/factory --contribute yes --account <login>
node mcp/scripts/factory.js derive --marker <protected-marker-file> --wait-quiet 30000
node mcp/scripts/factory.js status
node mcp/scripts/factory.js flush --store ourostack/factory
node mcp/scripts/factory.js finalize --job <job> [--job <job> ...]
node mcp/scripts/factory.js validate-pr --base <base-sha> --head <head-sha> --author-association <value>
node mcp/scripts/factory.js build --store <store-directory> --out <output-directory>
node mcp/scripts/factory.js job-link --store <owner/repo> --desk-remote <url> --person-prefix <prefix> --track <track> --slug <slug>
node mcp/scripts/factory.js evaluate --desk <desk-root> --task [desks/<alias>/]<track>/<slug>
node mcp/scripts/factory.js evaluate-accept --job <job>
```

The [CLI](../mcp/scripts/factory.js) returns one JSON result. `derive` accepts only a marker in the protected marker directory, waits for source quiet for up to five minutes, and then returns `written`, `held`, `skipped`, `not_opted_in`, `log_missing`, `source_unreadable` or `invalid`, with the selected store when known. `flush` makes one delivery attempt and prints `{ result, pr? }`; `finalize` takes one to eight distinct jobs and prints each job's outcome. Local `status` includes marker/finalize counts, derivation receipts, routing warnings, the last flush result per store and skipped boot checks; it is not a public report and must not be uploaded as facts. No command prints the machine secret or a token.

## Waste labels

When a task reaches `done`, `desk:task-lifecycle` runs `evaluate`, and the agent handles its answer as `desk:session-start` Step 4.8 says: when the answer is `ready`, it starts a fresh `desk:observer` subagent in the background with only the brief paths. `evaluate` first records an evaluation request at `evaluate-requests/<job>.json`, because the session that finished the job is usually not derived until it ends. `evaluate --pending` prepares retained requests again; a request is cleared once every session of the job has ended and has accepted labels or has its labels held back because its facts are quarantined, and moved to `evaluate-requests/quarantine/` as `expired` after 30 days or `not_opted_in` when its stores lose consent. Without factory state or consent, `evaluate` answers `not_opted_in` and creates nothing. The observer labels each session's waste with the [factory-evaluator rubric](../skills/factory-evaluator/SKILL.md) and never sees the working agent's conversation. `done` does not wait for it.

- **`evaluate`** computes the task's job ID exactly as the task tools do and, for each of the job's sessions (from the jobs index) that a store with consent holds, writes one brief to `evaluations/<job>/<store-slug>/<host>-<session-id>.brief.json` in the protected state folder. It answers `ready` with the brief paths, `not_opted_in` when no store has consent, or `no_sessions`. A session whose ID is not a version-4 UUID gets no brief, because its labels could never be published. Neither does a session whose facts are quarantined, even facts too broken to read: its labels could only ever travel with those facts, so its labels key is quarantined instead, as `facts_quarantined` with the quarantined facts file's name in the record's `facts` field, and the session counts as settled.
- **The brief** ([evaluator](../mcp/src/factory/evaluate-run.js)) holds the job, the session, the plugin version and rubric version the labels must carry, the host's session log path from the session's marker (or `null` when the marker or the file is gone), the session's start as the clock origin, the session on the published clock, the `unavailable` codes that apply and the output path. Its intervals come from the same code that publishes facts (`publishedClock`), so evidence copied from them matches the store's facts. The brief stays on this machine.
- **`evaluate-accept`** checks each answer against a brief rebuilt from the session's own local facts and marker, never the brief file the evaluator can edit; facts that are gone are refused as `facts_missing`. The checks are: JSON within the facts size cap, the labels v1 schema, the brief's job, session, plugin version and rubric (`job_mismatch`, `session_mismatch`, `evaluator_mismatch`), every `unavailable` code the brief names and no false `facts_missing` (`inconsistent`), and the store's own evidence and range checks against the brief's intervals (`evidence_unmatched`, `range`). Each session comes back `accepted`, `missing`, `rejected` with `{ code, path }` errors (including `too_large` and `unsafe_file` for an answer file that cannot be read), `not_opted_in` or `invalid_brief`. No result echoes anything the evaluator wrote. Accepted labels are rebuilt field by field, written as canonical bytes to `labels/<store-slug>/<job>/<session-id>.json` in the protected state folder, and the brief and answer are removed. A rejected answer never enters the outbox.
- **Delivery.** Local labels are already on the published session clock, as offsets from the session's start, never times of day. `toPublishedLabels` maps them to `labels/<job>/<session-id>.json` in the store and keys the job ID exactly as the facts transform does for a desk that is not known to be private. `pendingLabels` lists labels whose published bytes the store has not received, recorded in `delivered/<store-slug>.json` under `labels/<job>/<session-id>.json`.

## Store-side validation and reports

`validate-pr` judges exactly what merging the head into the base would land. It builds the merge result with `git merge-tree --write-tree` (Git 2.38 or later; an older or unreadable Git fails with `git_too_old`, and a merge-tree failure other than a conflict with `merge_tree_unavailable`, both without a result), lists changes as the base against that tree, and reads bytes through `git show` and `git ls-tree`. It refuses a head whose merge conflicts (`merge_conflict`) and a head that carries merge commits not already on the base (`unexpected_merge`). A `base...head` diff would read only one merge base, while the merge uses all of them, so a crafted head could otherwise pass while its merge changed something else. It never checks out, imports or executes candidate-controlled files. Contributor changes are limited to at most 500 added or modified data files of two kinds: published facts at `facts/<host>-<session-id>.json` and published labels at `labels/<job>/<session-id>.json`. Each facts file must pass the canonical published-bytes gate, match its filename identity, preserve host/session identity when modified and never reduce `session.duration_ms`. Validation output contains only stable reason codes and safe paths. Any change that is not a published facts or labels file, including any other file under `facts/` or `labels/`, is accepted only for GitHub author associations `OWNER`, `MEMBER` or `COLLABORATOR`, and is marked as maintenance for the store workflow to leave unmerged. Those maintainers may also remove facts and labels files; a removal is always maintenance, and every other author's removal is rejected. A modified facts file's previous bytes are read at the base, and its new bytes in the merge result.

A labels file holds an independent evaluator's waste labels for one job's session, in the exact [labels v1 schema](../mcp/src/factory/label-schema.js) (`desk.factory.labels/1`). It carries the job and version-4 session IDs, the evaluator, a list of stretches, and a list of what the evaluator could not read. Nothing in the file is free text:

- **Evaluator.** `plugin_version` is a Desk version such as `3.2.0` or `3.2.0-alpha.58`: three numbers of at most three digits, optionally followed by `-alpha.N`, `-beta.N` or `-rc.N`. `model` uses published facts' own model-ID validator: a token of at most 80 characters with no spaces, with no date, time of day or credential-shaped value. `rubric` is the rubric version as a digit string from `1` to `999`.
- **Stretches.** Each stretch is a `[start_ms, end_ms)` span on the session clock with a `class` of `value`, `support` or `muda`, a `waste` that names one of the eight classic wastes for `muda` and is `null` otherwise, `mura` and `muri` flags, and at least one evidence range. Stretches are listed in start order and never overlap. An evidence range may cite any interval of the session, not only one inside its own stretch; a defect stretch may rest on an earlier failed tool call, for example.
- **Unavailable.** `unavailable` uses a closed set of codes. `session_log_missing` means the host's session log was gone or unreadable, so the labels rest on the facts alone. `facts_missing` means the job's local facts were missing, so the file carries no stretches.

The gate reads that session's facts file, `facts/<host>-<session-id>.json` for either host, from the tree the merge would leave. It reads the file in the merge result when the merge adds or modifies it, treats it as absent when the pull request removes it, and otherwise reads it at the base tip, so labels whose branch predates their facts pass once the facts reach `main`. Exactly one such file must exist (`facts_missing`, `facts_ambiguous`) and pass the published-facts gate (`facts_invalid`); labels that declare `facts_missing` need no facts file, but one that exists is still checked. The labels must name a job that file binds (`job_unbound`), every stretch must end within the session (`range`), and every evidence range must equal one interval's `start_ms` and `end_ms` exactly (`evidence_unmatched`). Evidence names time ranges rather than list positions, so labels stay valid when a still-running session is re-derived and grows. The job and session inside the file must match its path (`job_mismatch`, `session_mismatch`). Anyone may replace a labels file, but only with labels from an evaluator whose plugin version and rubric are both no lower than the ones it replaces (`evaluator_downgrade`); the previous bytes are read at the base.

A public store receives a plugin's name and version only when the plugin was installed from a public repository; the flush resolves each source's visibility, and the store's own, with the references', and never publishes the source itself. Every other plugin, including one with no known source, and every plugin when the store's visibility is unknown, is counted in `refs.private.plugins`. A store known to be private or internal, an organization's work store, receives every plugin's name. `refs.private.plugins` is optional in the published schema, so files published before it existed stay valid.

Published facts and labels share one refusal for secrets. Model IDs, plugin names and PR and commit repository names are refused as `credential_like` when they start with a token prefix such as `ghp_`, `github_pat_` or `sk-`, or hold a 16-character or longer hex or letter-and-digit run, a password value or an IPv4-looking run. The factory keeps its own copy of Desk's credential rules, and a test holds the two in parity. The rule can also refuse a real name: a repository such as `acme/build2026Q3release` holds a 16-character letter-and-digit run, so a facts file that names it is refused as `credential_like`.

`build` reads regular files directly under `facts/` and `labels/<job>/`, validates them again, sorts every key and collection explicitly, and replaces the output directory with deterministic `README.md`, `index.md`, `jobs/<job>.json`, `jobs/<job>.md` and `rollups/` bytes. It reads no wall clock. A store without `facts/` has zero sessions and publishes an empty index. Dotfiles such as `.gitkeep` are ignored; any other entry that is not a published facts file stops the build with a stable code (`invalid_facts_entry`, `facts_entry_not_regular_file`, `facts_not_directory` or `invalid_published_facts`), and so does any entry under `labels/` that is not a labels file in a job directory (`invalid_labels_entry`, `labels_not_directory`) or that fails the labels gate or names another job or session than its path (`invalid_published_labels`). This matches the facts policy: `validate-pr` gates what merges, so such a file means the store was changed around the gate, and a future labels schema version needs a matching build before labels in it can merge. A labels file that passes but no longer matches its session's facts, for example because the facts were re-derived, is not used and is counted in the rollups' coverage by reason (`evidence_unmatched`, `range`, `job_unbound`, `no_facts`, `facts_ambiguous`, or `facts_missing` when the labels declare it). Sessions with a job offset are placed on the job clock; sessions without one still count toward coverage and signals but do not enter the timeline. The classed formulas cover lead time, queue, active and busy time, parallelism, concurrent sessions and agents within a job, wait unions, flow efficiency, rework signals and unavailable first-pass yield.

Missing data is never a measured zero. A wait total, the active-time family or the API-retry signal is `unavailable` with the declared reason when every contributing session lacks its field (`human_waits`, `permission_waits`, `api_retries` or `turns`), and is marked `partial` with the count of uncovered sessions when only some do. A `tool_durations` gap, such as an open session's unfinished tool call, means only some tool intervals are missing, so it makes the active-time family partial and never unavailable. Flow efficiency and the "What mattered" shares use activity and waits clipped to the job clock's `[0, lead]` window, so no share exceeds lead time; work before the task card is reported separately as active before card. Busy time is the plain sum of turn, tool and subagent intervals, so a tool call inside its own turn counts twice and parallelism measures overlapping recorded work, not concurrent agents. Status follows the latest transition once any terminal one exists, and a transition without an offset never supplies a lead time. A job whose latest transition reopens it after `done` is open again: its lead time and flow efficiency are censored at the latest session end like any open job's, and the earlier `done` stays in its transition history. Once such a job closes again, its lead time ends at the `done` that begins its final terminal stretch, the first `done` after the last reopen; a job closed only once is unaffected.

The [rollups](../mcp/src/factory/pipeline/rollups.js) answer which waste costs the most across jobs, with no who and no when. Jobs are grouped by plugin version, host, job class and waste type, never by contributor. A job's plugin version is the Desk version all its sessions report (`unknown` when any session reports none, including a session whose Desk install source was not known to be public, `mixed` when they disagree), and its host is the one host of all its sessions (else `mixed`). Published facts carry neither the task card's `kind` nor milestone 4's organization signal, so every job's class is `other` and `search_waste` is unavailable with reason `not_in_published_facts`; `coverage.json` records both.

- `rollups/muda.json` is a Pareto of muda time by waste type, largest first with ties broken by waste name, overall, per job class and per plugin version, with each waste's share, cumulative share and job count. Muda time comes from labels: a finished job counts only when every one of its sessions has usable labels for it, and a waste the evaluator did not find is then a measured zero. Each session's labeled waste counts once in any one total, even when the session is bound to several jobs (the labels of the first such job by job ID are used); each Pareto reports the labeled sessions it summed and how many of them several jobs share. A job with some sessions labeled is excluded as `partial`, and one with none as `not_labeled`. A group without a fully labeled job has no Pareto, and a Pareto with no muda has no shares.
- `rollups/measures.json` gives the measure catalog's median, 75th percentile and counted jobs overall and per plugin version, host and job class: `lead_time`, `queue_before_start`, `active_time`, `flow_efficiency`, `human_wait`, `permission_wait`, `api_retry_wait`, `tool_failures`, `tool_retries`, `api_retries`, `compactions`, `retouches`, `muda_time`, `muda_time.<waste>` and `search_waste`. It lists andon's quality measures: `tool_failures`, `tool_retries`, `api_retries`, `retouches` and `muda_time.defects`.
- `rollups/tool-kinds.json` sums calls and failures per tool kind over every session with facts, each session once, most failures first.
- `rollups/coverage.json` counts unattributed sessions and their session time, and labels files used and unused by reason.
- `rollups/index.md` renders all four.

Only finished jobs count. A job is finished when its status is `done` or `cancelled` and its lead time is not censored; every measure of any other job, including a job reopened after `done`, is excluded as `open_job`, because its totals so far are right-censored and the newest plugin version always has the most open jobs. Each group reports its open jobs. Only complete values count. A finished job's value is excluded when the formulas mark it unavailable or `partial`, and each measure lists its exclusions by reason; a measure no job supplies has no median, never a zero. Medians and p75 use the nearest-rank method: sort the counted values ascending and take the value at 1-based rank `ceil(p × n)`, so the result is always a measured value. Output is byte-stable: JSON keys are sorted and every list has an explicit order.

### The kaizen check

In a job that can write issues but not code, the store's build runs `factory.js kaizen-check --store . --repo <owner/repo>` with the workflow token in `GH_TOKEN` ([kaizen.js](../mcp/src/factory/pipeline/kaizen.js)). A kaizen card is an open issue labeled `kaizen` whose body holds one fenced `yaml` block with `kaizen: 1`, a `signal` from the measure catalog, a `job_class` (`any`, or a class the store fills), optional `evidence_jobs`, an optional `countermeasure` pull request URL, the `plugin`, the `version` that first carries the countermeasure (empty until it ships) and a `hypothesis` naming a measure and a direction (`down` or `up`). For each card with a version, the check takes the finished jobs of that class whose every session ran the plugin at that version or later (after) and those whose every session ran an earlier version (before); jobs whose sessions straddle the version are left out as `mixed_versions`, jobs without the plugin as `plugin_not_reported`, and any job's excluded measure under its own reason. Versions order by semantic-version precedence, as Desk's release checks do.

The [comparison](../mcp/src/factory/pipeline/compare.js) treats jobs that share a session as one independent group, because the per-job measures count that session's events in each of them; it reports each side's jobs, groups and median (nearest rank), the change in median (after minus before) and its 95% cluster-bootstrap interval from 10,000 resamples of the groups, seeded with the card's number so every build reproduces it. A side enters the comparison only when a distribution-free 95% interval for its median can exist: with n independent groups the chance that all of them fall on one side of the true median is 2 × 0.5^n, which must be at most 5%, so each side needs at least 6 groups. The code derives that minimum from the confidence level rather than storing it. Below it there is no interval and no verdict, whatever the values. The card gets `confirmed` when the whole interval lies in the hypothesis's direction and `not-confirmed` when it lies wholly in the other. Otherwise it carries neither, and the comment says which of two things holds: "not enough independent jobs yet" (no interval) or "no clear change so far" (the interval touches or spans zero). Published facts do not carry a job class yet, so every job is `other`; a card that names any class other than `any` or `other` gets the error `job_class_not_published` rather than waiting forever. A card without a version gets a comment saying so, and a card that does not parse gets one comment listing stable error codes with the field or block line. The check keeps exactly one comment of its own per card, edits it only when the numbers change, and never closes a card. A card whose issue calls fail is reported with a stable code and the rest are still checked; the command then exits 1. It echoes nothing from the card but validated values, and its comments carry no date or time.

### Andon

Then the build runs `factory.js andon --store . --repo <owner/repo>` ([andon.js](../mcp/src/factory/pipeline/andon.js)). Andon watches only the plugins listed under `andon.plugins` in the store's `factory.json`, a maintenance path that intake pull requests cannot change; a store without the file raises nothing. For each tracked plugin, quality measure (`tool_failures`, `tool_retries`, `api_retries`, `retouches` and `muda_time.defects`) and job class, it uses only finished jobs whose every session ran exactly one version of the plugin, and treats a version as comparable when its jobs form at least 6 independent groups, the same minimum as the kaizen check. It compares the latest comparable version with the comparable version before it, so a version superseded before it gathered enough jobs is skipped rather than blocking the comparison. When the 95% interval for the change in median lies wholly above zero (worse), it opens an issue labeled `andon` titled `Andon: <plugin> <version> <measure> <job class>`, or updates or reopens the one it opened before, so there is never a second issue for the same alarm. The body gives the numbers, lists every compared job as evidence, and names every other plugin whose versions changed between the two sets of jobs; the regression then belongs to that set of versions, not necessarily to one plugin. The build closes its own andon issue, with a comment, when the alarm's version or a later comparable version is no longer clearly worse than the baseline; with too few groups to compare, it neither opens nor closes. A reviewer who judges an alarm not to be a real regression labels it `andon-dismissed`: the build never reopens or closes that issue, but when its numbers change it updates the body and adds a comment with them. It reads and changes only issues `github-actions[bot]` opened. Andon watches quality measures only, so no flow gain can offset a quality regression.

Each job Markdown report has exactly four second-level sections: `What happened`, `What mattered`, `What was waste` and `What we could not see`. Every Markdown value shows its evidence class. The job report names public pull requests and counts private references. The index reports sessions seen as unavailable, because the store only receives sessions that published facts, and includes bound and unattributed session counts, host counts, every unavailable field/reason rate and plugin-version session counts. Generated files contain no calendar dates, times of day, task names, local paths or transcript text. `job-link` reuses the binding module's accepted job-ID calculation and points to the job Markdown on the store's `reports` ref.

The [runner](../mcp/src/factory/derive-run.js) combines the existing native derivers, job binder, store resolver and consent-aware outbox. Per-session locks prevent concurrent derivations from overwriting one another. Receipts retain source identity, size, modification time and the effective marker hash. [Lifetime reconciliation](../mcp/src/factory/session-lifetime.js) checks native resumes and later root activity before treating a marker as ended; unclassifiable or over-limit lifecycle records cannot certify closure. Sweep and file-based requests use only the protected marker reread under the derivation lock; an enumerated copy cannot override that read on timestamp grounds, and a missing file cannot fall back to the copy. Quietness and source identity are checked under the lock. `sweep(env, { quietMs: 600000 })` derives quiet changed logs and currently ended sessions, not busy resumed sessions with stale end markers. A requested `derive --wait-quiet` also rechecks quietness under the lock, including late shutdown writes. Markers remain available for retry and later resumes. Each session start runs `sweep` before delivery, described next.

## Delivery: flush, finalize and the boot check

[`flush(env, { store, runner, deadlineMs })`](../mcp/src/factory/flush.js) is the only code that sends anything to a store, and it never sends local facts. It takes `flush.lock` in the protected state folder (a lock older than ten minutes is abandoned; a live one returns `locked`), reads the store's consent and account, and transforms every outbox file that is not quarantined with `toPublished` and the public gate `validatePublishedBytes`. Each referenced repository's visibility, each plugin's install source and the store's own visibility, and the visibility of the desk's own GitHub remote, come from the seven-day cache or `GET /repos/{owner}/{repo}` with the account's token: `private: false` is public, `private: true` private, and 403 or 404 unknown. Because answers are cached for seven days, a plugin repository that turns private, or a store that turns public, can keep its old answer for up to a week. A desk that is not known to be private publishes machine-keyed job IDs without timing, keyed by the protected 32-byte machine secret. A file the transform refuses (`implausible_session_span`, `session_id_not_v4`, `invalid`) or the gate rejects (its first error code) is quarantined and never sent. When nothing changed since the last delivery, the flush ends there without a network call.

Otherwise it reads the store. With push permission the machine's intake branch `intake/<intake_id>` lives in the store; without it, in the account's default-branch-only fork, created on first use and updated with `merge-upstream` (a fork that is not ready yet returns `fork_pending`). Closed intake PRs are read newest first, page by page, down to the last PR already read, which is remembered by number in status and moved only after every page has been read. When the store automation (`github-actions[bot]`) commented a first line `factory-rejected: <code>` on one, followed by one such line per further code, every file of that PR, all pages of up to 500, is quarantined with its first data code. When every code is `merge_conflict` or `unexpected_merge`, the intake branch was stale, not the facts bad: nothing is quarantined, the files go out again on a branch rebuilt from the store's current default branch, and the flush reports `intake_stale_retried` with `stale_retries`, the number of stale-refused PRs it read, instead of `delivered_pr_open`. `validator_unavailable` never closes a PR. Known limitation: the comment names no file, so a rejected PR quarantines its good files too; a follow-up needs the store to name the offending files, or the flush to re-check each file against the current gate and resend the ones that pass. Accepted waste labels travel the same way: each local labels file becomes its published form through `toPublishedLabels`, with the job keyed exactly as its session's facts are, and the labels gate `validateLabelsBytes`; one either refuses (`invalid`, or the gate's first code such as `too_large`) is quarantined at `quarantine/<store-slug>/labels/<job>/<session-id>.json` and never sent. A rejected intake PR quarantines its labels files with its facts, and a stale one sends them again, under the rules above. Labels go only with their session's facts, already on the default branch or in the same batch, because the store's gate refuses labels without facts and that refusal would quarantine every file of the PR; labels whose facts are not there yet wait for a later flush. Labels whose facts are quarantined, by this flush, by a rejection it reads or by an earlier flush, would wait forever, so they are quarantined too, as `facts_quarantined` naming those facts. Files whose exact published blob already sits at `facts/<name>`, or at `labels/<job>/<session-id>.json` for labels, on the store's default branch are marked delivered. The rest, at most 500 files and 24 MiB per flush with facts first, become one tree and one commit titled `Factory intake`; only the intake branch is force-updated, to exactly that commit, and left alone when it already holds the same tree on the same base. The open PR for that head is reused, or one is opened titled `Factory intake` whose body is only the file count. Store trees, PR lists and comments are read as data and never executed.

Every outcome is one stable code: `delivered_pr_open`, `intake_stale_retried`, `nothing_pending`, `not_opted_in`, `no_account`, `gh_missing`, `gh_too_old` (older than 2.40.0), `auth_failed`, `store_missing`, `fork_pending`, `rate_limited`, `offline`, `locked`, `deadline` or `unexpected`, recorded as `last_flush` in `status.json`. The token comes from `gh auth token --user <account>`, lives only in memory and reaches `gh api` only as `GH_TOKEN`, with `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1` and `GIT_TERMINAL_PROMPT=0` and every ambient token removed. It never appears in an argument, a result, status, an error or a file. `deadlineMs` (120 seconds) is checked before and after every `gh` call, and a call still running at the deadline is abandoned; the Git calls that read a desk's remote share the same deadline, and one killed by its time limit or a signal stops the flush rather than reading as a desk without a remote. A flush on a machine without factory state returns `not_opted_in` and creates nothing.

`finalize(env, { job, runner })` re-derives the job's sessions from the jobs index and every marker updated since the job's finalize request, letting a session that is still writing go quiet for five seconds, within its own deadline. It then flushes every store holding one of the job's files, waiting out another flush's lock within its own deadline, and removes the request only once all of those files are delivered or quarantined. Any failure, a busy or unreadable session, or a file still in the open PR keeps the request for the next end of turn or session start. A request older than 30 days is dropped.

Both session-start hooks run the [boot-check registry](../hooks/boot-checks.cjs) after building their existing output: an ordered list of checks, each with its own budget inside one 300 ms total, and the real time each takes is charged against that total. A check that overruns, including one that blocks synchronously past its budget, or fails is skipped for that start with its line and repair discarded. When factory state exists, the skip and its elapsed milliseconds are recorded as `boot_checks` in `status.json`; on a machine without factory state it is deliberately not recorded anywhere, because creating that state would turn on finalize requests; repairs start detached with ignored stdio after every check has run. When no check has a line, the hook's output is byte-identical to what it built; otherwise it gains exactly one line, `Desk boot: <line>; <line>`, addressed to the agent. The checks, in order:

1. `factory` ([source](../mcp/src/factory/boot-check.js)) reads only consent, the jobs index, the delivered record, the outbox, quarantine and finalize names, and the first 40 lines of the bound desk's task cards. When the desk's store has no consent decision it returns `Factory: this desk hasn't decided whether to contribute measurement data; ask the operator once (desk:session-start)`. For every pending finalize request, whatever person prefix the task tools bound it under, and every finished job (`done` or `cancelled`, updated within 30 days) with an undelivered outbox file, it starts one detached `factory.js finalize` for up to eight of them. The plugin scan and the Git calls that read the desk's remote stop at the check's deadline, and the check is then skipped rather than guessing. Cards are read in the desk layout only, below `desks/<alias>/` when `DESK_PERSON` names one; nothing infers a person from other files.
2. `labels` ([source](../mcp/src/factory/boot-check.js)) runs when a store has `contribute: true`. It reads the names in `evaluate-requests/` and in each contributing store's `quarantine/<store-slug>/labels/<job>/`, the times of those job folders, and, only when both hold something, the jobs index; it never opens a request or a quarantine record. A retained request counts as waiting unless every session the jobs index lists for its job has quarantined labels. When any request is waiting, it returns `Factory: N finished tasks have no waste labels yet; run the evaluator for them in the background` and starts one detached `factory.js evaluate --pending`, which prepares their evaluator briefs again. Finished jobs with quarantined labels, from a job folder updated within 30 days or a request left out of the waiting count, are reported as `Factory: N finished tasks have quarantined waste labels that will not be delivered; tell the operator (desk:session-start)`, without a repair. `desk:session-start` Step 4.8 says what the agent does with each line.
3. `desk-health` ([source](../mcp/src/runtime/desk-health.js)) reads the bound root's own `last-start` record. A degraded record becomes one line such as `Desk: degraded (crew checkout on feature-x; writes paused); run desk_doctor`. Otherwise, when a branch is checked out, it starts a detached fast-forward. That process fetches in the background and runs `git merge --ff-only @{upstream}` only when the checkout is on its state branch (the configured one, else `main`), has no tracked changes or Git operation in progress, and has no commits its upstream lacks, checked again after the fetch.
4. `workspace-tidy` ([contract](workspace-tidy.md)).

After their output is built, both hooks start [factory-start.cjs](../hooks/factory-start.cjs) detached with ignored stdio, but only when a store has `contribute: true`. It runs one `sweep` and then a flush of every consented store within one 120-second deadline, prints nothing and always exits 0.

## Completion and remaining boundary

The [task tools](../mcp/src/tools/task.js) write `finalize/<job>.json` on `done`, `cancelled` and archive, including repeat archive calls, only when factory state already exists. They use the same job identity as binding; a factory failure emits a fixed diagnostic code without failing the completed task operation. This does not wait for a store, create consent or mark a report delivered.

The [CLI](../mcp/scripts/factory.js) advertises `finalize`, so the end-of-turn hook now starts it for pending requests, and the `factory` boot check is the backstop. Delivery to the live public store, and installed Claude, Copilot and Desktop behavior for delivery, remain unverified until the channel update is installed and the controller runs the live proof.
