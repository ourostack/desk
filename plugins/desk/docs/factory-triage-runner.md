# Factory triage runner

**Owned-catalog implementation candidate; not installed-host qualification.**
Native qualification and publication remain disabled until the implementation
gates and independent functional/security reviews pass. Unit or direct-server
proof is not an installed-engine certificate. A protected candidate is not
fresh authority or permission to publish.

## Authority and admission

The model and prepared/source content are adversarial. The parent, installed
engine/runtime and privileged policy controllers preserve the admitted scope.
Unknown applicable delivery, malformed settings, active hooks/helpers, unsafe
effective grants, provider/billing selectors and unsupported provenance hold.
The collector runs bounded non-model `doctor` only after command-bearing policy
preflight. Version/help labels and absent files alone do not establish admission.
See [the collector and policy reader](../mcp/src/factory/triage-runner.js).

The retained macOS arm64 adapter verifies the installed Anthropic signature,
Apple loader, sealed boot snapshot, SIP/authenticated root and actual shared-cache
identities. Its policy reader is pinned to inspected installed bytes, including
managed JSON/drop-ins, MDM plists, managed MCP and remote cache. Restricted
mode does not excuse incompatible managed controls. Native invalid-settings
diagnostics return fixed codes, not raw private policy. Other platforms or
unknown source revisions remain holds; no installed engine is copied or patched.
See [launch-chain inspection](../mcp/src/factory/triage-runner.js).

## Clean startup, wire and custody

Each run uses protected `triage-prepared.json`, a sealed snapshot and two
directional nonblocking FIFOs outside Git. The sole MCP command is `/usr/bin/env
-i`, followed by ordered fixed fields, the absolute resolved Node runtime and
fixed launcher. Non-Darwin fields are exactly `LANG=C LC_ALL=C TZ=UTC`. Darwin
adds only `__CF_USER_TEXT_ENCODING`, constructed from actual equal UID/EUID as
uppercase unpadded `0x<UIDHEX>:0:0`; it is never copied from inherited state.
Each launcher/server reconstructs or checks exact keys/bytes before application
imports. No HOME/PATH/auth/provider/preload selector is forwarded.
See [the shared environment and launch recipe](../mcp/src/factory/triage-custody.js),
[launcher](../mcp/scripts/launch-triage-catalog.js) and
[server](../mcp/scripts/triage-catalog-server.js).

The installed SDK remains the parser/server/transport. Wire envelope 2 accepts
JSON member order and grammatical whitespace outside strings. A bounded lexical
walk checks decoded duplicate keys at every depth, prototype keys, Unicode,
numbers and raw limits before JSON.parse; the original closed request is checked
before SDK field stripping. IDs stay control-free, nonempty strings of at most
64 bytes or nonnegative safe integers. Depth 32, 1024 keys and the existing raw
frame/aggregate/count limits remain enforced. A number token must name exactly the value JSON.parse produces: overflow, underflow, unsafe integers and lost precision such as `1.0000000000000001` refuse, while `1e2`, `0.1` and `1.50` stay accepted.

`tools/call` params take the native client's shape: `name`, `arguments` and an optional closed `_meta` holding only a `progressToken` (a string of at most 128 bytes or a safe integer) and `claudecode/toolUseId` (a string of at most 128 bytes). Both are validated and then ignored; any other `_meta` key refuses. Argument objects reach `dispatchCatalogTool` unstripped, where each tool's closed schema applies.

`notifications/cancelled` with a `requestId` and an optional `reason` of at most 1024 bytes is accepted after initialize and is advisory. The transport never forwards it to the SDK: an in-flight request still completes, a sealed submission stays sealed and nothing is partially sealed. A read that is still queued with that ID is dropped without a response.

Up to 8 requests may be in flight or queued at once. `initialize` and `candidate_submit` run alone: each waits for in-flight requests to finish, and everything behind it waits for its response, so the receipt chain stays ordered. A request over the limit gets a JSON-RPC error (`-32000`, `catalog_busy`) for that request alone and the session stays open.

Claude Code 2.1.296 probes a stdio server once with `server/discover` (protocol `2026-07-28`) before `initialize`. The server accepts that probe only as the first frame and only in the exact native shape: a string ID `server-discover-probe-<n>`, and `params._meta` holding exactly the protocol version `2026-07-28`, the bounded client info and the closed client capabilities. It answers the probe itself, never through the SDK, with a JSON-RPC method-not-found error (`-32601`), and records the answer as a `discover_answered` observation. The client reads that answer as a legacy peer and sends `initialize` with `2025-11-25` on the same process. A second probe, a probe after any other frame, or any other request before `initialize` still closes the session with `protocol_state`. A respawned server still cannot continue a session. The direct lane sends the recorded native probe bytes first, so both lanes cross the same handshake.

Client offers `2025-06-18` or `2025-11-25` negotiate only `2025-06-18`.
Bounded name/version and optional title/description/websiteUrl are inert data.
Only closed roots/listChanged, empty elicitation form/url, and the exact optional
`io.modelcontextprotocol/ui` MIME declaration are recognized; sampling, tasks,
experimental and unknown extensions reject. None enables counterpart calls.
The custom server response remains tools-only with four exact tools.
Unknown notifications and unsolicited responses refuse; well-formed unknown
requests get side-effect-free method-not-found. Actual installed-native
qualification is not inferred from direct SDK compatibility.
See [wire and protocol enforcement](../mcp/src/factory/triage-protocol.js).

The repository's Node≥20 floor is unchanged. This owned-catalog mechanism
requires the selected runtime's actual `node:module.registerHooks` capability
for its complete-load provenance; missing capability holds before run-resource
creation. The current implementation does not claim owned-catalog support for
Node20 or silently substitute a weaker module inventory.
See [preparation capability checks](../mcp/src/factory/triage-custody.js).

Owned-catalog launch is supported only on Darwin, the one host with process provenance. `ownedCatalogHostSupport()` is the single host split: on any other host the direct lane, wire cases and native runs refuse with `provenance_unsupported` before spawning a launcher, server or native engine, so no model turn starts and no receipt exists. Linux keeps POSIX private-file custody (uid, owner-only modes, FIFOs); Windows has no POSIX owner and mode bits, so that custody refuses there too. Tests follow the same split through one shared helper and assert this refusal on an unsupported host instead of skipping. Unit tests that read the installed Claude Code 2.1.296 engine run only with `DESK_TRIAGE_REAL_CLI=1`; CI never depends on a host engine, and the real-engine checks belong to the qualifier run. See [host support](../mcp/src/factory/triage-custody.js) and [the test helper](../../../tests/desk/mcp/__tests__/factory/_owned_catalog_host.mjs).

So that every POSIX host, including Linux CI, measures the same custody and control code, each Darwin-only or real-engine scenario also runs through a test-only facade. `createNonacceptedOwnedCatalog()` runs the actual launcher, server, FIFOs, restore and materialize code with two substitutions: host support is assumed, and Darwin `ps` provenance is an observer double that requires both owned processes to be live and reports a fixed epoch start. `createNonacceptedControlHost()` runs the actual control collection and local admission readers against a caller-built engine pin and private managed roots. Both keep every receipt, custody record, run and control collection in their own fresh registries. Production code never calls them, and no option, environment variable or file selects them. Real restore refuses any bundle that carries the observer double's epoch start, so facade evidence cannot be restored as real custody. `runNonacceptedDirectQualification()` drives the direct-only qualifier through the custody facade and takes no launch, so it cannot reach native runs or write a qualified record.

qualification directory, executing admission/auth/native commands or touching

through a separately allocated synthetic-custody, memory-only unit transaction.
That facade always returns `authority:false`; synthetic launch counters and

The real qualifier takes only the engine path and environment and refuses a launch that carries anything else; `runOwnedCatalogNative`, `collectTriageAdmission`, `collectTriageControls` and `inspectLaunchChain` start or read everything themselves. Those substitutions live only in the nonaccepted facades. The qualifier's import is inert, and its
direct entry still calls the fixed production route. See

The direct path uses the installed unmodified SDK Client, ordinary latest offer
and native-shaped metadata, without forced-version or wire-order normalization.
The parent opens/drains the receipt reader before spawn, independently observes
live launcher/server lineage, command, clean environment and loaded source
closure, then sends fixed ready control. A successful submit response waits for
its authenticated private receipt to drain. Native success/exit or native MCP
EOF initiates server stdin closure; server alone emits terminal, then launcher
and parent verify normal process/stdio closure. One absolute deadline includes
the teardown reserve. Initial FIFO zero reads are not terminal proof. These are
first-party runtime controls, not a universal OS sandbox or privileged-admin
tamper-proof claim. See [custody and lifecycle](../mcp/src/factory/triage-custody.js).

A catalog session closes in exactly one of two accepted ways, and the terminal receipt names which: `stdin_eof` when the client ends the server's stdin, or `client_sigint` when the client sends SIGINT. Off Windows, Claude Code 2.1.296 closes a stdio server by sending SIGINT, then SIGTERM if the process is still alive after 100 ms, then SIGKILL 400 ms later; it never ends stdin. The launcher therefore treats the first SIGINT after ready as a graceful client close. Only the launcher starts a server close, so it signals the server only while no close is under way: it stops forwarding stdin and passes the SIGINT to the server, which runs the normal finish path and writes the `client_sigint` terminal itself. If the qualifier's finish frame already started a stdin-EOF close, the launcher forwards nothing and the terminal keeps `stdin_eof`, because a signal that reaches a server already exiting could kill it after its terminal. A SIGTERM after that SIGINT is not forwarded either; the launcher waits for the server's own close, and the engine's later SIGKILL reaches only the launcher, which then fails closed. A second SIGINT, SIGHUP, a SIGINT before ready and a SIGTERM with no SIGINT before it stay fatal. Signalled directly, the server still exits cleanly on a SIGTERM after a SIGINT only once its terminal receipt is durably written. The parent stops waiting as soon as it sees a `server_refused` observation or a launcher exit that is nonzero or signalled, instead of waiting for the deadline, and a native run whose session was refused sends SIGTERM to a native process still running instead of waiting for it to close by the deadline, then returns that refusal. The native run asks to finish on both the success result and a zero native exit, in either order, so the parent sends at most one finish frame after ready; a second request before the terminal drains sends nothing, because the launcher refuses a third control frame. The direct lane can replay the engine's exact SIGINT, SIGTERM and SIGKILL schedule, with the finish frame sent up to 20 ms on either side of the SIGINT, through the nonaccepted facade only. That replay judges the launcher as the native lane does: the engine's signals can reach the launcher after its last write, while Node tears the process down, so only the launcher's authenticated `launcher_exit` observation counts, never its own exit status.

The client times its `server/discover` probe with `min(3000, floor(MCP_TIMEOUT / 3))` milliseconds, with `MCP_TIMEOUT` defaulting to 30000, and a probe that times out leaves a 7-day legacy verdict in the client's state. A native run whose server read the probe at or after that timeout from native spawn may have timed out client-side, so it fails with `native_probe_late` rather than passing on a handshake the client may not have seen.

A native run also observes the native process itself with `ps`. Its parent must be this process, its command line must be exactly our launch (the resolved engine path and argv), and the executable must hash to the pinned Claude Code 2.1.296 engine. The observation is part of the restored custody: real restore checks that the native identity names the run's PID and recorded invocation. A Node imitation of the engine fails this check, so the real export never accepts it as a native run.

Two timing windows remain and are documented rather than closed. First, between the native init event and the SIGTERM that ends a rejected run, the native process keeps running; the deadline and reaping bound it, but a watcher is not synchronous prevention. Second, the server's module inventory is taken inside Node's load hook over the exact source bytes Node evaluates, so the hash and the load cannot differ; the parent's later re-hash of each file only confirms the files on disk still match.

These checks prove runtime confinement against the model child. They are not tamper-resistance against code running as the operator's own uid, which can modify Desk itself. Each real run therefore re-checks the launch chain, controls, sign-in, tool list and live receipts instead of trusting an earlier result.

### Accepted limits

These limits were reviewed and accepted. They are not open defects.

- **The boundary is the model child, not the local user.** A process running as the operator's own uid can write a complete, self-consistent evidence directory, because restore verifies receipts with the key stored beside them. It can also swap the installed engine around exec time, because the native identity is a path, argv and file-hash check rather than an executable-image check. It can also pass structured `owned` and `fixture` inputs to the real exports. None of these can fake a live run. Each real run re-checks the chain, controls, sign-in, native init manifest and live receipts, and a different fixture fails at reload.
- **Model provenance is not proved.** An allowlisted `HTTPS_PROXY` with `NODE_EXTRA_CA_CERTS` in the operator's environment could put a scripted model behind a genuine engine. Qualification proves the engine's tool surface, not where the model's answers came from.
- **`notifications/cancelled` is advisory.** It never interrupts a request in flight. It never unseals or partially seals a submission. It only drops a read that is still queued.
- **A SIGINT is a graceful close.** Claude Code's first SIGINT after ready closes the session with a `client_sigint` terminal receipt. A SIGINT from any process running as the same user looks the same, so it can end a run early. It can never make a run pass, because acceptance still needs a sealed submission, the matching native tool result and native success.
- **Two module roots trust the same uid.** The owned server and the parent load modules from the source tree and from the `node_modules` folder Node resolves the MCP SDK from (inside a checkout, or the runtime pack beside an installed source mirror). Both must be owned by this uid or root and closed to group and world writes. The runtime pack is checked against its archive hash only when it is extracted, so a same-uid writer can change a module there. A change after qualification is caught, because every loaded server module and every file of the parent's dependency packages is hashed in the record. A change before qualification is qualified with it.
- **HOME is inherited, validated and bound, not taken from passwd.** The design reviewer preferred the passwd home, so an ambient HOME could not select another home. We kept the inherited value: it must be an absolute, normalised directory owned by this uid with no group or world write, and it is part of the environment fingerprint, so a different HOME makes the record stale (`environment_changed`). Task 6 inherited HOME without these checks, and tests and operators that isolate HOME keep working.
- **An operating-system update makes the record stale.** The chain fingerprint binds the macOS build and the dyld shared cache, so the record goes `stale/chain_changed` after an update, and the loop qualifies again within its once-a-day limit.
- **The engine pin follows a retained build.** Triage keeps working after Claude Code updates only while the pinned 2.1.296 build stays in `~/.local/share/claude/versions/`. Whether that build updates itself when run with `-p` is not verified; each run re-checks its hash.
- **The measurement guard reads this process's own `NODE_OPTIONS`.** cmux's `--require` preload removes itself from `process.env` before the guard reads it, so a cmux shell does not trip the guard. Nothing relies on that.
- **The `server/discover` fallback is pinned to Claude Code 2.1.296.** The probe shape, the `-32601` answer and the probe timeout come from that engine's source. A native run is accepted only for the pinned 2.1.296 engine hash, and any other engine is refused before launch. A probe in any other shape, a probe that arrives late, or a client that does not fall back to `initialize` on the same process all close the session rather than pass.

Fixed authenticated `observation` frames on the same private receipt FIFO retain
first input/output bytes before parsing, refusal codes, write/backpressure and
closure metadata. They have separate diagnostic ordinals and cannot advance or
replace bootstrap/submit/terminal. Up to 16 server observations and one launcher
exit observation share the existing 2 MiB/393216-byte receipt bounds; the pump
has a fixed 24-frame ceiling. Each raw prefix is bounded to 8192 bytes, with original
length/hash and explicit truncation. The launcher retains an idle writer solely
for its actual child-close observation, writes only after the server is closed,
then closes it. A second bootstrap or replacement server remains invalid, and
every later receipt must carry the bootstrapped server PID.
Null pre-exit metadata is unobserved, not proof of successful exit; observations
are protected evidence, never an MCP tool/resource or model result.
See [observer validation](../mcp/src/factory/triage-custody.js),
[server](../mcp/scripts/triage-catalog-server.js) and
[launcher](../mcp/scripts/launch-triage-catalog.js).

## Qualification and protected unaccepted output

The explicit qualifier's direct lane runs actual non-model server subprocesses;
it never issues a qualified record without two native positive receipts. The
supported way to run it is `factory.js triage-qualify` (next section); the
script itself takes an engine and an evidence folder:

```sh
node plugins/desk/mcp/scripts/qualify-triage-runner.js --cli /absolute/existing/engine --out /protected/evidence
```

Evidence remains owner-only outside Git. The version-3 `owned_catalog_mcp`
record v7 binds protocol envelope 2 and its schema/negotiation identity, recipe
version 3, table E296/3, controls /3, both control
collections and their closed builtin-basis hashes, exact optional false-map
and eleven-ID registry hashes, and current effective source-fold identities.
It rejects old safe-mode/native-path/probing records and unissued caller objects.
Reusable invocation identity permits only seven typed per-run bindings:
generation, snapshot path/hash, receipt/control FIFO paths, deadline and protected
run directory. Every other command/flag/tool/settings/env/message byte stays
fixed. New authorized prepared content requires a fresh full handshake; the
synthetic fixture is not a permanent production input freeze. That fixture ships beside the custody module as `v12-owned-catalog.json` and is part of the owned source identity, so tests read it there and a changed fixture is a changed source.
See [qualifier](../mcp/scripts/qualify-triage-runner.js) and
[record/identity verification](../mcp/src/factory/triage-runner.js).

An observed empty/mismatched native init manifest rejects pending bootstrap
immediately. A successful result or closed child without authenticated
bootstrap also fails immediately; a watcher or deadline is not synchronous
per-tool prevention. Failed transactions retain bounded protected invocation,
inline config/settings, stderr and lifecycle/receipt evidence. Unobserved
channels are distinct from fully observed empty channels. Old failed attempts
remain failures and are never reconstructed as actual receipts.

Invocation serialization and lifecycle snapshot exceptions are captured
inside the transaction boundary. Captures retain bounded raw stdout/stderr
and receipt bytes, including invalid UTF-8, with truthful optional-channel
observations and stage receipts. A capture error never erases the first
startup refusal. Missing protected stage persistence stops qualification
before another launch; failed output creation or reload returns a bounded
hold rather than an unhandled exception.

Native/private submit proof requires the actual closed manifest, correlated
prepared/card Reads, exact submitted bytes/receipt ID, one native session shared
by init/tool/result events and normal terminal/exit. Two native sessions must be
genuinely distinct; changing a receipt ordinal is not a second launch. Missing,
forged, mutated or cross-session evidence holds. See
[native correlation and restoration](../mcp/src/factory/triage-custody.js).
Restoration also compares the full invocation's owned launch with the
receipt-bound custody launch; coherently changing a deadline and its argv field
does not create a valid replacement identity. See
[the restored invocation checks](../mcp/src/factory/triage-custody.js).

Node 6 materializes only an exact protected **unaccepted** candidate and
original-brief provisional row counts. Node 8 separately rereads fresh
card/claim/ruling/evidence authority before acceptance, annotation or publication.
Model restraint, prose, unchanged sentinels or one successful run cannot replace
the required proof. Source/policy drift invalidates acceptance/new launches; this
is not synchronous prevention of arbitrary privileged mutation.

The current candidate still requires complete lifecycle/fatal-case proof,
persisted qualification conformance and strict final coverage. Neither this
document nor the local suite asserts installed-host qualification, release,
scheduling activation or live rollout.

## How the record comes to exist and when it must be redone

The loop's triage step launches only with a record that restores. The record lives at `<factory state>/triage/qualification/qualification.json` (the factory state folder is `~/.local/state/ouroboros-skills/desk/factory` unless `XDG_STATE_HOME` moves it).

### For the operator

```sh
node ~/.claude/plugins/cache/ourostack/desk/<version>/mcp/scripts/factory.js triage-qualify --check
node ~/.claude/plugins/cache/ourostack/desk/<version>/mcp/scripts/factory.js triage-qualify
```

- `--check` launches nothing. It prints what restore says now: `qualified`, `missing`, `stale` with a reason and whether qualifying again can clear it (`requalify`), or `damaged` with a reason. It waits for no one: while the loop worker or a qualification holds `loop-worker.running`, it answers `busy`.
- Without `--check`, the command qualifies when the record does not restore. It starts two real model sessions on the subscription (about a minute in all), reserved together as one triage opportunity in the shared launch ledger, so it refuses when the day's launches or the current window are used up. It refuses quietly on any host but macOS arm64, in a headless session, with a billing variable set, under coverage or loader measurement, without the pinned engine, or when signed out.
- An earlier record is moved aside as `qualification.aside-<UTC stamp>-<hex>` and never deleted. Each is about 8 MB; you may move old asides to the Trash.
- The command also clears an automatic suspension (below).

### What the loop does by itself

When restore says `missing`, or `stale` with `requalify: true`, the loop worker qualifies once per UTC day at most (`autoQualifyTriage` in [triage-qualify.js](../mcp/src/factory/triage-qualify.js)), under its own lock and with at least 20 minutes left in its run. The marker `triage/auto-qualify.json` is written before the attempt starts, so a crash never retries the same day, and a marker that cannot be read counts as today's attempt. After three attempts in a row for the same host-side reason, automatic qualification stops for that reason and reports `auto_suspended` until `triage-qualify` runs. Reasons a release causes (`record_version`, `source_changed`, `engine_changed`) never count toward that limit. The two launches are reserved only after the qualifier's own chain, admission, control and sign-in checks pass, just before the first launch; a refusal there launches nothing and puts the earlier record back.

### What makes a record stale

The record is keyed on content, not on where Desk is installed, so a release with byte-identical files, a copy at another path, or a different ambient `PATH` or `TERM` keeps it. Restore answers ([restoreTriageQualification](../mcp/src/factory/triage-runner.js)), checking the cheap things first and launching nothing:

| Reason | What changed | Qualifying again helps |
| --- | --- | --- |
| `record_version` | An earlier record version (v6 was keyed on absolute paths and the ambient environment) | yes |
| `qualification_failed` | The last qualification failed; its `failure-capture.json` is beside it | yes |
| `source_changed` | A runner, custody, catalog, qualifier or helper file, the fixture, `package-lock.json`, a file of the parent's dependency packages, or a loaded server module | yes |
| `runtime_changed` | The Node runtime's path or bytes | yes |
| `engine_changed` | The engine pin moved, or the record's engine file changed while the pinned build is still installed elsewhere | yes |
| `engine_unpinned` | No installed file is the pinned 2.1.296 build; the loop opens the improvement card "The triage runner's engine pin is behind the installed Claude Code" | no: a Desk release must re-derive the engine table |
| `engine_mismatch` | The caller named a different engine than the record's | no |
| `environment_changed` | The constructed child environment: HOME, the account, the temporary folder, `CLAUDE_CONFIG_DIR`, proxy or CA variables | yes |
| `environment_unsafe` | HOME, `CLAUDE_CONFIG_DIR` or the temporary folder is not a private folder of this account | no |
| `chain_changed` | The launch chain: engine signature, macOS build, sealed system volume, dyld shared cache | yes |
| `chain_unavailable` | The launch chain could not be inspected | no |
| `policy_changed` | Managed or user policy sources | yes |
| `policy_blocked` | Policy no longer admits the fixed invocation | no |
| `host_unsupported`, `measurement_active` | Not macOS, or coverage or loader measurement is active | no |

A `damaged` record (unreadable, non-canonical, an unknown shape, receipts that fail restoration) is never treated as stale and never replaced automatically; `triage-qualify` moves it aside. `loadTriageQualification` keeps its earlier contract on top of restore.

### The child environment

The engine, its sign-in probe, `doctor` and the OS readers get one constructed environment ([triageChildEnvironment](../mcp/src/factory/triage-runner.js)): `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `TERM=dumb`, `LANG=en_US.UTF-8`, `SHELL=/bin/sh`, the account's name, the validated inherited HOME, the system's per-user temporary folder from `getconf DARWIN_USER_TEMP_DIR` (owner-only), and, when set, `CLAUDE_CONFIG_DIR` (an absolute private folder) and the proxy and CA variables. Nothing else is inherited. Intent selectors and billing variables are still read from the ambient environment first, so filtering never hides them.

### The engine

The pin stays: the reviewed byte ranges of Claude Code 2.1.296 back every control. The runner finds that build by content: the record's engine, then the default `claude`, then Claude Code's own versions folder. A candidate counts only as a regular file whose folders, up to `/`, only this account or root can change.

### Where the runner loads from

The installed plugin copy has no `node_modules`. [triage-home.js](../mcp/src/factory/triage-home.js) (`importTriageRunner`) loads the runner from the plugin's own folder when its packages resolve there, and otherwise from the source mirror that the MCP server's own runtime preparation admits for exactly this source, chosen from the account's home alone. A failure is a quiet `runtime_unavailable` or `runtime_unloadable`.
