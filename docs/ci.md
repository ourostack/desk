# CI, releases and red main

One tier: a pull request runs all of it, and from opening a pull request to the release is under 10 minutes, so no check waits until after the merge. The workflows in `.github/workflows/` are the list of checks; `CI gate` knows which jobs a pull request may skip, so a skipped job never passes it by accident. Main requires `CI gate`, `Windows suite`, `Validate skills`, `Claude Code plugin load` and `ax-xray` (the Ouro AX X-ray and action claims, which fail when a must claim does not hold), and merges on green with auto-merge (no merge queue). Main does not require branches to be up to date: with a 6 minute run that would make every busy hour a queue of rebases.

Only a change to nothing but `docs/`, `SETUP.md` or `LICENSE` may skip all but Quick checks and the skill checks. The root `README.md` is not on that list, because a test reads it. `windows_suite_shards.test.js` keeps the list the same in Quick checks, the Windows suite and both main workflows.

**Keep the pull request under 10 minutes.** The longest of the coverage shards and the Windows shards sets the time. When one grows past about 3.5 minutes, add shards (`strategy.job-total` splits the coverage shards; `WINDOWS_SHARDS` and `suite-durations.json` split the Windows suite) instead of accepting the wait. A check that must run on a pull request never moves off it; make it faster.

**macOS checks run on `main` after the merge, never on a pull request** (the `macos-checks` job is skipped for `pull_request`, and `CI gate` requires it only on other events); a red run opens a `main is red` issue. The reason: **macOS runners are the scarcest pool** (5 at once on a standard plan, shared by the whole account). Measured over the last 30 merged pull requests (2026-11-18), the Windows shards set an 8 minute floor, and every pull request that took longer than 12 minutes without a new push was waiting for a macOS slot, up to 43 minutes. So the native macOS checks (ACL and marker identity, the real browser, Crew member binding) share one job, `macOS checks`, and a new macOS check is a step there, never a job of its own. The two Darwin runtime packs are built in that job too (every host-bound pack is built by `.github/actions/build-runtime-pack`, and `production_runtime_pack.test.js` pins that each target is built on its own host on every change, not which job builds it). A pull request asks for one macOS runner.

**Qualify the affected native platforms on the actual candidate.** The Windows and macOS legs run on the pull request, so confirm the affected test files ran and passed there. If integration changes the candidate, the new push reruns them. For bounded Windows evidence on a branch, dispatch with an `only` regular expression, for example `gh workflow run desk-windows-suite.yml --ref <branch> -f 'only=^runtime/pr_publication\.test\.js$'`. A partial run qualifies only its selected tests.

**Read a cancelled Windows shard from its progress.** `run-suite-files.mjs` replaces `results.json` atomically as each file starts and finishes (`complete: false`, `expectedFiles`, and `running` naming the current file and its start time) and writes `complete: true` only after the last file; `run-as-standard-user.ps1` prints the shard's output to the job log while it runs. A shard the 25-minute job limit cancels therefore uploads its finished files, and the aggregate `Windows suite` names the file it was on instead of reporting every file missing. This changes what is reported, not any deadline: the 10-minute file limit and the 25-minute job limit stand, and a cancelled shard stays red. Original #1930 (job 140867971783, shard 20/26 on #1929) ran its test step 20.5 minutes after a 4-minute setup (other shards: about 30 seconds) and left no file-level evidence, so whether it was a slow runner, two files at their limit or one hung file was not observable.

**Keep archive evidence separate.** Windows archive-handoff receipts use `windows-archive-race-observations.json`; finite identity-bridge observations use `windows-archive-identity-observations.json`, so a later identity fixture cannot overwrite the handoff's failed capture or actor receipts. The same per-shard, per-attempt archive artifact retains either or both files when present. Identity observations are not proof of the handoff's native stages or a passing archive.

**Read early actor failures from their own receipts.** The [handoff collector](../tests/desk/mcp/__tests__/tools/archive_handoff_qualification_child.mjs) retains each child's existing bounded `productionAttempts` in `actorReceipts[].productionAttempts`, including capture failures before a move decorator exists. The top-level `productionAttempts` still belongs to the parent process. An actor's `receipt` keeps its existing move/candidate observation when available, otherwise falls back to its last production attempt; missing stages remain explicit. A child that exits before final IPC can still have missing evidence. These observations do not change archive outcomes, deadlines or qualification gates, and retaining a failure is not a readiness repair.

**Keep the always-on context small.** `Validate skills` runs `scripts/check-context-budget.mjs`, which measures what every Copilot session receives from Desk at start (the boot text on a clean desk, `using-desk`, the startup line and pointers) and fails when the boot text or `using-desk` passes its budget in `scripts/context-budget.json`. Cut the text or move it into a skill that loads on demand; raise a budget only with an eval that shows the text earns its place.

**Keep lockfiles public.** Hosted gateway tests run `node hosted/infra/check-lockfiles.mjs` for every tracked `package-lock.json`, including lockfile-only changes. Registry tarballs must resolve from `registry.npmjs.org`; the hosted lockfile also requires sha512 integrity. Repair a lockfile with `node hosted/infra/normalize-lockfile.mjs <path>`, which preserves versions and verifies integrity using the configured registry.

**Releases.** Every push to `main` runs the workflows again on the merge commit, as the tripwire for a merge that interacts badly with another. The release never releases a combination no run has checked. When a merge's pull request was tested against the main it landed on, the release builds at once. When main moved meanwhile, it holds until `main`'s own run passes on that commit (the `workflow_run` trigger in `desk-release.yml`). While a `main is red` issue is open nothing releases. `.github/scripts/release-gate.mjs` makes the decision.

**Stuck pull requests.** `pr-keep-moving.yml` comments on a PR, mentioning its author, once per head commit when it conflicts with `main` (naming the files) or a required check is red (naming the check, and saying to merge `main` in when the branch is behind). It does not update branches itself: a push made with the workflow's own token starts no pull_request run, so the required checks would sit stale.

**Red main.** When a check fails on `main` after the merge, its workflow opens a `main is red: <check>` issue labelled `red-main`, and the issue closes itself when the check passes on a `main` commit that carries the failure. The author of the pull request that turned `main` red fixes or reverts it within 30 minutes. If that author is gone, whoever reads the issue first reverts the merge commit through a pull request. Agents draining this repository's issues take `red-main` issues before anything else. A random failure gets its own issue before anyone reruns it.

**Interrupted coverage shards.** Each shard's `timings.json` is replaced atomically as files start and finish. `file_seconds` retains completed timings; `running_files` names the current file and its `started_at` timestamp. The seven-minute watchdog prints this snapshot and retains untruncated process commands in `stuck-process-tree.txt` before stopping its group. Inspect earlier timings as well as the current file: a young last child is not evidence that it consumed the whole shard budget.

**Status-budget diagnostics.** The [covered shard step](../.github/workflows/desk-mcp-tests.yml) enables `DESK_STATUS_DIAGNOSTICS=1` for the existing [late-workspace protocol fixture](../tests/desk/mcp/__tests__/runtime/late_workspace_protocol.test.js). The fixture stages `status-request-diagnostics.jsonl` inside its checkout, which the real-home guard allows; the next non-cancelled step copies that exact file into the normal shard artifact after the runner exits, including on failure. Staging outside the shard output preserves the runner's empty-output-at-start contract. A failed copy is a failed step; a shard without this fixture (or a process killed before publication) may have no receipt, reported explicitly by the copy step.

The fixture buffers up to 128 JSON-RPC requests and 2048 stages, reports dropped entries, and writes only after session shutdown (including failed assertions). Publication failure does not replace a prior close/assertion failure: both errors are retained in an `AggregateError`; either failure alone remains a failure. Unattributed stages and stages whose request was not recorded (including request overflow) increment `dropped.stages` and their separate reason counters without retaining extra stage records. Disabled mode remains inert. An unfinished request retains `endMs: null` and `metrics: null`; a pending stage likewise has no fabricated completion measurements. To use the same opt-in locally, set `DESK_STATUS_DIAGNOSTICS_OUTPUT` to a file in an existing test-owned allowed directory; without it, the fixture prints the buffered receipt after shutdown. Ordinary status calls neither enable these measurements nor change their response.

The [collector](../tests/desk/mcp/__tests__/runtime/_status_diagnostics.js) retains the initiating request ID through asynchronous runtime detail, even if that request has already answered. `session_dispatch` and `runtime_detail` bound the outer work; source stages cover root inspection, search, active tasks, factory, local sync and reader close. Times are fixture-relative monotonic milliseconds. Process CPU includes worker/background threads; optional main-thread CPU and event-loop active/idle include unrelated callbacks over the same interval, not request-only CPU. Missing APIs remain null, overlapping intervals must not be summed, and active time does not distinguish synchronous blocking from host descheduling. Admission waits and joined/cached detail have only outer boundaries, not separate attributed stages. These diagnostics preserve the existing 750 ms cap and destination checks; a local capture is not covered Linux qualification or a cause for the original #1435 delay.
