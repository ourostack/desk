# CI, releases and red main

One tier: a pull request runs all of it, and from opening a pull request to the release is under 10 minutes, so no check waits until after the merge. The workflows in `.github/workflows/` are the list of checks; `CI gate` knows which jobs a pull request may skip, so a skipped job never passes it by accident. Main requires `CI gate`, `Windows suite`, `Validate skills` and `Claude Code plugin load`, and merges on green with auto-merge (no merge queue). Main does not require branches to be up to date: with a 6 minute run that would make every busy hour a queue of rebases.

Only a change to nothing but `docs/`, `SETUP.md` or `LICENSE` may skip all but Quick checks and the skill checks. The root `README.md` is not on that list, because a test reads it. `windows_suite_shards.test.js` keeps the list the same in Quick checks, the Windows suite and both main workflows.

**Keep the pull request under 10 minutes.** The longest of the coverage shards and the Windows shards sets the time. When one grows past about 5 minutes, add shards (`strategy.job-total` splits the coverage shards; `WINDOWS_SHARDS` and `suite-durations.json` split the Windows suite) instead of accepting the wait. A check that must run on a pull request never moves off it; make it faster.

**Qualify the affected native platforms on the actual candidate.** The Windows and macOS legs run on the pull request, so confirm the affected test files ran and passed there. If integration changes the candidate, the new push reruns them. For bounded Windows evidence on a branch, dispatch with an `only` regular expression, for example `gh workflow run desk-windows-suite.yml --ref <branch> -f 'only=^runtime/pr_publication\.test\.js$'`. A partial run qualifies only its selected tests.

**Releases.** Every push to `main` runs the workflows again on the merge commit, as the tripwire for a merge that interacts badly with another. The release never releases a combination no run has checked. When a merge's pull request was tested against the main it landed on, the release builds at once. When main moved meanwhile, it holds until `main`'s own run passes on that commit (the `workflow_run` trigger in `desk-release.yml`). While a `main is red` issue is open nothing releases. `.github/scripts/release-gate.mjs` makes the decision.

**Red main.** When a check fails on `main` after the merge, its workflow opens a `main is red: <check>` issue labelled `red-main`, and the issue closes itself when the check passes on a `main` commit that carries the failure. The author of the pull request that turned `main` red fixes or reverts it within 30 minutes. If that author is gone, whoever reads the issue first reverts the merge commit through a pull request. Agents draining this repository's issues take `red-main` issues before anything else. A random failure gets its own issue before anyone reruns it.
